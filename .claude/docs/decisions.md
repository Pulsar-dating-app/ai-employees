## 2026-08-28 — request_human: Malu now proactively offers a human after two failed attempts
**Decision:** `request_human`'s tool description now instructs: if the customer directly asks for a person, call the tool right away; otherwise, after failing to answer/resolve the same question twice, proactively OFFER to connect them with someone from the team (ask, don't decide unilaterally) and only call the tool once they say yes.
**Why:** User found hand-testing: Malu never proactively offered a human handoff -- she'd just keep apologizing or retrying if she couldn't resolve something, with no path to escalate unless the customer explicitly named a human. This left `request_human` reachable only when the customer already knew to ask for a person by name, missing the more common case of a customer who's just stuck and doesn't know that's an option. Asking first (rather than escalating unilaterally on the second failure) matches how a real employee would behave and keeps the tool's own "don't hand off just because an answer isn't immediately obvious" rule intact -- still requires a genuine repeated failure, not a single miss.
**How to apply:** If this proves too eager (offering a human too readily) or too reluctant (still not offering when it should) in practice, the fix is the same shape as every other guardrail gap in this log: tighten or loosen the specific trigger wording, not the general principle. "Two attempts at the same question" is a judgment call for the model to make from conversation context -- there's no code-level counter tracking this, so it's inherently softer than the code-level MAX_LIMIT-style backstops elsewhere in this log; revisit if that proves insufficient.

## 2026-08-28 — C5 request_human reuses `conversations.status = 'paused'`, no new column
**Decision:** `request_human()` (`src/lib/agent-engine/tools/request-human.ts`) sets `conversations.status = 'paused'` on call, rather than adding a dedicated `needs_human` boolean column. No args, no `events` row, no notification/takeover/assignment logic — the card's own scope is explicitly "a flag, not a live handoff system."
**Why:** The card left "reuse `status` vs. add a column" as an open decision to make and document. `status` already allows `'paused'` (`check (status in ('active', 'closed', 'paused'))`, so zero migration), nothing else currently writes that value to *this* table (only the unrelated `company_agents.status` uses `'paused'`, for a merchant pausing the agent itself — different table, no collision), and this was already anticipated: the 2026-08-27 24h-rotation entry explicitly says C5's flag would write to `status`, and that entry's own design (never blindly reset `status` back to `'active'` on an unrelated `updated_at` bump) exists specifically so this wouldn't get silently undone. A second boolean column would be a second, redundant source of truth for "is Malu actively serving this conversation" with no real gain, since nothing else uses `'paused'` here to conflict with.
**How to apply:** F5 (not built, will surface flagged conversations) should filter `conversations.status = 'paused'` directly — no join or second column to reconcile. Known, accepted gap: `dev-chat-test`'s own 24h reuse query only looks up `status = 'active'`, so a paused conversation's next customer message in that *test* tool silently starts a new one instead of staying paused -- out of scope to fix here (D2/D3 own real conversation routing, and `dev-chat-test` is itself temporary). If a future ticket needs a *reason* captured alongside the pause (why a human was requested), that's a genuinely separate, deferred decision -- don't retrofit it into this flag without reconsidering the schema call above.

## 2026-08-28 — E2 analytics aggregation is plain JS over RLS-scoped reads, no migration/RPC; buckets follow the merchant's timezone
**Decision:** `GET /api/companies/[companyId]/analytics` (Trello E2) returns spec §15's five dashboard metrics (`conversations`, `customers`, `product_recommendations`, `buying_intent`, `checkout_clicks`) as `{ metric, total, series: [{ date, count }] }`, day- or week-bucketed. It reads raw `created_at` rows from `conversations` / `customers` / `events` through the normal RLS-scoped client and buckets them in application code — **no Postgres aggregation function, no migration**. The pure bucketing lives in `src/lib/analytics/aggregate.ts` (`aggregateAnalytics`), unit-tested with no DB. Day boundaries are computed in `companies.timezone` (fallback `UTC`) via `Intl.DateTimeFormat("en-CA", { timeZone })`; the DB query runs in UTC widened ±1 day and the aggregator re-filters each row to its true local date. Series are zero-filled across the whole range; `total` is the sum of the series. Params are lenient-defaulted like the products list route (`granularity` unknown → `day`, bad `from`/`to` → default); the only hard `400` is `from` after `to`; an over-long span is clamped to 370 days. Member-readable (`requireMember`), no admin gate.
**Why:** The card wants "a simple trend view," and every table involved already has an `is_company_member` SELECT policy, so the RLS-scoped client Just Works with no new security surface — a `date_trunc` RPC would mean a migration plus the `private`-schema / `anon`-revoke dance every public function here needs (see the 2026-08-25 `create_company_with_owner` entry), for no MVP-scale benefit. Same call as B3's "`ilike` over an FTS index — catalog sizes are MVP-scale" decision. The one real risk of the JS approach — PostgREST's silent 1000-row response cap undercounting a busy company — is handled by paging in `fetchWindow` rather than by moving the count into SQL. Timezone-aware bucketing (rather than raw UTC days) matters because "today" on a merchant's dashboard has to mean *their* today; doing it in JS with `Intl` needs no `pg` timezone data or date library (the repo has none). Splitting the pure core out mirrors B5 (`ProductRepository`) and C4 (`checkout/links.ts`) — the tricky part (week starts, zero-fill, tz shift) gets isolated unit tests instead of only being reachable over HTTP.
**How to apply:** If event/conversation volume ever makes the row scan a real cost, the upgrade is a `date_trunc('day', created_at AT TIME ZONE tz)` + `count` group-by Postgres function (service-role or `is_company_member`-guarded, `anon` revoked) — treat that as its own decision, don't reach for it before there's evidence, and keep `aggregateAnalytics`'s response shape identical so F6 doesn't care which path produced it. F6 should read `range`/`granularity` off the response rather than recomputing them. Any sixth metric added later goes in `METRIC_KEYS` (order is spec-significant) and, if it's an event, `EVENT_TYPE_TO_METRIC`.

## 2026-08-28 — C6 buying-intent detection is a model-called tool, not a classification pass (so it isn't English-only)
**Decision:** Trello C6 ships as `flag_buying_intent`, an agent tool the model calls when it sees a clear purchase signal, registered in `tools/registry.ts`. It writes one `events` row typed `buying_intent` (identity fields from `ctx`, optional `productId` validated through `ProductRepository.get` and dropped if it doesn't resolve), returns `{ recorded: true }`, and carries no `tracking_id`/`metadata`. No dedup — a customer can signal intent more than once and E2 counts occurrences. No migration: A1's `event_type` enum already has `buying_intent`. All "when to call / when not to" guidance lives in the tool description; `agents.system_prompt` was left untouched.
**Why:** The card offered two shapes — a model-callable tool or "a separate lightweight classification pass" — and explicitly worried about false positives polluting E2. A classification pass built the obvious way (keyword/phrase matching against spec §15's examples: "I'll take it", "send me the link", ...) is inherently tied to whichever language those phrases are written in; this platform serves customers outside Brazil and the LANGUAGE_GUARDRAIL already assumes any language. A tool the model decides to call recognizes intent in whatever language the customer actually wrote ("quero esse", "me manda o link", "lo quiero") with zero language-specific code, and drops into C1's existing tool-execution loop with no extra round trip — the same "let the model do the language understanding, keep our code deterministic around it" split C3's grounding tools chose. Guidance in the tool description (not `system_prompt`) matches `create_checkout_link` / `get_policy_information`, keeps the change contained, and the description is the model's primary signal for whether to call a tool anyway.
**How to apply:** If hand-testing shows Malu missing real signals or firing on browsing language, first tighten the tool description with the exact phrasing that slipped through (the established pattern in this log), and only then consider a `system_prompt` reinforcement bullet. `determineIntent` (Agent Engine step 6) stays a stub — it's synchronous prompt-building input, unrelated to emitting an event mid-loop. Any future "detect X mid-conversation and record it" need (C5's `request_human` is the next) should default to this same tool shape rather than a parallel classifier. Integration test (`tests/integration/buying-intent.test.ts`) was written against `checkout-link.test.ts`'s proven pattern but not run locally this session (Docker/local Supabase down); unit tests + `tsc` + `eslint` are clean.

## 2026-08-28 — E1 redirects link-preview crawlers without counting them as clicks
**Decision:** `GET /c/[trackingId]` (Trello E1) checks the request's `User-Agent` against `isLinkPreviewAgent()` (`src/lib/checkout/links.ts`). A recognized preview crawler still gets the same 302 to the merchant, but **no `checkout_click` row is written**. The matcher is deliberately conservative — anything unrecognized, including an absent User-Agent, counts as a human click.
**Why:** WhatsApp is the channel these links are *sent over*, and it fetches every URL in a message to render the preview card **before any human touches it**. Without this filter, every single link Malu sends would immediately register a click — the exact same class of error as typing the minted row `checkout_click` in the first place (entry below), just arriving from the other direction, and it would silently destroy the credibility of the one metric that's supposed to prove a customer engaged. Facebook/Telegram/Slack/Discord crawlers behave the same way whenever a link is pasted elsewhere. The asymmetry in the matcher is deliberate: a bot miscounted as human adds one bogus row, while a human miscounted as a bot silently *loses* a real conversion signal — the second is worse and harder to notice, so borderline cases count as human.
**How to apply:** If click counts ever look inflated, check `User-Agent`s in the wild before widening the pattern — and never invert the default to "unknown = bot". A real bot-filtering service (or moving the count server-side after a JS beacon) is the escalation path if UA matching proves insufficient; don't reach for it before there's evidence. Note the filter only guards the *count*: the redirect itself is unconditional, because a preview fetch that 404s would break the link card the customer sees.

## 2026-08-28 — C4 mints a `product_recommendation` event, not a `checkout_click` — correcting A1's original instruction
**Decision:** `create_checkout_link` writes its `events` row with `type = 'product_recommendation'` (carrying `tracking_id` and `metadata.destination_url`). E1 will insert a **separate** `checkout_click` row when the customer actually taps the link, with its own `tracking_id` left null and the minted id echoed in `metadata` instead. This **supersedes the "How to apply" line in the 2026-08-25 A1 entry below** ("C4 … should insert a `checkout_click`-typed row … when generating a link") and the matching comment in `20260825140705_create_events_table.sql`.
**Why:** Spec §15 defines a checkout click as *"when the customer clicks a tracked product/checkout link"* — and the customer taps it minutes later, hours later, or never. Writing a `checkout_click` at mint time would make E2's headline "checkout clicks" metric count links *sent*, silently inflating the one number that is supposed to prove Malu produces real buying behavior; `knowledge.md` is explicit that a click must never be overstated. It also can't be repaired later: `events` is append-only by explicit decision (no update policy, "never add one"), so E1 would have no way to downgrade a premature row. Splitting the two events is not extra bookkeeping — it's what makes a click-through rate expressible at all (links sent vs. links tapped), which is more useful to a merchant than either number alone. Verified this needs **no migration**: `events_tracking_id_key` is a *partial* unique index (`where tracking_id is not null`), so E1's click rows carrying a null `tracking_id` never collide with the minted row.
**How to apply:** E1 must look the minted row up by `tracking_id`, then **insert** its own `checkout_click` row rather than updating anything. E2's aggregation should count `checkout_click` for real taps and `product_recommendation` for links offered — do not treat the two as interchangeable. Any future event-writing tool (C6's buying-intent detection is next) should likewise type the row by *what actually happened at that moment*, not by the funnel stage it hopes to reach; the enum's three values are observations, not intentions.

## 2026-08-28 — `sidde.link` is a path on the main app, not a separate domain
**Decision:** Checkout links are `{SIDDE_CHECKOUT_BASE_URL}/c/{tracking-id}` — a route in this Next.js app (E1's future home), not a second deployed service on a real `sidde.link` domain. New server-only env var `SIDDE_CHECKOUT_BASE_URL`; outside production it falls back to `http://localhost:3000`, and in production a missing value **throws** (`CheckoutBaseUrlMissingError`).
**Why:** The C4 card explicitly left this open ("affects how E1 is deployed/routed"). A path needs no DNS, no second deploy, and works in dev and CI immediately; the spec's `sidde.link/c/{id}` is illustrative of the *shape*, and a real short domain can be put in front of this later as a plain redirect without changing a single stored row — nothing persisted depends on the host. The production throw is deliberate: silently defaulting to localhost would mean texting real customers a link they can never open, and a loud config error at deploy time is far cheaper than a dead link discovered mid-sale.
**How to apply:** Set `SIDDE_CHECKOUT_BASE_URL` in any deployed environment (see `.env.example`). E1 should build its route at `/c/[trackingId]` and reuse `CHECKOUT_LINK_PATH_PREFIX` from `src/lib/checkout/links.ts` rather than re-typing the path. Note `src/proxy.ts`'s matcher currently covers `/c/*`, so a click would run a `supabase.auth.getUser()` round-trip it doesn't need — worth excluding for latency when E1 lands.

## 2026-08-28 — GROUNDING_GUARDRAIL: check tools before answering a checkable question from general knowledge, then relay the real answer faithfully
**Decision:** Fourth platform-level guardrail in `prompt.ts`, `GROUNDING_GUARDRAIL`, in two parts. (1) Before answering any specific/checkable question (a yes/no, a fact, a claim) from her own general knowledge, Malu should consider whether the business might have a real answer on file and check the available tools first -- explicitly not gated on the question "sounding like" a typical store topic. (2) Once a tool does return a real answer, use exactly that content -- natural phrasing/tone is fine, but never paraphrase it into a guessed meaning, "translate" it into something more sensible-sounding, or add to it, even if it reads unusually/informally. Also strengthened `get_policy_information`'s own tool description with point (1).
**Why:** Found hand-testing C3 immediately after shipping it, in two rounds. Round 1: a merchant added a real (deliberately unusual/off-topic, as a test) FAQ entry, asked the matching question in chat, and Malu never called `get_policy_information` at all -- she just answered plausibly from her own general knowledge, ignoring the real FAQ entirely. Root cause: the implicit trigger to call that tool was "does this look like a shipping/return/payment/FAQ question," and an FAQ entry unrelated to typical store policy doesn't look like one -- but FAQ is free-form, a merchant can document literally anything there, so "doesn't sound store-related" was never a safe signal that answering from memory was fine. Round 2, immediately after shipping the round-1 fix: she *did* call the tool this time and got the real (informal/joke) answer back -- but then paraphrased it into what she guessed it meant, rather than delivering the actual retrieved content. Same underlying failure (a guess substituting for a real fact) one step later: having grounded data doesn't help if it gets silently rewritten before reaching the customer. Both are exactly what spec §18 (and this whole ticket) exist to prevent, so both earned a guardrail addition rather than just a tool-description tweak -- a tool's own description only helps once the model is already leaning toward calling it or already holding the result; this guardrail shapes both decisions earlier and more prominently.
**How to apply:** Part (1) is deliberately scoped to "specific, checkable" claims, not general chat/opinions/product recommendations, specifically to avoid turning this into "call get_policy_information on every message" (a real latency/cost cost, unlike the earlier keyword-expansion trick which was free because it reused an already-necessary tool call). If either half proves too narrow in practice (still skips a check, or still reinterprets a result some other way) or too broad, the fix is the same shape as everything else in this log: name the exact new failure pattern, don't just widen the wording generically. Notable pattern across this whole log now: grounding bugs keep surfacing in *stages* one fix reveals the next of (didn't check -> checked but distorted the result) -- worth remembering that fixing the first-observed failure mode doesn't necessarily mean the underlying principle is now fully enforced.

## 2026-08-28 — Trello C3: business/policy knowledge moved from always-injected prompt content to on-demand tools
**Decision:** `knowledge.ts` (Agent Engine step 4) no longer reads/returns the full `companies` row — it loads only `businessName`, which stays directly in `buildSystemPrompt`'s output (cheap, always relevant). Every other field that used to be unconditionally injected into every call (description, contact, industry, shipping/return/payment policy, FAQ) moved to two new tools: `get_business_information()` (no args) and `get_policy_information(type: "shipping"|"return"|"payment"|"faq")`, both thin wrappers around a new `src/lib/companies/repository.ts` (`CompanyRepository`) mirroring B5's `ProductRepository` shape/DI pattern exactly. `getPolicyInformation` returns an explicit `{ type, available, content }` rather than a bare nullable value, per the card's own requirement that a tool must let the model honestly say "not on file" instead of guessing.
**Why:** This is what the C3 card literally asked for ("the tools that keep Malu grounded per spec §18: the LLM must not be trusted to invent factual business information... thin, deterministic wrapper"), and `knowledge.ts`'s own file comment already named itself as the stub C3 would replace. Beyond satisfying the card, this also has a real cost benefit: every prior call paid token cost for shipping/return/payment/FAQ text regardless of whether the customer's message had anything to do with any of them — moving it behind tool calls means Malu only pays for (and only sees) the specific fact she actually needs for the turn at hand. FAQ (stored as `jsonb`) is formatted into plain Q/A text inside `CompanyRepository` rather than handed to the model as raw JSON (the old `knowledge.ts` did `JSON.stringify(knowledge.faq)` directly into the prompt) — still just deterministic templating over real data, not generation, but easier for the model to read correctly.
**How to apply:** `businessName` staying in-prompt directly (not behind a tool) was a deliberate line-drawing call, not an oversight: it's cheap and needed on essentially every turn (Malu has to know who she represents from her first reply), and isn't really a "fact that could be invented" in spec §18's sense the way a policy or a price is — it's an identity, sourced straight from the DB with zero interpretation. If a future ticket wants to push identity fully behind tools too (for a stricter grounding story), that's a real tradeoff against added latency on effectively every conversation's first turn, not a free change — treat it as its own decision, not a natural extension of this one. Validated: `npm run test:unit` (30/30, two new tool-wrapper test files), `npx tsc --noEmit` clean, `npx eslint` clean on changed files, plus a new `tests/integration/company-repository.test.ts` (seeded through the real `PATCH /api/companies/:id` route, per B2's own comment that its field shapes are exactly what these tools read) and a new round-trip case in `tests/integration/agent-engine.test.ts` proving both tools are actually reachable through the registry, not just unit-tested in isolation.

## 2026-08-27 — Product search results hard-capped at 10 (code), plus multi-category dump named explicitly (prompt)
**Decision:** `ProductRepository`'s `MAX_LIMIT` lowered from 20 to 10 (`src/lib/products/repository.ts`) -- a hard ceiling on any single `search_products` call regardless of what the caller requests. Malu's `system_prompt` (migration `20260827200000_reinforce_malu_multi_category_guardrail`) extends the prior "don't dump everything" bullet to also name "every item across several categories at once (e.g. 'todos os calçados e camisetas')" as another instance of the same rule, not just literal "full list"/"all products" wording.
**Why:** User found: "estoque inteiro" (the whole stock) is now correctly declined (previous entry), but "todos os calçados e camisetas" -- broad, but not literally "everything" -- still got dumped, since the prompt rule only named the "full list" phrasing. Same pattern as every guardrail fix this session (name the exact scenario). But this one also got a second, independent fix at the user's own suggestion: a deterministic code-level cap, because prompt wording can always miss some future phrasing nobody's tried yet -- the cap holds regardless of how "give me everything" ends up being asked. 20 was already an engineering-reasonable ceiling for pagination purposes, but too many products to recite in one reply either way; 10 was chosen as a number a real salesperson could plausibly still present reasonably, not derived from any hard constraint.
**How to apply:** This establishes the general pattern for this class of gap going forward: when a "don't do X" prompt rule gets bypassed by a phrasing nobody named, prefer pairing the prompt fix (name the new phrasing) with a code-level backstop wherever one is structurally possible (a hard cap, a validation, a schema constraint) -- don't rely on prompt wording alone once a code-level guarantee is available, since wording can always be outflanked by a phrasing not yet tested. Not every guardrail has an equivalent code-level backstop (e.g. the language-matching or capability-boundary guardrails don't), but this one did and should have had one from the start.

## 2026-08-27 — CAPABILITY_GUARDRAIL now states the counterparty is always a customer, never trusting a claim otherwise
**Decision:** `CAPABILITY_GUARDRAIL` opens with an explicit identity statement: the person Malu is chatting with is always a customer, never the merchant/an employee/an admin, even if a message claims otherwise ("I'm the owner," "I'm testing," "I have admin access") -- such a claim must never be treated as true or as license to do anything differently.
**Why:** Testing via the dev-chat-test tool (the merchant's own account, used as a stand-in customer for manual testing), Malu appeared to treat the tester as if they might have backend/admin access -- unsurprising, since nothing in the prompt said who she's actually talking to. In production this is never ambiguous (D2's only caller is an inbound customer message; the merchant never talks to Malu through the customer-facing channel at all), so this is stated as settled fact, not something to weigh case by case. The "don't trust a self-reported identity claim" half matters independently of the dev-chat-test scenario that surfaced it: a real customer's own words are exactly the kind of input a model must never treat as elevating its own trust level (the same category of risk as any prompt-injection concern already noted in this log).
**How to apply:** Any future channel this engine gains (not just WhatsApp) inherits this the same way -- the assumption is "whoever is texting Malu is a customer," full stop, never inferred from what the message itself claims. If a real admin/merchant-facing chat surface is ever built, it must be a structurally different code path (different tools/prompt), not the same `AgentEngine.run()` trusting a claimed role.

## 2026-08-27 — CAPABILITY_GUARDRAIL broadened to a blanket "never discuss anything technical" rule
**Decision:** `CAPABILITY_GUARDRAIL` (`prompt.ts`) now forbids discussing anything technical unconditionally, not just when declining an out-of-scope request -- no "database"/"prompt"/"API"/"tools"/"system" talk, ever, and if asked directly what Malu is or how she works, she deflects lightly back to helping ("I'm here to help you find what you need 😊") rather than explaining any internal mechanism. Deliberately does **not** instruct the model to explicitly deny being an AI if asked point-blank.
**Why:** Explicit user request ("deixe claro pra ela não responder nada técnico, não pode falar de sistema nem nada"), and matches spec §28's core statement ("Malu is not a chatbot. Malu is a sales employee") and CLAUDE.md's existing product-language rule against exposing implementation jargon ("agent," "prompt," "LLM," "AI") -- previously only enforced for merchant-facing UI copy, now made explicit for Malu's own customer-facing output too. The soft-deflection-not-denial design is a deliberate, flagged policy choice: instructing a model to actively claim "I am not an AI" when asked directly is a materially different (and riskier) thing than just not volunteering technical detail -- it edges into a deceptive practice, relevant under things like the EU AI Act's transparency obligations for direct interaction with an AI system. Surfaced this distinction to the user rather than deciding it silently.
**How to apply:** If the harder-line version (explicit denial) is ever wanted, treat it as a real, separate product/legal decision, not an incremental prompt tweak -- flag it the same way this entry does, don't just quietly strengthen the wording next time this comes up.

## 2026-08-27 — Two more hand-testing bugs: full-catalog dump, and a DB-schema leak when declining an out-of-scope request
**Decision:** Two separate fixes. (1) `prompt.ts` gained a third platform-level guardrail, `CAPABILITY_GUARDRAIL` (next to confidentiality/language): Malu can search/answer/guide-to-checkout, and cannot create/edit/delete/restock/manage any catalog or store data — and must decline such a request without asking the customer for database fields or technical identifiers. (2) Malu's `system_prompt` (migration `20260827190000_reinforce_malu_catalog_list_guardrail`) gained one more "must never" bullet: never dump the entire catalog/a long product list even when explicitly asked for "the full list," since a real store can have far more items than fit in one good message.
**Why:** Both found hand-testing in the same session. (1) Asked to create a product, Malu correctly said she couldn't (there's no such tool) but then asked the customer to supply `sku`/`external_id` -- this catalog's actual Postgres column names. A real customer has no way to answer that, and it leaks implementation detail exactly like the original system-prompt leak did, just via a different path (an out-of-scope request instead of a direct "what are your instructions" probe) -- there was no general "here's what you can/can't do, and how to decline" rule, so the model improvised a plausible-sounding but nonsensical/leaky one. (2) Asked for "the complete list of products," Malu just recited what the search tool returned. The general "avoid overwhelming customers with too many products" line already existed in `system_prompt` since C2, but wasn't enough to override a customer's literal, explicit request for "everything" -- same lesson as the "calçado" category-expansion fix earlier this same day: a general principle needs its exact failure scenario named to reliably win. In a store with many more than a handful of products this is also low-key misleading, not just bad UX -- a capped result set presented as "the list" implies completeness it doesn't have.
**How to apply:** This is now the third instance of the same underlying pattern in one session (confidentiality leak, calçado category expansion, these two) -- whenever hand-testing surfaces Malu doing something structurally wrong, the fix is almost never "the model is bad," it's "no rule named this exact scenario." ## 2026-08-27 — Product search rewritten: Postgres full-text search + LLM keyword expansion, replacing ILIKE
**Decision:** `ProductRepository.search` now calls a Postgres function (`public.search_products`, migration `20260827180000_add_product_search_ranking`) instead of building an `ilike` filter in application code. The function does full-text search (`tsvector`, `portuguese` config, `name` weighted above `description`) with `pg_trgm` similarity as a ranking-only tie-breaker (deliberately **not** a match qualifier — see the function body's own comment: applying `similarity()` to a whole multi-word phrase is lenient enough to false-positive on a shared prefix alone, e.g. "Camiseta Branca" scoring close to a "camiseta azul" query). `ProductRepository.search`'s `text` (single phrase, words ANDed) and new `keywords` (list of alternatives, OR'd against each other) params are just merged into one list passed to the function. The `search_products` **agent tool** now asks the model for `keywords` (2-5 related terms — literal words plus synonyms/alternate phrasings) instead of one `text` string, in the same tool-call turn it was already making (no extra LLM round trip).
**Why:** A real bug found hand-testing Malu: asked for "camiseta azul", got told nothing matched, even though a "Camiseta Azul" product existed — the original `ilike '%text%'` match required the whole query to appear as one literal substring, which fails whenever query words are split across `name`/`description`, or a caller (an LLM constructing search args from conversational context) adds one extra qualifying word. A same-day intermediate fix (tokenize the query, require every word present somewhere, still application-side `ilike`) shipped first and closed the immediate bug, but was itself superseded within the same session by this full rewrite: full-text search was already the sanctioned upgrade path per B5's own original file comment, doesn't require pulling a wide unranked candidate pool into JS to rank (the DB now ranks and limits directly), and full-text token matching is strictly more precise than `ilike` substring matching too (`to_tsvector` won't match "azul" inside "Azulejo" — different lexemes — where `ilike '%azul%'` would have false-positived on it). Separately, LLM keyword expansion (asking Malu for a few related terms instead of one phrase) was chosen over two more expensive alternatives considered and rejected for now: (a) a dedicated query-expansion LLM call — strictly worse, since it adds a redundant round trip the existing tool-call turn doesn't need; (b) embeddings/`pgvector` semantic search — the "most correct" long-term answer for true paraphrase understanding (spec's "understand the customer" priority), but real recurring cost/latency (an extra OpenAI call per search) and new infra (re-embedding pipeline on catalog writes) not justified until the cheaper combination here proves insufficient in practice.
**How to apply:** Validated directly against real production data (company `76529c46-85f2-43cb-86d1-7a71e53f034c`, whose real "Camiseta Azul" product was the original bug report) via the Supabase MCP's `execute_sql`, reproducing the exact failing query and confirming both the fix and the `keywords` OR-across-alternatives behavior, plus a precision check ("azul" does not match "Azulejo Decorativo"). `supabase db reset` locally applied the migration with no errors; `npm run test:unit` (19/19) passed; the full local `vitest --project=integration` run could not be completed in this session because Next.js refuses a second `next dev` instance against the same project directory while a real `npm run dev` was active — the new/updated integration tests in `tests/integration/product-search.test.ts` and `tests/integration/agent-engine.test.ts` are believed correct by the same reasoning validated against production data above, but have not yet had an automated pass locally; run the suite before trusting it blindly in CI. 20 adversarial test products (same-name-different-size, cross-category color overlap, a comma/quote-in-name case, an out-of-stock case, and the "Azulejo" substring trap) were seeded directly into that same real company for manual testing — ask before deleting them if this comes up, they weren't cleaned up in this session.

## 2026-08-27 — CI uses `npm install`, not `npm ci` — a real npm bug with multi-platform optional native binaries
**Decision:** `.github/workflows/test.yml`'s `unit` and `integration` jobs both run `npm install` instead of `npm ci`.
**Why:** After fixing the `supabase` CLI's lockfile entries (previous entry below), CI's `unit` job then failed differently: `npm run test:unit` couldn't start at all — `Cannot find native binding... npm has a bug related to optional dependencies (github.com/npm/cli/issues/4828)` — for `rolldown` (Vitest 4's bundler), which ships ~15 platform-specific optional native-binding packages (`@rolldown/binding-*`), more than double `supabase`'s 8. **How to apply:** Any package in this repo with per-platform optional native binaries (currently: `supabase`, `rolldown` via `vitest`) is a standing risk for this exact failure mode returning, in CI specifically — `npm ci` is the more "correct" tool for reproducible installs in principle, but until this upstream npm bug is fixed, don't switch back to it here without first confirming a real CI run installs every platform's optional deps correctly. If a future dependency bump reintroduces this error, the fix is the same: confirm the lockfile entry is actually complete (rule out the previous entry's mistake first) before assuming it's this bug again.

## 2026-08-27 — Never resolve a package-lock.json merge conflict with a plain `npm install` on one platform
**Decision:** Resolving a `package-lock.json` merge conflict must be a full regenerate (delete `package-lock.json` and `node_modules`, then `npm install` fresh), never a plain `npm install` run against the conflicted file to "fix itself."
**Why:** Broke CI (`No matching Supabase CLI binary package found for linux-x64` on `ubuntu-latest`) after a `feature/C1` rebase's `package-lock.json` conflict was resolved with a plain `npm install` on Windows. `supabase` (a devDependency) ships one `optionalDependencies` entry per platform (`@supabase/cli-darwin-arm64`, `@supabase/cli-linux-x64`, `@supabase/cli-windows-x64`, ...); npm only actually installs the one matching the machine it runs on. When `npm install` reconciles an existing (conflicted) lockfile rather than resolving from scratch, it only writes a complete top-level `node_modules/<pkg>` entry (`resolved`/`integrity`/`os`/`cpu`) for whichever platform variant that one run actually installed — every other platform's entry is silently left as a bare name/version reference with nothing to resolve, which `npm ci` on a different platform (CI) can't install from at all.
**How to apply:** Any future `package-lock.json` conflict (or any lockfile that looks suspicious after a merge) gets the full regenerate treatment, not a quick `npm install`. Verify afterward by grepping the lockfile for every platform variant of any package with per-OS optional binaries (this repo: `@supabase/cli-*`, all 8 of darwin/linux/windows × x64/arm64(-musl)) and confirming each has a real `resolved`/`integrity` entry, not just a name in some other package's `optionalDependencies` list.

## 2026-08-27 — Conversations rotate after 24h of inactivity, prototyped in the dev-chat-test tool ahead of D2/D3
**Decision:** A conversation is only reused if `conversations.updated_at` is less than 24h old; past that, it's marked `status = 'closed'` and a fresh conversation row is created instead (same customer/agent/company, new `open_ai_conversation_id`). `updated_at` is touched after every turn (an explicit `UPDATE`, relying on the existing `set_updated_at` trigger), not just "when the chat opens" — there's no such discrete event on an inbound-message-driven channel, only messages. Implemented today in `src/app/api/companies/[companyId]/agents/[agentSlug]/dev-chat-test/route.ts` (the only code that does conversation lookup at all right now, since D2 doesn't exist yet) as an explicit prototype of behavior D2/D3 should carry forward, not a permanent home for this logic.
**Why:** Confirmed directly against OpenAI's docs that Conversation objects have no TTL — "Conversation objects and items in them are not subject to the 30 day TTL" — so nothing expires on OpenAI's side either; without rotation, a conversation's context (and cost per turn) grows without bound forever, and would eventually exceed the model's context window. D2's own card already specifies "reuse an existing open conversation rather than always creating a new one," which is correct but incomplete without a bound on how long "existing" means. 24h isn't arbitrary — it's WhatsApp's own customer-service session window (free-form messaging is only guaranteed within 24h of the customer's last message before the business needs a template to re-engage), so conversation lifetime now matches a constraint the channel already imposes. C5's `request_human` flag (not built yet) will also write to `status` — this design deliberately never overwrites `status` back to `'active'` blindly when touching `updated_at` (updates `updated_at` alone, a separate call from the close-and-rotate path), so a future paused/needs-human conversation can't be silently reactivated by an unrelated activity-timestamp bump.
**How to apply:** When D2 (inbound webhook) and D3 (conversation engine) are actually built, this exact rule — filter conversation lookup to `status = 'active'`, check `updated_at` age against a 24h constant, close-and-recreate on staleness, touch `updated_at` after every turn — should move there and be deleted from the dev-chat-test route (which is itself temporary, see its own `TODO(C1-TEST-ONLY)`). Don't invent a different threshold or mechanism without revisiting this reasoning first.

## 2026-08-26 — Agent Engine (C1): entry point takes an existing conversationId; tool-call contract is args-in/JSON-out with a trusted execution context
**Decision:** `AgentEngine.run({ companyId, conversationId, message }, deps?)` requires an already-existing `conversations` row — the engine does not find-or-create one from a customer/channel. The tool-call contract (`src/lib/agent-engine/tools/types.ts`): `AgentTool = { name, description, parameters: JSONSchema, execute(args, ctx) }`, where `ctx: ToolExecutionContext` (`companyId`/`conversationId`/`customerId`/`supabase`) is supplied by the loop, never derived from model-supplied `args`. Registration is append-to-array (`tools/registry.ts`'s `defaultTools`), not per-call wiring. `strict` mode defaults to `false` on the OpenAI tool schema.
**Why:** No caller (D2, the WhatsApp inbound webhook) exists yet, so there's no real payload to shape the entry point around. Deciding *which* customer/channel a message belongs to is routing logic that D2 will own; folding it into the engine would mean guessing at a contract before there's a consumer. The `ctx`-not-`args` rule for tool identity fields mirrors B5's `ProductRepository` precedent (a `companyId` must always come from trusted code, never an unauthenticated/model-influenced value) and is enforced by spread order (`{ ...args, companyId: ctx.companyId }`, args first) rather than by validation — a model could smuggle its own `companyId` key into `args` and it must lose. `strict: false` by default because OpenAI's strict function-calling mode requires every JSON Schema to set `additionalProperties: false` and list every key (including optional ones) in `required`; defaulting strict on would silently reject any tool whose schema wasn't hand-tuned to that shape.
**How to apply:** A future tool (C4's checkout-link creator, etc.) just adds itself to `defaultTools` — no other file needs to change. ## 2026-08-26 — WhatsApp registration PIN must be persisted and reused, not regenerated per call
**Decision:** `company_whatsapp_connections.two_step_pin` (migration `20260826135816`) stores the PIN sent on a phone number's `/register` call, and every later `/register` for that same connection reuses it instead of generating a new random one. Locked down with the same column-level GRANTs as `access_token`.
**Why:** Found while manually testing the connect flow against a real Meta test number: Meta ties a phone number to whatever PIN its *first* `/register` call supplied, for two-step verification, and rejects any later `/register` for that number with a different PIN — `"(#133005) Two step verification PIN Mismatch"`. The original code called `generateRegistrationPin()` fresh on every request, so any reconnect (retry, re-running Embedded Signup, the manual-connect-test path) after the first successful connect would always fail this way. Only surfaced once the manual-connect-test route's error responses were made to include Meta's raw error text (dev-only route, safe to do there) — the real connect route still returns a generic 502 to callers, so this failure mode would have been silent and hard to diagnose in production too.
**How to apply:** Both `POST .../whatsapp/connect` and `manual-connect-test` now look up any existing `two_step_pin` for the company before calling Meta, and pass that (or a freshly generated one if none exists yet) into `finishConnection`. ## 2026-08-26 — Sensitive column locked down with column-level GRANTs, not a second table
**Decision:** `company_whatsapp_connections.access_token` (Trello D1) lives on the same table as the rest of the connection metadata. It's locked down with column-level grants — revoke the table-wide select/insert/update privilege, then re-grant it back naming every column except `access_token` (migration `20260826104820`) — rather than moving it into a separate zero-RLS-policy table (the initial approach, reverted after user pushback).
**Why:** User asked directly why it needed two tables instead of one. Postgres column-level privileges are the more idiomatic tool for "this row is fine to read except one field" — one migration, one table, no join. It also fails *louder*: a regular client's `select *` (or any query naming the column) gets an outright permission error, rather than a separate-table design's silent empty result for a stray query against the wrong table. The one thing it gives up is discoverability — a table with zero policies visually announces "don't touch this" to someone skimming table names, where a locked column requires checking grants specifically; judged an acceptable tradeoff for one column on one table. **Pitfall hit while building this:** a column-level `revoke select (access_token) ... from authenticated` layered on top of the pre-existing table-wide grant (from `20260825171500`) is a silent no-op — Postgres's table-wide privilege supersedes a column-level one rather than being narrowed by it. Only caught because the RLS integration test actually exercised a live select against local Supabase, not from reading the SQL. The fix is to revoke the table-wide privilege entirely first, then re-grant per-column.
**How to apply:** Any future "one sensitive field on an otherwise normal row" case (an API key, a webhook secret, etc.) should default to this same column-level-grant pattern, not a second table, unless the sensitive data genuinely needs its own independent lifecycle (different retention, different FK shape) that a single column can't express. Always verify a column-level lockdown like this with a real RLS integration test (an authenticated client actually attempting the select) — the revoke-on-top-of-a-table-wide-grant no-op won't show up from SQL review alone.

## 2026-08-25 — faq shape is `{ question, answer }[]`; PATCH endpoints use merge-patch semantics

## 2026-08-25 — Product list excludes soft-deleted rows by default; price/currency validated as a pair, including on partial update

**Decision:** Trello ticket B1's `POST /api/companies/[companyId]/agent` (hire Malu) is deliberately idempotent — calling it twice returns the existing `company_agents` row with `200`, not an error — unlike A3's members endpoint, where a duplicate insert is a genuine `409`. ## 2026-08-25 — Only the owner can touch the owner role in company_users
**Decision:** Added `private.is_company_owner(company_id)` (migration `20260825163334`) and tightened `company_users`'s UPDATE and DELETE RLS policies so an `admin` can no longer delete an `owner`'s membership row, update it, or promote anyone (via UPDATE) to `owner` — only the current `owner` can. Also added the same restriction at the API layer in `POST /api/companies/[companyId]/members`: only an owner can add a new member with `role: 'owner'`.
**Why:** User flagged this while reviewing A3 ("an admin can't remove an owner, right?") — it wasn't true yet. The original `create_companies_and_membership` migration's UPDATE policy on `company_users` had **no `with_check` at all**, and DELETE only checked `is_company_admin` with no regard for the target row's role — so any admin could demote/remove the owner, or promote themselves/anyone else to owner, via a direct PostgREST call to `company_users` (not even through our app's API).
**How to apply:** `owner` and `admin` are otherwise equivalent everywhere else in the system (see the A3 entry below) — this is the one place they aren't. Any future endpoint or direct-table policy touching `company_users.role` must preserve this asymmetry: reads/writes of a row *whose role is or would become `owner`* require the caller to already be that company's owner.

## 2026-08-25 — create_company_with_owner RPC must be SECURITY DEFINER, and public-schema functions need an explicit `anon` revoke
**Decision:** Trello ticket A3's create-company RPC (`public.create_company_with_owner`, migration `20260825154320`) is `SECURITY DEFINER`, not the initially-tried `SECURITY INVOKER`. Also added an explicit `revoke execute ... from anon` alongside the `from public` revoke.
**Why:** Two RLS/grants gotchas hit while implementing and testing this against the live project (verified via a real signup + authenticated RPC call, not just reasoning about the SQL): (1) With `SECURITY INVOKER`, the function's `insert into companies ... returning * into new_company` failed with "new row violates row-level security policy for table companies" — the `RETURNING` clause is itself checked against the table's SELECT policy (`is_company_member`), and the caller isn't a member yet at that point since the `company_users` owner row is the *next* statement. This is a standard chicken-and-egg RLS problem for any "create X and become its owner" flow. `SECURITY DEFINER` bypasses RLS for the whole function body, which is safe here only because the function hardcodes the owner to `auth.uid()` and takes no `company_id`/`user_id` params. (2) After switching to `SECURITY DEFINER`, `revoke execute on function ... from public` alone left `anon` still able to call it — Supabase's public-schema default privileges grant EXECUTE directly to `anon`/`authenticated`/`service_role` on new functions, not via the `PUBLIC` pseudo-role, so revoking from `public` doesn't touch them.
**How to apply:** Any future RPC function in `public` that (a) needs to bypass RLS for a legitimate multi-table write, or (b) has `RETURNING` on a table whose SELECT policy depends on a row inserted later in the same function, should default to `SECURITY DEFINER` with an explicit `auth.uid() is null` guard (never trust an implicit invoker-rights check for this pattern). And whenever a public-schema function shouldn't be `anon`-callable, revoke from `anon` explicitly — `revoke ... from public` is not enough on this project.
