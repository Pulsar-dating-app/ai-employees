## 2026-08-26 — WhatsApp registration PIN must be persisted and reused, not regenerated per call
**Decision:** `company_whatsapp_connections.two_step_pin` (migration `20260826135816`) stores the PIN sent on a phone number's `/register` call, and every later `/register` for that same connection reuses it instead of generating a new random one. Locked down with the same column-level GRANTs as `access_token`.
**Why:** Found while manually testing the connect flow against a real Meta test number: Meta ties a phone number to whatever PIN its *first* `/register` call supplied, for two-step verification, and rejects any later `/register` for that number with a different PIN — `"(#133005) Two step verification PIN Mismatch"`. The original code called `generateRegistrationPin()` fresh on every request, so any reconnect (retry, re-running Embedded Signup, the manual-connect-test path) after the first successful connect would always fail this way. Only surfaced once the manual-connect-test route's error responses were made to include Meta's raw error text (dev-only route, safe to do there) — the real connect route still returns a generic 502 to callers, so this failure mode would have been silent and hard to diagnose in production too.
**How to apply:** Both `POST .../whatsapp/connect` and `manual-connect-test` now look up any existing `two_step_pin` for the company before calling Meta, and pass that (or a freshly generated one if none exists yet) into `finishConnection`. Any future code path that calls Meta's `/register` for a number must follow the same lookup-or-generate-then-persist pattern — never call it with an ad hoc random PIN.

## 2026-08-26 — WhatsApp token expiry is recorded, not auto-renewed
**Decision:** `company_whatsapp_connections.token_expires_at` (migration `20260826112152`) stores when the Meta access token goes stale (from `expires_in` on the code-exchange response — 60 days, for the "WhatsApp Embedded Signup Configuration With 60-Day Token Expiration" template used). No automatic refresh was built.
**Why:** User asked directly whether renewal could be added now. Renewal needs a scheduled job (call Meta's `fb_exchange_token` refresh before expiry, for every connected company) — this codebase has no scheduled/background-job infrastructure at all yet (no Supabase Edge Function cron, no Vercel Cron), so adding one is a real infra decision, not a small addition to this endpoint. It's also premature: nothing reads `access_token` yet (D4, the outbound adapter, doesn't exist), so there's no consumer to notice or care that a token expired.
**How to apply:** When D4 is built (or whenever something first reads this token to call Meta), that's the natural point to decide where a refresh job lives and build it — check `token_expires_at` before trusting `access_token` is still valid, and treat "needs refresh/reconnect" as a real state to design for then, not now. Don't let a stale token silently fail sends without surfacing it.

## 2026-08-26 — WhatsApp connection: Meta Cloud API direct, not a BSP
**Decision:** Trello D1 connects merchants to WhatsApp via **Meta's Cloud API directly**, using **Embedded Signup** (Facebook Login for Business + JS SDK), instead of a BSP (Twilio, 360dialog, etc.).
**Why:** User's explicit choice after weighing the tradeoff directly: (1) Cost — Meta direct is one fee layer (Meta's own conversation pricing); a BSP adds a second markup layer on top of Meta's, since the BSP is itself a reseller. (2) Merchant UX — Embedded Signup lets a merchant click "Connect," log into their own Meta Business account, and finish in one popup with the number auto-registered; BSPs have their own separate onboarding wizards, which are typically clunkier and add a visible waiting/approval step. (3) Accepted tradeoff — going live with real customers (not just Meta's dev test numbers) requires Meta Business Verification, an external, unpredictable-timeline step outside our control; BSP sandboxes are faster to prototype against but were rejected anyway given (1) and (2).
**How to apply:** D2 (inbound webhook), D4 (outbound adapter), and F4 (connection UI) all build against Meta's Graph API/webhook shapes, not a BSP's. F4's client-side JS SDK trigger needs its own Meta App ID + Embedded Signup Config ID (public-safe, `NEXT_PUBLIC_`-prefixed) — D1 only added the server-side `META_APP_ID`/`META_APP_SECRET`.

## 2026-08-26 — Sensitive column locked down with column-level GRANTs, not a second table
**Decision:** `company_whatsapp_connections.access_token` (Trello D1) lives on the same table as the rest of the connection metadata. It's locked down with column-level grants — revoke the table-wide select/insert/update privilege, then re-grant it back naming every column except `access_token` (migration `20260826104820`) — rather than moving it into a separate zero-RLS-policy table (the initial approach, reverted after user pushback).
**Why:** User asked directly why it needed two tables instead of one. Postgres column-level privileges are the more idiomatic tool for "this row is fine to read except one field" — one migration, one table, no join. It also fails *louder*: a regular client's `select *` (or any query naming the column) gets an outright permission error, rather than a separate-table design's silent empty result for a stray query against the wrong table. The one thing it gives up is discoverability — a table with zero policies visually announces "don't touch this" to someone skimming table names, where a locked column requires checking grants specifically; judged an acceptable tradeoff for one column on one table. **Pitfall hit while building this:** a column-level `revoke select (access_token) ... from authenticated` layered on top of the pre-existing table-wide grant (from `20260825171500`) is a silent no-op — Postgres's table-wide privilege supersedes a column-level one rather than being narrowed by it. Only caught because the RLS integration test actually exercised a live select against local Supabase, not from reading the SQL. The fix is to revoke the table-wide privilege entirely first, then re-grant per-column.
**How to apply:** Any future "one sensitive field on an otherwise normal row" case (an API key, a webhook secret, etc.) should default to this same column-level-grant pattern, not a second table, unless the sensitive data genuinely needs its own independent lifecycle (different retention, different FK shape) that a single column can't express. Always verify a column-level lockdown like this with a real RLS integration test (an authenticated client actually attempting the select) — the revoke-on-top-of-a-table-wide-grant no-op won't show up from SQL review alone.

## 2026-08-25 — Knowledge management UI mirrors B2's permission model instead of relying on its 403
**Decision:** F2's `/dashboard/teach` fetches the caller's own `company_users.role` server-side and computes `canEdit` (owner/admin, same rule as B2's `requireAdmin`), then disables every field and hides every Save button when `false`, plus shows a banner explaining why — rather than letting a plain member fill out a form and hit a 403 on save.
**Why:** B2's `GET` is member-readable but `PATCH` is admin-only — a UI that doesn't know this would let a plain member type a paragraph of policy text, click Save, and get a confusing permission error with no warning beforehand. Checking once server-side and gating the whole page is simpler and kinder than per-field error handling for an outcome that was always going to fail.
**How to apply:** Any future page backed by an endpoint with asymmetric read/write permissions (F3's product management is the next likely candidate) should fetch the caller's role once, compute a `canEdit`-style flag, and gate the UI with it — don't rely on the API's error response as the first time a user learns they can't do something.

## 2026-08-25 — next-intl for EN/PT, cookie-based with no locale-prefixed routing

**How to apply:** Add new UI strings to both `messages/en.json` and `messages/pt.json` under the right namespace — never inline a hardcoded string in a page/component again. Never translate `agents.slug`-derived display names (they're data, not UI copy) — only the copy around them.

## 2026-08-25 — faq shape is `{ question, answer }[]`; PATCH endpoints use merge-patch semantics
**Decision:** Trello B2's `PATCH /api/companies/[companyId]` establishes two conventions with no prior precedent in this codebase: (1) `companies.faq` (jsonb) is an array of `{ question: string, answer: string }` objects, capped at 50 entries (300/2000 char limits on question/answer), saved as a whole-array replace, not per-entry patches; (2) the endpoint uses merge-patch semantics — a field key present in the request body with value `null` clears that column, a key omitted entirely leaves the existing value untouched.
**Why:** `faq` had no shape decided anywhere before this — the ticket only suggested "likely an array of {question, answer}," so this is the first time it's been made concrete and worth recording so it doesn't drift. Merge-patch (vs. e.g. always overwriting every field, or treating `null` and omitted the same) was chosen because it's the only shape that lets a future UI (F2) save one changed field without having to first fetch and resend every other field, while still giving an explicit way to clear a field on purpose.
**How to apply:** Any future partial-update endpoint (B3's product update is the next one likely to need this) should follow the same merge-patch rule — check `field in body`, not just truthiness, to distinguish "omitted" from "explicitly null." Any future jsonb array field modeled on merchant-supplied structured data (not just `faq`) should default to whole-array-replace-on-save for MVP simplicity unless there's a concrete reason a UI needs entry-level granularity.

## 2026-08-25 — Product list excludes soft-deleted rows by default; price/currency validated as a pair, including on partial update
**Decision:** Trello ticket B3's `GET /api/companies/[companyId]/products` excludes `is_active = false` rows unless the caller passes `?includeInactive=true`. `DELETE` on a product does `UPDATE is_active = false`, never a real `DELETE`. Both `POST` (create) and `PATCH` (update) reject a `price` present without a `currency`; `PATCH` computes this against the row's state *after* the requested fields are merged in, not just the fields present in that one request.
**Why:** The card explicitly asks for soft-delete "to preserve historical event data" (`events.product_id` can reference a product) — a hard delete would either cascade-null those rows or fail the FK. Hiding inactive products from the default list keeps the common "list my catalog" call from needing every caller to filter deleted rows out client-side, while `includeInactive=true` still allows a UI that wants to show/restore them. Validating against the merged state (not just the request body) closes an easy hole: `PATCH { currency: null }` on a product that already has a `price` would otherwise silently produce a priced-but-currency-less row.
**How to apply:** Any future soft-deletable resource should default list endpoints to excluding inactive/deleted rows with an explicit opt-in query param, rather than making callers filter client-side. Any future paired-field validation (values that only make sense together) on a `PATCH` endpoint must validate the effective post-merge state, not just the fields present in that request.

## 2026-08-25 — Every public table needs explicit grants; hosted Supabase's default bootstrap isn't in any migration
**Decision:** Added `grant select, insert, update, delete on all tables in schema public to anon, authenticated, service_role` plus a matching `alter default privileges` (migration `20260825171500`), applied to the local dev database. **Not yet applied to the remote `ai-employees` project** — the auto-mode safety classifier blocked that specific `apply_migration` call as a broad permission change to a live project, and it needs explicit user sign-off before retrying (the remote project already has these grants from its own hosted-platform bootstrap, so applying is a no-op there, but the classifier can't know that).
**Why:** Building the local integration test environment surfaced that every single table in this schema (not just `companies`) only had `REFERENCES`/`TRIGGER`/`TRUNCATE` for `anon`/`authenticated`/`service_role` on a fresh `supabase db reset` — every `SELECT`/`INSERT`/`UPDATE`/`DELETE` failed with `permission denied for table X`, independent of and before RLS is even evaluated. **How to apply:** Before trusting this repo's migrations to stand up a working database from scratch anywhere other than the original hosted project (disaster recovery, a new environment, CI) — confirm this migration has actually been applied there. Any brand-new table should keep working automatically going forward because of the `alter default privileges` clause, but that only covers tables created *after* this migration ran.

## 2026-08-25 — Malu's agent row is a migration, not a seed.sql fixture; hire endpoint is idempotent by design
**Decision:** Trello ticket B1's `POST /api/companies/[companyId]/agent` (hire Malu) is deliberately idempotent — calling it twice returns the existing `company_agents` row with `200`, not an error — unlike A3's members endpoint, where a duplicate insert is a genuine `409`. Malu's row in `agents` (slug `malu`, `is_active`) was added via migration `20260825181902_seed_malu_agent`, not `supabase/seed.sql`.

Separately, `seed.sql` is explicitly local-dev-only (runs on `supabase db reset`, never touches the remote project — see the Supabase database changes convention), but Malu must exist on the live project for hiring to work there at all, so her row has to be a migration.
**How to apply:** Any future "activate/attach a platform-managed thing to a company" endpoint (not just agents) should default to this same idempotent-on-conflict shape rather than erroring on a repeat call, unless there's a specific reason a repeat really should be rejected (like A3's add-member, where a duplicate membership row is actually meaningless/wrong, not just redundant). Any other required-to-exist platform catalog row (future agents, etc.) belongs in a migration too, not `seed.sql`.

## 2026-08-25 — Only the owner can touch the owner role in company_users
**Decision:** Added `private.is_company_owner(company_id)` (migration `20260825163334`) and tightened `company_users`'s UPDATE and DELETE RLS policies so an `admin` can no longer delete an `owner`'s membership row, update it, or promote anyone (via UPDATE) to `owner` — only the current `owner` can. Also added the same restriction at the API layer in `POST /api/companies/[companyId]/members`: only an owner can add a new member with `role: 'owner'`.
**Why:** User flagged this while reviewing A3 ("an admin can't remove an owner, right?") — it wasn't true yet. The original `create_companies_and_membership` migration's UPDATE policy on `company_users` had **no `with_check` at all**, and DELETE only checked `is_company_admin` with no regard for the target row's role — so any admin could demote/remove the owner, or promote themselves/anyone else to owner, via a direct PostgREST call to `company_users` (not even through our app's API).
**How to apply:** `owner` and `admin` are otherwise equivalent everywhere else in the system (see the A3 entry below) — this is the one place they aren't. Any future endpoint or direct-table policy touching `company_users.role` must preserve this asymmetry: reads/writes of a row *whose role is or would become `owner`* require the caller to already be that company's owner.

## 2026-08-25 — create_company_with_owner RPC must be SECURITY DEFINER, and public-schema functions need an explicit `anon` revoke
**Decision:** Trello ticket A3's create-company RPC (`public.create_company_with_owner`, migration `20260825154320`) is `SECURITY DEFINER`, not the initially-tried `SECURITY INVOKER`. Also added an explicit `revoke execute ... from anon` alongside the `from public` revoke.
**Why:** Two RLS/grants gotchas hit while implementing and testing this against the live project (verified via a real signup + authenticated RPC call, not just reasoning about the SQL): (1) With `SECURITY INVOKER`, the function's `insert into companies ... returning * into new_company` failed with "new row violates row-level security policy for table companies" — the `RETURNING` clause is itself checked against the table's SELECT policy (`is_company_member`), and the caller isn't a member yet at that point since the `company_users` owner row is the *next* statement. This is a standard chicken-and-egg RLS problem for any "create X and become its owner" flow. `SECURITY DEFINER` bypasses RLS for the whole function body, which is safe here only because the function hardcodes the owner to `auth.uid()` and takes no `company_id`/`user_id` params. (2) After switching to `SECURITY DEFINER`, `revoke execute on function ... from public` alone left `anon` still able to call it — Supabase's public-schema default privileges grant EXECUTE directly to `anon`/`authenticated`/`service_role` on new functions, not via the `PUBLIC` pseudo-role, so revoking from `public` doesn't touch them.
**How to apply:** Any future RPC function in `public` that (a) needs to bypass RLS for a legitimate multi-table write, or (b) has `RETURNING` on a table whose SELECT policy depends on a row inserted later in the same function, should default to `SECURITY DEFINER` with an explicit `auth.uid() is null` guard (never trust an implicit invoker-rights check for this pattern). And whenever a public-schema function shouldn't be `anon`-callable, revoke from `anon` explicitly — `revoke ... from public` is not enough on this project.

## 2026-08-25 — A3 company creation/membership shipped as Next.js API routes, not server actions
**Decision:** Implemented Trello ticket A3 (create-company, list-companies-for-current-user, add/invite-member) as Next.js Route Handlers under `src/app/api/companies/` (`route.ts` for GET/POST, `[companyId]/members/route.ts` for POST), not as Server Actions like A2's `login`/`signUp`/`logout`.
**Why:** The card frames this as "the API surface every other epic builds against" — unlike A2's actions, which are only ever invoked from that same app's own `/login`/`/sign-up` forms, A3's endpoints need to be callable as a real HTTP API by any future epic/service, which Server Actions (form-bound, Next-internal call convention) don't support cleanly.
**How to apply:** Route Handlers are the default for API-surface tickets meant to be consumed outside the calling page/component; Server Actions stay reserved for form submissions within this same app (as in A2).

## 2026-08-25 — Next.js full-stack app, single codebase for dashboard + API

## 2026-08-25 — Supabase hosted email service rate-limits signup confirmation emails
**Decision:** No code change — documenting a constraint discovered while testing Trello ticket A2. The `ai-employees` Supabase project's built-in email service hit "email rate limit exceeded" after a couple of real signup attempts during manual QA (via the browser, using disposable `@mailinator.com` addresses — `@example.com` and the reserved `@sidde.test` TLD were both rejected outright as invalid by Supabase's email validation, separately from the rate limit).
**Why:** Supabase's built-in email sending (no custom SMTP configured) is intentionally low-volume — expected to force a real SMTP provider before production traffic. This blocked verifying the full signup -> email-confirm -> login round trip end-to-end in this session; login itself, error handling, session middleware, and route protection were all verified independently and work correctly.
**How to apply:** Before real users sign up in production (or before doing heavier signup QA), configure a custom SMTP provider in the Supabase project's Auth settings. Don't attempt to bypass this by inserting rows directly into `auth.users`/`auth.identities` — that was tried during QA and is correctly blocked as unsafe; treat Supabase Auth as the only writer to those tables.

## 2026-08-25 — Single shared `events` table for tracking/analytics
**Decision:** Added one `events` table (migration `20260825140705_create_events_table`) covering all three spec §14–15 tracked behaviors — `buying_intent`, `product_recommendation`, `checkout_click` — distinguished by an `event_type` enum column, rather than three separate tables. `company_id`/`conversation_id`/`customer_id` are required; `agent_id`/`product_id` are optional (`on delete set null`). Added a `tracking_id` column (partial unique index, nullable) as the `sidde.link/c/{tracking-id}` lookup key for checkout-click events, plus a catch-all `metadata` jsonb for type-specific extras like `destination_url`. No `updated_at` column, no update trigger, and only select/insert RLS policies (company-membership scoped) — rows are append-only.
**Why:** This was Trello ticket A1 (Sidde board), a foundational, no-dependency ticket meant to unblock the buying-intent (C6), checkout-link (C4), checkout-click redirect (E1), and analytics aggregation (E2) tickets. A shared table keeps E2's per-company rollup a single group-by-type query instead of three separate ones, and matches the project's existing "convert small stable value sets to a real enum" convention (see the 2026-08-23 enum entry below) for `type`.
**How to apply:** C4 (create_checkout_link tool) should insert a `checkout_click`-typed row with `tracking_id` set and `destination_url` in `metadata` when generating a link. E1 (redirect service) looks the row up by `tracking_id`. C6 (buying-intent detection) and the product-recommendation flow insert their own typed rows the same way, no `tracking_id` needed. Never add an `updated_at`/update policy to this table — if a future need requires mutating events, treat that as a new decision, not a default extension.

## 2026-08-23 — No messages table
**Decision:** Dropped `messages` from MVP scope entirely — not deferred, not planned. Conversation message history will not be persisted in our own database.
**Why:** `conversations.open_ai_conversation_id` already exists to let us fetch full message history from OpenAI's Conversations API on demand, so a local `messages` table would just duplicate what OpenAI already stores.
**How to apply:** Don't add a `messages` table or reintroduce message persistence without checking with the user first — this was an explicit scope cut, not an oversight. Anything needing conversation history (analytics, transcripts, agent context) should read it via the OpenAI Conversations API using `open_ai_conversation_id`.

## 2026-08-23 — Fixed-value columns converted to Postgres enums
**Decision:** Converted three varchar+CHECK columns to real Postgres enum types: `company_users.role` → `company_role` (`owner`/`admin`/`member`, unchanged values), `company_agents.status` → `company_agent_status` (simplified from `hired`/`active`/`paused` down to just `active`/`paused` — dropped the "hired" state), and `customers.channel` / `conversations.channel` → shared `conversation_channel` enum (`whatsapp` only for now).
**Why:** User request, to get type-safety on fixed-value columns instead of relying on CHECK constraints. `company_agents.status` was intentionally simplified to 2 values rather than converted 1:1 — user's call, not carried through to `conversations.status` (still `active`/`closed`/`paused` as varchar+CHECK, deliberately left unconverted).
**How to apply:** When an app needs to hire an agent, `company_agents.status` now only has `active`/`paused` — there's no intermediate "hired but not yet active" state, so hiring flow must decide this at insert time. New channels (beyond `whatsapp`) require an `ALTER TYPE conversation_channel ADD VALUE '...'` migration, not a data-only change — this is a tradeoff since the spec lists future channels (website, Instagram, TikTok) as roadmap items.

## 2026-08-23 — Internal RLS helper functions live in a `private` schema
**Decision:** `is_company_member`, `is_company_admin`, and `handle_new_user` were created in `public`, then moved to a new `private` schema not listed in `supabase/config.toml`'s `[api].schemas`.
**Why:** Supabase's security advisor flags `security definer` functions reachable via PostgREST RPC (`/rest/v1/rpc/...`) as publicly callable. These functions only exist to be called from inside RLS policies/triggers, not directly by clients. Putting them in an API-unexposed schema removes the RPC surface while leaving them fully usable from RLS (which executes in-database, unaffected by PostgREST schema exposure).
