## 2026-09-02 — P7: usage metering + one shared reply gate; the reply-quota hard stop ships off by default
**Decision:** The per-channel billing check is now one function, `evaluateReplyGate` (`src/lib/billing/enforcement.ts`), that folds P4's "lapsed subscription" rule together with P7's monthly reply-quota soft cap — web chat and the Instagram webhook both call it where they used to call `isBillingLapsed`. It returns `{ allow: false, reason: "lapsed" | "grace_exceeded" }` or `{ allow: true, overPlan: boolean }`. Metering is `recordAiReply(companyId)` — a thin best-effort wrapper over P2's `record_ai_reply` RPC — called once after a real AI reply is persisted, on either channel (+1 per replying `AgentEngine.run()`, no weighting). The band math is a pure `classifyUsage` in `src/lib/billing/limits.ts`; the two knobs (`BILLING_GRACE_MULTIPLIER` default `1.2`, `BILLING_HARD_STOP_ENABLED` default **off**) are env-backed, not hard-coded. Past the grace band with the hard stop *armed* → the AI is skipped and a hard-coded PT canned line (`QUOTA_EXCEEDED_CUSTOMER_TEXT`) goes out instead; with it *off* (the shipped state) the bot keeps answering and only P5's banner escalates.
**Why:** One function instead of two gates because "is this company's subscription lapsed?" and "is it past its reply quota?" are the same decision made at the same point, and letting them live in separate call sites is how they drift. The hard stop ships off because the grace percentage — and the plan reply limits themselves (`plans.ts` placeholders) — aren't decided yet, and the P-epic rule is "never stop from nowhere": until there's a real number to enforce, going quiet on a paying customer is worse than briefly over-serving one. Env knobs (not constants) so that decision is a deploy toggle, not a PR. `recordAiReply` is best-effort (logs, never throws) for the same reason the Instagram adapter is: the customer already has the reply, and losing a count must not turn into a failed response. The gate moved *after* the inbound-message persist on Instagram (it was before session resolution) so the `grace_exceeded` path can send a canned reply without re-sending it on a webhook redelivery — the `mid` idempotency row already guards that point.
**How to apply:** Any new inbound channel calls `evaluateReplyGate` before `AgentEngine.run()` and `recordAiReply` after persisting the reply — never write `company_message_usage` another way, and never re-add a separate lapsed check. `isBillingLapsed` stays in `activation.ts` only as the predicate the P4 webhook tests assert against. Flip `BILLING_HARD_STOP_ENABLED=true` once the grace policy is signed off; tune `BILLING_GRACE_MULTIPLIER` the same way. The "+1 on a genuine reply over HTTP" path has no integration test (no OpenAI in the suite) — `recordAiReply` is covered in-process in `billing-usage.test.ts`; if OpenAI mocking is ever added, that gap closes for free. Per-bot weighting, if ever wanted, is an `amount` arg on the RPC + a `{ slug: number }` map in `limits.ts` — still no migration.

## 2026-09-02 — Scheduling replies: default company timezone, pre-formatted slot labels, and a no-Markdown guardrail
**Decision:** Three fixes from watching Ana handle the first real Instagram booking:
1. **`companies.timezone` now defaults to `America/Sao_Paulo`** (migration `20260902180000`: column default + backfill of all existing NULLs + `create_company_with_owner` wraps the arg in `coalesce(..., 'America/Sao_Paulo')` so an explicit NULL from onboarding still lands on the default). It also gets a real field in Settings → Business info (a curated 7-zone list: the four distinct Brazilian offsets + New York + Lisbon + UTC), validated as a real IANA name in the B2 PATCH route.
2. **The scheduling tools return a ready-to-speak `label`/`startsAtLabel`/`endsAtLabel`** on every slot and appointment result (`formatWallClock` in `src/lib/appointments/time-format.ts` — `Intl.DateTimeFormat` `en-US`, 24h, in the business timezone → `"Wed, Sep 3, 14:40"`). The raw ISO instants stay for `book_appointment`'s slot arg; the tool descriptions now say to speak the label and never recompute from the ISO.
3. **`prompt.ts` gained `FORMATTING_GUARDRAIL`** — plain text only, no Markdown (`*bold*`, `-`/`1.` lists, `#`, backticks). Platform-level, both agents, every channel.
**Why:** `companies.timezone` was NULL for all 8 production companies — there had never been a UI for it, and a pre-scheduling decision (`business-info-section.tsx`) deliberately left it out as "not something a merchant needs to set." Once epic J made it load-bearing, the NULL → `"UTC"` fallback meant Ana told customers their options were "horário UTC," and — asked to convert — she offered raw UTC clock times as if local. LLMs reliably translate `"Wed"/"Sep"` and 24h↔12h but get timezone arithmetic wrong, so the conversion has to happen in code before the model sees it. Separately, Ana's replies were full of `*asterisks*` and `- ` bullets that Instagram and web chat render as literal punctuation ("parece um bot") — nothing had ever told the model these are chat messages, not Markdown.
**How to apply:** Any new value an agent will speak that represents an instant goes through `formatWallClock` (or an equivalent server-side format) with the company timezone — never hand the model a bare ISO string and a timezone name and expect a correct spoken time. `America/Sao_Paulo` as the default is a Brazil-first product call (BRL, pt-BR, the zone has no DST since 2019), overridable per company in Settings; a future non-BR market would want the default derived from country at onboarding instead. The Markdown guardrail is prompt-only — there is no output sanitizer; if a model ignores it, that is the lever to reinforce.

## 2026-09-02 — Instagram connection id: store the professional-account id from `GET /me?fields=user_id`, not the OAuth `user_id`
**Decision:** `connectInstagramAccount` now derives `company_instagram_connections.instagram_user_id` from `GET https://graph.instagram.com/v25.0/me?fields=user_id,username` (the long-lived token is the only input), not from the `user_id` the code-for-token exchange returns. `exchangeCodeForShortLivedToken` no longer reads `user_id` at all; `fetchUsername(token, id)` became `fetchAccountProfile(token)` returning `{ instagramUserId, username }`. The one existing production row was hand-patched (`27743120758720144` → `17841478208149979`).
**Why:** Found in production right after the signature fix, wiring the first real Instagram DM for App Review. The webhook returned `200` but no message ever persisted and Ana never replied. A temporary `[ig-route]` diagnostic showed the route bailing at `if (!connection) continue`: the webhook's `entry[].id` / `recipient.id` was `17841478208149979`, but the stored `instagram_user_id` was `27743120758720144`. **Instagram API with Instagram Login issues two different ids for one account** — the OAuth token response's `user_id` (and `GET /me?fields=id`) is *app-scoped*; the id that messaging webhooks arrive under and that the Send API addresses in its path (`POST /{ig-id}/messages`) is the *Instagram professional-account id*, which only `GET /me?fields=user_id` returns. They never matched, so every real inbound DM missed its connection lookup. Same class of bug as the signature one (app-scoped vs product-scoped credential/identifier), same day.
**How to apply:** Anywhere you need "the id that identifies this Instagram business on inbound webhooks or as a Send API target," it is the `user_id` field from `/me`, never the OAuth exchange's `user_id`. The human-takeover send path (`conversations/[conversationId]/messages/route.ts`) and N5's `sendInstagramMessage` both take `connection.instagram_user_id`, so both were equally broken before this and are fixed by the stored value being correct — no change at those call sites. N6 token refresh never used the id. Integration mock: `instagram-api-mock.ts` serves `GET /v25.0/me` returning `user_id: "igsid_{code}"`, deliberately distinct from the OAuth branch's `user_id: "igid_{code}"`, so a test proves which one the connect flow persists; `instagram-webhook.test.ts` has a negative case asserting a webhook addressed to the `igid_` value finds no connection.

## 2026-09-02 — P3 follow-up: `createCheckoutSession` gets NO idempotency key
**Decision:** Removed the `idempotencyKey: billing-checkout:<companyId>:<planKey>` from `stripe.checkout.sessions.create` in `src/lib/stripe/billing.ts`. The customer-create call keeps its key.
**Why:** Found in local end-to-end testing. Stripe caches an idempotent response for 24h and a Checkout Session also expires 24h after creation, so a stable key made a second "start checkout" click **replay the earlier Session** — one the merchant had already completed (or let expire) — instead of minting a fresh one. The merchant lands on a dead Stripe Checkout page. A Session is single-use and free; an un-deduped double-submit just creates a second Session that expires unused, which is harmless. (The real double-charge risk was always on `subscriptions.update`, which the P3→Portal refactor already removed from our code.)
**How to apply:** Don't put an idempotency key on `checkout.sessions.create` / `billingPortal.sessions.create` — both mint short-lived single-use redirects where "make a fresh one" is always the right answer. Keep idempotency keys for things you genuinely never want duplicated (Customer creation, and any future one-off charge).

## 2026-09-02 — Instagram webhooks are signed with INSTAGRAM_APP_SECRET, not META_APP_SECRET (N4 got it wrong)
**Decision:** `verifyInstagramSignature` now computes the `X-Hub-Signature-256` HMAC with `process.env.INSTAGRAM_APP_SECRET` (the Business Login credential), not `process.env.META_APP_SECRET`. The N4 code and every comment/doc/`.env.example` note that said "Meta signs every webhook with the top-level app secret regardless of product" were wrong for **Instagram API with Instagram Login** — that product is issued its own App ID + Secret and signs its webhooks with that Instagram App Secret.
**Why:** Found in production while wiring up the first real Instagram connection for Meta App Review. Every real webhook delivery (`User-Agent: facebookexternalua`) returned `403` — the route rejected it at the signature check, 9 ms in. A temporary diagnostic in `verifyInstagramSignature` that logged only *shapes* (no secret values) computed the HMAC over the raw body with **both** secrets and compared each to the header: `matchesMeta: false`, `matchesInstagram: true`, every time. So Meta was signing with the Instagram app secret. The assumption held for the classic Graph API / Messenger / WhatsApp (which is why `meta-graph-api.ts`'s dormant WhatsApp path still correctly uses `META_APP_SECRET`), but Instagram Business Login is a separate product with separate credentials end to end — OAuth `client_id`/`client_secret`, and now the webhook signature too.
**How to apply:** Any future "verify a Meta webhook signature" code must first ask *which product's credentials issued this integration*. Instagram Business Login → `INSTAGRAM_APP_SECRET`. Classic Graph API products (WhatsApp Cloud API, Messenger, Facebook Login) → `META_APP_SECRET`. The GET verify-token check (`INSTAGRAM_WEBHOOK_VERIFY_TOKEN`) was already correct and is unaffected. The integration test's `TEST_APP_SECRET` was flipped to `"test-instagram-app-secret"` to match `global-setup.ts`'s `INSTAGRAM_APP_SECRET`; nothing else in the webhook route changed. If a diagnostic-log-in-prod is ever needed again, the pattern that worked here: log booleans/lengths/first-12-hex-chars only, promote the debug branch's preview straight to production (no merge to `main`), read one delivery, roll back by promoting a clean deployment.

## 2026-09-02 — P4: Stripe webhook — one sync path, event dedup via `processed_at`, no dunning grace (past_due blocks via a reply gate, not by pausing agents)
**Decision:** `POST /api/webhooks/stripe`: verify signature (bad → 400), then `stripe_webhook_events` insert-before-process with a new `processed_at timestamptz` column (migration `20260902170000`) — inserted-and-unstamped means a delivery is mid-flight (skip, 200), stamped means done (skip, 200), our insert means process→stamp→200, a thrown handler means 500 with `processed_at` left NULL so Stripe's retry re-processes. Every handler funnels through `syncBillingFromSubscription(sub)`: `plan_key` from `sub.items.data[0].price.lookup_key` → `getPlanByLookupKey` (unknown key → log + keep existing `plan_key`), period from the **subscription item** (not the root, in `2026-08-26.dahlia`), write via `.update()` with an `insert` fallback (a blind upsert NOT-NULL-violates `plan_key` when the key is unknown), and a second-granularity `period_start` change opens the next `company_message_usage` row. `checkout.session.completed` adds a one-active-subscription guard (`subscriptions.cancel` a different still-live sub, best-effort). **Dunning: no grace.** P4 just records `past_due`/`unpaid`/`canceled`; the block is `isBillingLapsed(companyId)` (= has a `company_billing` row not in `{active, trialing}`) checked before `AgentEngine.run()` in the web chat route and the Instagram webhook, beside the existing K6 gate. A company with **no** billing row is not "lapsed" — that cut-over is P6.
**Why:** The user reversed the earlier "não parar do nada" specifically for *payment* failure ("não podemos permitir dias de uso sem pagar") — the reply-*quantity* soft-cap is untouched. Blocking via a **reply gate that reads `company_billing.subscription_status`** rather than pausing `company_agents` means recovery is automatic (`invoice.paid` → status `active` → gate passes) with zero un-pause bookkeeping and no collision with the merchant's own K6 toggle; it also reuses the exact "skip before the engine" shape both channels already have for `paused`/K6. `plan_key` from the price's `lookup_key` (not subscription metadata) because the Customer Portal changes the price and never our metadata — the lookup key is the only always-current signal, which is why P1 put lookup keys on the Prices. `.update()`-not-upsert because Postgres validates the candidate row's NOT NULL columns on `INSERT … ON CONFLICT` even when it will UPDATE, so omitting `plan_key` (the correct thing when the key is unknown) blew up an upsert. `processed_at` over a bare "seen it" row because insert-and-forget silently drops an event whose handler threw after the insert. `invoice.paid` is kept even though `customer.subscription.updated` covers the same transitions — cheap belt-and-suspenders on the recovery path.
**How to apply:** Any new billing-relevant Stripe event gets a `case` in `dispatchStripeEvent` and, if it's subscription-shaped, routes through `syncBillingFromSubscription` — don't write `company_billing` from a handler directly. The reply gate is `isBillingLapsed`, not `isBillingActive` (which stays strict `{active, trialing}` for P6's activation gate): the gate must *not* fire for a company that never subscribed. Manual config: `stripe listen --forward-to …/api/webhooks/stripe` for the local `whsec_…`; a deployed env registers the endpoint in the Dashboard with `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`. Stripe's failed-payment retry schedule (Dashboard) only controls how long until `unpaid`/`canceled` — we block on the first `past_due` regardless.

## 2026-09-02 — R1/R3/R4: email epic in one PR; sends are best-effort & never block a booking; reminder cron reuses N6's pg_cron pattern; failed sends retry, no-email stamps
**Decision:** R1 (Resend transport), R3 (confirmation + decline emails) and R4 (reminder cron) shipped as one PR. `sendEmail` never throws (logs + `{ ok: false }`), and every appointment-email call (`notifyAppointmentConfirmed`/`notifyAppointmentDeclined`/`sendReminderForRow`) is `void`/best-effort — a mail failure or a customer with no email is a silent no-op, never a failed booking or a 500. **R3 fires from two places**: `AppointmentRepository.book` emails on a `confirmed` insert (not `requested`); the H3 PATCH route emails on the merchant acting on a *pending* request (`requested→confirmed` = confirmation, `requested→cancelled` = decline note) — not on cancelling an already-confirmed booking. **R4** (`/api/cron/appointment-reminders`, hourly) selects `confirmed` + `reminder_sent_at IS NULL` + `starts_at ∈ (now, now+25h]`, sends, then stamps `reminder_sent_at` — except a `failed` send is left un-stamped for the next hour's retry; a `skipped` (no email) is stamped so it isn't retried forever. Same pg_cron+pg_net+Vault trigger pattern as N6, with a new shared `src/lib/cron/auth.ts` bearer check (N6's route refactored onto it). New Vault secret `cron_secret` (generic, = `CRON_SECRET`) rather than reusing `instagram_token_refresh_cron_secret`.
**Why:** One PR because R1 alone is inert and R3/R4 are its only two consumers — splitting would be three reviews of one feature. Best-effort everywhere follows the Instagram-adapter precedent: a booking succeeding is the product's job, an email is a courtesy on top; coupling them would let a Resend outage break scheduling. R3 split across `book()` and the PATCH route because those are genuinely two moments — creation-time auto-confirm vs. merchant approval — and the PATCH route already had the `requested→X` transition in hand. The 25h window (not a tight 23–24h band) plus `reminder_sent_at` idempotency means a same-day booking still gets a reminder and a missed cron hour self-heals, at the cost of a reminder possibly landing a little over 24h out — fine. Failed-send-retries vs no-email-stamps: a transient Resend failure shouldn't lose the reminder, but a booking that will never have an email shouldn't be reconsidered every hour for a day. Resend returns 200 on accept, so a non-200 is a genuine reject, safe to retry. `cron_secret` is a fresh generic name so future `/api/cron/*` routes share one secret and the N6 job's already-scheduled command doesn't need touching.
**How to apply:** Turn R4 on in production exactly like N6 — set the `cron_secret` Vault secret (`app_base_url` is already there from N6), then `select private.schedule_appointment_reminders();`. A third `/api/cron/*` route reuses `cronAuthError` and the same two Vault secrets; give it its own `private.schedule_*()` + job name. Any new appointment email = a `render*Email` in `templates.ts` + a `notify*`/`send*` in `email/appointments.ts`, called best-effort from wherever the state change happens. If email deliverability ever needs to be *observable* (did the confirmation actually arrive?), that's a `sent_emails` table + webhook from Resend — not built; today a failed send is only in the logs.

## 2026-09-02 — P3: plan checkout is one admin route; new sub → Checkout, existing sub → Customer Portal (we never call subscriptions.update)
**Decision:** `POST /api/companies/[companyId]/billing/checkout`, admin-gated. `enterprise` → 400 `enterprise_contact_only` (no self-serve; the CTA is P5). **No live subscription** → create/reuse Stripe Customer, **upsert a `company_billing` stub row** (`stripe_customer_id` + `plan_key` + `subscription_status: 'incomplete'`, upsert on `company_id`), create a `subscription`-mode Checkout Session, return `{ mode: 'checkout', url }`; `planKey` (`starter`|`pro`) is required only on this path. **Live subscription** (`stripe_subscription_id` + status active/trialing/past_due) → a **Stripe Billing Portal session** (`flow_data.type = "subscription_update"` deep-link), return `{ mode: 'portal', url }`; the route does **not** call `subscriptions.update` and does **not** touch `company_billing`; `planKey` is ignored. Session **never sets `currency`** (BRL Price + Adaptive Pricing owns presentment; no geo code). Stripe calls live in `src/lib/stripe/billing.ts` — `getOrCreateStripeCustomer` (idempotency key `billing-customer:<companyId>`) / `createCheckoutSession` (**no** idempotency key — see the 2026-09-02 follow-up) / `createBillingPortalSession`. `metadata` (`companyId`/`planKey`) on both the session and `subscription_data`. `src/lib/billing/activation.ts` `isBillingActive()` **created but not wired** — P6 enforces it on hire + K6 activate. Stateless local Stripe mock (`STRIPE_API_BASE_URL` → SDK `host`/`port`/`protocol`) that 400s any session create carrying `currency`.
**Why:** Plan change goes through the **Customer Portal**, not `subscriptions.update` in our code, because (a) Stripe Checkout genuinely can't modify an existing subscription — confirmed in Stripe's own docs, "Checkout sessions are only for initial subscription signups" — so the choice was always Portal vs. build-our-own; (b) building our own swap means owning the idempotency key, the proration-invoice card decline → `past_due`, downgrade credit, currency-locked edge cases, for an action a merchant does rarely; (c) the Portal throws in card update / invoices / cancellation for free, which P5/P6 would otherwise build; (d) it keeps our entire Stripe write surface to two calls (create Checkout Session, create Portal Session) — no `subscriptions.update` means the idempotency-key-on-a-toggle problem never exists. The user's instinct ("shouldn't the change come through a webhook?") is exactly this: merchant acts on the Portal → `customer.subscription.updated` → P4 writes `company_billing`. P3 still writes the `incomplete` stub on first checkout (not left to P4) so Customer reuse and "is there a live subscription?" have a local anchor without a `subscriptions.list` every call. Upsert (not insert) on that stub because a concurrent first-checkout double-submit would 500 on `unique(company_id)`. No `currency` on the session is the load-bearing half of the multi-currency design (P1). `isBillingActive` unwired because its enforcement points are P6 and a hard block here predates the P4 webhook that sets `active`.
**How to apply:** Never add `subscriptions.update` to our codebase for plan changes — the Portal owns it; if a one-click in-app upgrade is ever wanted as a conversion optimisation, build *only* that flow and keep the Portal for everything else. P4 fills `stripe_subscription_id` / `subscription_status` / period / `plan_key`-on-change columns from webhook events — P3 only ever sets `stripe_customer_id`, `plan_key` (initial), and `incomplete`. The Customer Portal must be configured + set as default in the Stripe Dashboard per environment (sandbox config `bpc_1UBFRxHAg1kV3YLSEVKLouiN`); the Portal API call fails without a saved config. `success_url` / `return_url` point at `/dashboard/settings/billing`, which doesn't exist until P5 (404 interim). When P6 wires `isBillingActive`, call it in the hire `POST` and the `PATCH` that sets `company_agents.status = 'active'` — return 402/403 with an upgrade pointer, don't silently no-op.

## 2026-09-02 — R2: intake fields become typed + stable-keyed with a predefined core set; email is a locked required field (no booking without one)
**Decision:** `appointment_intake_fields` gains `key` (immutable slug, `unique(company_id,key)`), `field_type` (`email`/`name`/`phone`/`cpf`/`date`/`text`), and `is_enabled`. `intake_answers` is keyed by `key`, not the editable label. A fixed predefined core set (`email`, `full_name`, `phone`, `cpf`, `date_of_birth`) is trigger-seeded for every company (`after insert on companies`, backfilled for existing ones); its labels/types are code constants, the merchant only toggles enable/require. **`email` is locked enabled + required** — the PUT route refuses to change either. `book()` matches answers by key, format-checks known types (`invalid_intake_answers` on a bad value), and writes `name`/`email`/`phone` answers onto the `customers` row (blanks only). The PUT contract changed to `{ predefined?, custom? }` with a full server-side rebuild.
**Why:** The user flagged the K8 model as fragile — a human label as the `intake_answers` key means renaming a label orphans answers, the AI has to echo it back exactly, and nothing is validated. The user's own proposed shape (email always required, fixed toggle-able fields, free custom fields after) is the standard "structured core + freeform tail" booking pattern and is what we adopted. Email strictly required (no company-level escape hatch) because every downstream feature — J5's cross-device lookup, R3 confirmation, R4 reminder, R5 waitlist — is dead without it, and a merchant who wants zero email friction is rare enough not to design around. Trigger-seeded rows (not a code-merged virtual list) so `loadIntakeFields` stays one plain query and the settings UI is one uniform list; the `after insert on companies` trigger covers every creation path (`create_company_with_owner`, onboarding) without touching them. Predefined labels fixed (not editable) because the whole point is a canonical key/type — a merchant renaming "Email" buys nothing and risks confusion. Validation deliberately light (regex/digit-count, not full CPF checksum or RFC email) — enough to stop "sim" being stored as an email, not a spec engine.
**How to apply:** A new predefined field = one entry in `PREDEFINED_INTAKE_FIELDS` (`src/lib/appointments/intake-fields.ts`) + a row in `private.seed_predefined_intake_fields` + a backfill `select private.seed_predefined_intake_fields(id) from companies`. Custom fields are always `field_type = 'text'`; giving merchants a type picker for custom fields is a future extension (the column already supports it). Pre-R2 `intake_answers` rows stay label-keyed and are left as-is — K10's display un-slugs the key and those old keys pass through essentially unchanged; no data migration. If email verification ever ships (with R1), that's what would let a stated-email booking be *acted on* cross-device (J5) — unrelated to this field being required.

## 2026-09-02 — P2: billing schema — usage counter is a new row per period (not a reset), one atomic RPC is the only writer, enum over-populated
**Decision:** Three tables + one enum + one function, migrations `20260902150000` / `20260902150100`. `company_billing` (1/company, Stripe subscription mirror), `company_message_usage` (1/company **per billing period**, `unique(company_id, period_start)`, holds `replies_used` + a `reply_limit` snapshot), `stripe_webhook_events` (`event_id` PK idempotency ledger). The "monthly reset" is **not** a mutation — the P4 webhook inserts a fresh `company_message_usage` row when Stripe's `current_period_start` advances; the old row is kept. `record_ai_reply(p_company_id uuid) returns table(replies_used int, reply_limit int)` is `SECURITY DEFINER` in `public` (execute revoked from `anon`/`authenticated`, `service_role` only), and is the **single writer** of `replies_used` — one `UPDATE … FROM company_billing … WHERE u.period_start = b.current_period_start RETURNING`. No usage row for the current period → returns zero rows, caller proceeds without counting or blocking; row creation is exclusively P4's. `plan_key` is `text` + `CHECK (in 'starter'/'pro'/'enterprise')`. `stripe_subscription_status` enum carries Stripe's **entire** value set (`incomplete`, `incomplete_expired`, `trialing`, `active`, `past_due`, `canceled`, `unpaid`, `paused`), not just the states our flows create. RLS: member `select` on billing + usage, no write policy, `insert`/`update`/`delete` also revoked from `authenticated`/`anon`; `stripe_webhook_events` is RLS-on-zero-policies. No generated Supabase types (the repo has never used a typed client). Tests: `tests/integration/billing-schema.test.ts`.
**Why:** A new row per period instead of zeroing a counter makes the whole thing idempotent and self-healing — a redelivered `invoice.paid` hits `on conflict do nothing`, a late webhook just means the previous period's row keeps taking the count for a bit (harmless under soft-cap), and Stripe stays the sole clock (annual plans, proration, dunning, trial→active all work with no extra logic — same reasoning as N6's cron). Snapshotting `reply_limit` onto the row means a mid-period upgrade/downgrade can't retroactively change what the customer was already told their ceiling was. A single atomic RPC as the only increment path is what keeps a future per-bot/per-channel weight a parameter + a config map rather than a migration; doing the check-and-increment in one `UPDATE` (not select-then-update from the app) is what makes concurrent replies safe. The RPC deliberately does **not** self-provision the usage row: that would need the plan's limit reachable from SQL, which would drag the plan catalog back into the database and undo P1's "catalog in code" decision — so P4 (TypeScript, can `import` `plans.ts`) owns row creation, and it creates the first row at `checkout.session.completed`, before any bot can reply. **Decision:** The embeddable widget's iframe (`public/widget.js` → `/talk/{company}/{agent}?embedded=1`) uses the `embedded=1` query param purely to drive UI (whether `chat-widget.tsx` shows a close button), while `document.referrer` — read fresh at each `fetch()` call, never stored in state or a ref — is the only thing that becomes `embeddedOn` in API calls. ## 2026-08-30 — M3: embed-domain checking requires client self-report; rate limits are three separate checks, not one
**Decision:** The public chat API's domain-allowlist enforcement depends on the client (M4/M5, not built yet) sending an `embeddedOn` field captured at iframe-load time (`document.referrer`) — the API itself cannot observe which site embedded the chat page from the request's own `Origin`/`Referer` headers, because the chat page's `fetch()` calls to its own API are always same-origin to Staffra regardless of iframe nesting. Separately, rate limiting is three independent checks (per-IP rolling window via a new table, per-conversation rolling window and per-conversation hard cap both reusing `messages` directly) rather than one unified mechanism.
**Why:** This isn't a design shortcut, it's the actual architecture: the only point in the whole request lifecycle where "what page embedded this" is observable at all is client-side, at the moment the iframe loads — by the time the page's own JS calls the API, that context is gone from the HTTP layer entirely (the request originates from Staffra's own document, not the parent frame's). Any implementation that tried to read this from server-side headers alone would silently not work, full stop — not a matter of trying harder. Splitting rate limiting three ways rather than one generic mechanism was a deliberate response to three genuinely different threats: an IP hammering the endpoint (any conversation, any company), a single conversation being spammed in a short burst, and a single conversation running up an unbounded lifetime cost even at a slow, individually-reasonable pace — one counter can't distinguish these, and conflating them would either under-protect one case or over-restrict a legitimate one.
**How to apply:** If M4/M5's actual implementation of "capture and send `embeddedOn`" ends up using a different signal than `document.referrer` (e.g. a `postMessage` handshake with the parent frame instead), the API contract here (`embeddedOn` as an arbitrary URL string) doesn't need to change, only what populates it — don't revisit this decision for that. The `embeddedOn`-based check is honestly no more spoofable outside a real browser than anything else in this three-layer scheme (a raw `curl` call can already lie about the subscription-gate-adjacent facts too) — it's scoped to stop casual/accidental misuse, not a determined attacker, consistent with the roadmap's own stated bar. If a rate-limit threshold proves wrong in practice (too strict for real usage, too loose against real abuse), adjust the specific constant in `src/lib/web-chat/rate-limit.ts` — don't collapse the three checks back into one to "simplify," they're answering three different questions on purpose.

## 2026-08-29 — I1 Google Calendar connect: JS popup code client (mirroring D1), not a server-redirect OAuth flow
**Decision:** `company_calendar_connections` (migration `20260829201627`) + `POST /api/companies/[companyId]/calendar/connect` implement Google OAuth as a structural copy of D1's WhatsApp Embedded Signup flow: a browser-side JS SDK (K2, not built yet — Google Identity Services' `google.accounts.oauth2.initCodeClient({ ux_mode: 'popup' })`) drives the actual consent popup and hands the browser a short-lived authorization `code`, which gets POSTed to our route as `{ code }`. ## 2026-08-29 — Appointments: DB-level exclusion constraint prevents double-booking; buffer time is baked into `ends_at`
**Decision:** Trello H3's `appointments` table prevents overlapping bookings for the same company with a native Postgres constraint, not an application-layer check: `exclude using gist (company_id with =, tstzrange(starts_at, ends_at, '[)') with &&) where (status not in ('cancelled', 'no_show'))`, requiring the `btree_gist` extension. `ends_at` is always computed server-side (never trusted from the client, on both create and reschedule) as `starts_at + (service.duration_minutes + service.buffer_minutes) minutes` — the buffer is part of the reserved slot, not a separate field layered on top. A violation raises Postgres error `23P01`, caught in the POST and PATCH route handlers and turned into a clean `409`.
**Why:** An app-layer "SELECT for overlaps, then INSERT if clear" check has a real race window — two concurrent booking requests for the same slot (plausible the moment Ana's own booking tool exists and a customer double-taps, or two customers grab the same last slot at once) can both pass the check before either insert lands. A database-level exclusion constraint closes that window structurally: the second conflicting insert is rejected by Postgres itself, not by a check that already ran too early. Baking `buffer_minutes` into `ends_at` (rather than checking `duration_minutes` for the constraint and `buffer_minutes` separately) keeps the constraint's own range check simple and correct by construction — there's only one interval per appointment to reason about, and cleanup/travel time between bookings is enforced by the exact same mechanism as the booking itself, not a second parallel check that could drift out of sync with it.
**How to apply:** Any future code that reads `appointments.ends_at` expecting "when the service ends" (rather than "when the slot is fully released") must subtract `buffer_minutes` back out — this will matter first for K4's appointments-view UI, which should show the customer-facing end time, not the buffer-inclusive one. Don't add a second overlap check anywhere in application code on top of this constraint; catching `23P01` is the correct and sufficient response to a conflict.

## 2026-08-29 — Hybrid product search: pgvector semantic leg fused with lexical search via RRF, generated at write time
**Decision:** `products.embedding vector(1536)` (migration `20260829150000_add_product_embeddings`, `text-embedding-3-small`) adds a semantic search leg alongside the existing `search_vector` lexical one. `search_products` fuses both via Reciprocal Rank Fusion (`score = 1/(60+rank_fulltext) + 1/(60+rank_vector)`, each leg's own top-50 candidate pool computed independently), rather than a weighted sum of `ts_rank` and cosine distance (incomparable scales). Embeddings are generated **at write time** (`src/lib/products/embeddings.ts`, wired into `POST`/`PATCH`/the B4 import route), never blocking a write on failure (`null` = "not embedded yet," falls back to lexical-only for that row). `ProductRepository.search`'s new `openaiClient?` param is **not** defaulted the way `supabaseClient?` is — only `search_products` (via a new `ctx.openai` on `ToolExecutionContext`) passes one; every other caller stays lexical-only unless it opts in. `tests/integration/global-setup.ts` sets `DISABLE_PRODUCT_EMBEDDINGS=true` for the spawned test process so the integration suite's ~60 product-create call sites never make a real OpenAI call. `PRODUCT_PUBLIC_COLUMNS` (`src/lib/products/columns.ts`) replaces `select("*")` everywhere a product row reaches a client, so the 1536-float column never leaves the server. A one-off script (`scripts/backfill-product-embeddings.mjs`) embedded all pre-existing products (28, on the real project).
**Why:** Lexical search has a hard ceiling that no amount of tokenizing, keyword expansion, or word-dropping can close: `to_tsvector('portuguese', 'roupa')` and `'vestiment'` (from "Vestimentas") are unrelated lexemes to Postgres, full stop, because full-text search compares stems, not meaning. Found by hand-testing the same day as the lexical fixes above — a merchant's real category word ("Esporte") and a customer's paraphrase ("algo pra usar no estádio", "time") shared no lexeme, so the earlier fixes (category-in-vector, dead-word-dropping) could not have closed this specific gap; only comparing *meaning* can. RRF over a weighted sum: `ts_rank` and cosine distance have no common scale, and picking arbitrary weights would silently let one leg dominate — RRF's rank-position-only formula sidesteps calibration entirely and is the standard choice in Postgres hybrid-search references (Supabase's own, Weaviate's). Write-time generation (not a backfill-only job) is the direct lesson from this session's earlier CSV-in-bucket discussion: a snapshot or lagging job reintroduces exactly the staleness problem that was explicitly rejected for a merchant's catalog — a product must be semantically searchable from the moment it's created, and an edited name/description/category must not leave a stale vector behind. The opt-in (not defaulted) `openaiClient` param exists specifically so this feature costs nothing in tests or in any future caller that doesn't ask for it — `supabaseClient?` can default safely because a local Postgres call is free and deterministic; defaulting a paid external API call would not be. `PRODUCT_PUBLIC_COLUMNS` was a bug found while making this change, not introduced by it: `search_vector` had already been silently leaking through every `select("*")` since the 2026-08-27 full-text migration.
**How to apply:** If recall still misses a real paraphrase, the fix is almost never "add another lexical special case" — check whether the vector leg is actually finding it (query `search_products` directly with a real embedding) before reaching for prompt/lexical changes. Both legs' candidate pools are capped at 50 — if a company's catalog grows past a size where that pool misses genuinely relevant items, raise it there, not in the final `p_limit`. Precision-affecting change: a product's PRICE/description edit only re-embeds when `name`/`description`/`category` is part of the same `PATCH` (see `[productId]/route.ts`'s own comment) — don't assume every edit refreshes the vector. If the embedding model ever changes, that's a new migration widening the column plus a full re-embed; two different models' vectors are not comparable, so a mixed-model column would silently corrupt ranking. `EMBEDDING_MODEL`/`EMBEDDING_DIMENSIONS` are pinned constants in `embeddings.ts`, not env-configurable, specifically to prevent that drift.
**Known limitation, found while testing this same change:** the vector leg (`vector_top` in the SQL) has **no similarity/distance threshold** — it's a plain top-50 nearest-neighbour pool with no "too far to count" cutoff, so on a small catalog (a handful of products) a genuinely unrelated product can still surface with a low RRF score, ranked behind the real match rather than excluded (`product-search-hybrid.test.ts`'s precision test asserts the ranking guarantee, not absence — see its own comment for why). Deliberately not fixed with an invented cutoff: real embedding-model cosine distances have no universal "unrelated" value, and an untuned threshold risks silently re-introducing the exact recall gap this whole feature exists to close — the same "don't guess, name the exact failure first" discipline every other guardrail fix in this log follows. If hand-testing turns up a case where this is a real customer-facing problem (an irrelevant product actually gets *recommended*, not just present in a tool result the model correctly ignores), that's the concrete failure to tune a threshold against — pick it empirically from this catalog's real embedding distribution, don't guess one now.

## 2026-08-29 — Product search: category is indexed, and a word the catalog never uses is dropped instead of killing the query
**Decision:** Two changes to product search recall, from one hand-testing report. (1) `products.category` joins `name`/`description` in the `search_vector` generated column, weighted `C` (migration `20260829120000_index_product_category_in_search_vector`). (2) `ProductRepository.search` gains a zero-result relaxation: when the strict pass finds nothing, each distinct word is probed once in parallel (`limit 1`, same filters), words matching nothing anywhere in the catalog are dropped, and the search re-runs with the survivors **still ANDed**. `search_products`' tool description also now tells the model to keep each term to one or two words and to add the kind of thing it is (sport/activity/occasion) as its own term.
**Why:** A merchant asked Malu for "camisa de time", then "camisa de futebol", and was told the store had neither — but "camisa do corinthians" found the shirt instantly. Verified against the real catalog before changing anything, and it was two independent causes, neither of them "the model doesn't know Corinthians is a team". First: `websearch_to_tsquery('portuguese', 'camisa de futebol')` is `'camis' & 'futebol'`, and "futebol" existed **only** in `products.category`, which was never indexed — real merchant-curated data invisible to search, with the `p_category` filter no help since it needs an exact case-sensitive value the model is told never to guess. Second: `'camis' & 'tim'` matched nothing even though `'camis'` alone matched, so one word the catalog has never heard of silently killed an otherwise good query. The relaxation is deliberately *not* OR-of-words: that would answer "camiseta azul masculina" with a "Calça Azul", reintroducing exactly the irrelevance the 2026-08-27 full-text rewrite existed to remove. A word with no match anywhere carries no information, so dropping it loses no precision while everything the catalog does know stays required together. Prompt guidance alone wasn't enough for the same reason as everywhere else in this log — a model can always phrase a keyword some way nobody anticipated — so the code-level backstop pairs with it, in the spirit of `MAX_LIMIT`.
**How to apply:** This **supersedes** the earlier integration test asserting that "camiseta azul masculina" must return `[]` when only "Camiseta Azul" exists; that expectation turned out to be the same bug in miniature. The invariant that actually matters is unchanged and is still pinned by that test: search must never degrade into matching ANY word — a product sharing only "azul" must never come back for a camiseta query. Keep it that way; if recall still falls short, drop more *dead* words, never relax the AND between live ones. Note the relaxation costs one probe per distinct word, but only on a path whose alternative is telling the customer the store has nothing. Any future field a merchant curates (brand, tags, variant labels) is a candidate for the same `search_vector` treatment — weight it below `name`, and remember a generated column has to be dropped and re-added, taking its index with it.
## 2026-08-29 — SCOPE_GUARDRAIL: Malu is for this store only, but defers to the business's own data first
**Decision:** Fifth platform-level guardrail in `prompt.ts`. Malu refuses questions unrelated to this store, its products, an order, or helping this customer shop — general knowledge, trivia, history/geography, news, weather, maths/homework, code, medical/legal/financial advice — even when she knows the answer and it would take a second. **Ordered after (and explicitly deferring to) `GROUNDING_GUARDRAIL`**: she checks whether the business has something on file first, and a real answer on file always wins however off-topic the question sounds; she declines only when there's nothing. The guardrail also names what stays in scope (greetings, small talk, courtesy, empathy, needs/occasion/size/style/budget discovery, opinions on the store's own products) and what framings not to fall for ("just this once", "quick question", roleplay, an off-topic question smuggled into a real one — answer the store part only).
**Why:** Found hand-testing: asked for a country's capital and when the light bulb was invented, Malu answered both. The deference ordering is the load-bearing part: C3's guardrail exists *because* "this doesn't sound like a store question" was found to be an unsafe reason to skip checking the FAQ ("Setembro chove?"), so a scope rule written naively would have silently reverted that fix. Naming what remains allowed is equally deliberate — the obvious failure mode of a scope rule is a wall, and needs discovery is spec §6's core sales behaviour, not off-topic chat.
**How to apply:** Prompt-only, with no code-level backstop, and that's not an oversight: unlike C7's numeric grounding check, "is this off topic" is a semantic judgement with no canonical value in Postgres to test against, so there's nothing deterministic to pair it with. If it proves too strict (declining something that was really about the store) or too loose (still answering trivia), name the exact case in the wording — same shape as every other guardrail entry in this log — and re-check the two assertions in `prompt.test.ts` that pin the FAQ precedence, which must never be weakened to make a scope fix work. Note that it deliberately does **not** make her deny being an AI or explain any restriction; that stays consistent with `CAPABILITY_GUARDRAIL`'s soft-deflection policy call (see the 2026-08-27 entry).

## 2026-08-29 — C7 grounding validation: post-hoc fact check (approach b), enforced only where Postgres has a canonical value
**Decision:** Trello C7 ships as `src/lib/agent-engine/grounding.ts`, replacing C1's pass-through `validateResponse` stub. The card offered two MVP approaches and asked for one to be picked and documented — this is **(b)**: `runToolLoop` now returns the tool results it used to discard, and the final text is checked against them before it can be sent. Enforcement is **restricted to numeric price and stock claims**; non-numeric policy/characteristic claims stay covered by the prompt-level `GROUNDING_GUARDRAIL` only. A figure is grounded if it appears in this turn's tool results, in the customer's own message, or in the company's real current data (active products' `price`/`stock`, plus the numbers in its policy/FAQ/description text). On failure the turn is regenerated once with a `developer`-role correction naming the rejected figure; only a second failure returns the canned `UNGROUNDED_FALLBACK_TEXT`. The rejected draft is deleted from the OpenAI conversation before the retry.
**Why:** Approach (a) ("constrain the model to quote/template tool results directly") is not enforcement — it's another instruction, the same category as the guardrail that hand-testing already broke twice during C3, and reciting fields would wreck spec §7's humanized conversation. The card's own framing ("a guarantee instead of a hope") only survives a deterministic check. The scope restriction is the honest half of that: **only a fact with a canonical value in Postgres can be verified deterministically**, so "we accept returns" or "it's cotton" cannot be pattern-checked without a second model in the loop, and claiming otherwise would ship a check that quietly guesses — exactly the failure mode this ticket exists to remove. Precision was prioritised over recall throughout (narrow claim patterns, URLs stripped, percentages skipped, ambiguous number formats counting every plausible reading) because a false block degrades *every* conversation while a miss lands back on the guardrail that already exists. The company-data source is what makes the whole thing usable: OpenAI holds prior turns server-side, so a price retrieved two turns ago and merely restated has no tool result in this process and would otherwise be blocked on an ordinary restatement — and checking live rows rather than caching a per-conversation ledger means a **stale** price fails, correctly. Regenerating before falling back matters because the model still has its tools: the common outcome is Malu actually looking the figure up, in her own voice and the customer's language, instead of a canned line. Deleting the rejected draft is not tidiness — `store: true` means a blocked invented price would otherwise sit in server-side history and be quoted back next turn, leaking the exact number the check just refused to send.
**How to apply:** Two things are now deliberately blocked that a merchant may notice: a **self-calculated total** ("as duas juntas ficam R$ 139,80" — real prices, invented sum) and a figure quoted for a product the store doesn't have. The first got a matching sentence in `GROUNDING_GUARDRAIL` — prompt and enforcement must stay in sync, or the model keeps producing text the check keeps rejecting. If a false block shows up in hand-testing, fix the **claim pattern** that over-matched, not the general principle (same shape as every other guardrail entry in this log); if an invented figure gets through, add the pattern that missed. Do not widen the check to all numbers — result counts ("encontrei 3 opções"), sizes and dates are numbers too, and blocking those was the first thing ruled out. Extending enforcement to delivery-time or business-hours figures is plausible later but was left out: those are policy numbers whose canonical form is free text, so they'd ride on the policy-text source with much weaker precision. `AgentEngineResult.grounding` exists for G1's QA pass to see the check fire; `UNGROUNDED_FALLBACK_TEXT` is the one string in the pipeline that can't honour `LANGUAGE_GUARDRAIL`, and `deps.ungroundedFallbackText` is the seam for D2 to localise it once real routing knows who it's talking to.

If either half proves too narrow in practice (still skips a check, or still reinterprets a result some other way) or too broad, the fix is the same shape as everything else in this log: name the exact new failure pattern, don't just widen the wording generically. Notable pattern across this whole log now: grounding bugs keep surfacing in *stages* one fix reveals the next of (didn't check -> checked but distorted the result) -- worth remembering that fixing the first-observed failure mode doesn't necessarily mean the underlying principle is now fully enforced.

## 2026-08-27 — search_products: general-category words must be expanded into concrete product types

## 2026-08-27 — Product search rewritten: Postgres full-text search + LLM keyword expansion, replacing ILIKE
**Decision:** `ProductRepository.search` now calls a Postgres function (`public.search_products`, migration `20260827180000_add_product_search_ranking`) instead of building an `ilike` filter in application code. The function does full-text search (`tsvector`, `portuguese` config, `name` weighted above `description`) with `pg_trgm` similarity as a ranking-only tie-breaker (deliberately **not** a match qualifier — see the function body's own comment: applying `similarity()` to a whole multi-word phrase is lenient enough to false-positive on a shared prefix alone, e.g. "Camiseta Branca" scoring close to a "camiseta azul" query). `ProductRepository.search`'s `text` (single phrase, words ANDed) and new `keywords` (list of alternatives, OR'd against each other) params are just merged into one list passed to the function. The `search_products` **agent tool** now asks the model for `keywords` (2-5 related terms — literal words plus synonyms/alternate phrasings) instead of one `text` string, in the same tool-call turn it was already making (no extra LLM round trip).
**Why:** A real bug found hand-testing Malu: asked for "camiseta azul", got told nothing matched, even though a "Camiseta Azul" product existed — the original `ilike '%text%'` match required the whole query to appear as one literal substring, which fails whenever query words are split across `name`/`description`, or a caller (an LLM constructing search args from conversational context) adds one extra qualifying word. A same-day intermediate fix (tokenize the query, require every word present somewhere, still application-side `ilike`) shipped first and closed the immediate bug, but was itself superseded within the same session by this full rewrite: full-text search was already the sanctioned upgrade path per B5's own original file comment, doesn't require pulling a wide unranked candidate pool into JS to rank (the DB now ranks and limits directly), and full-text token matching is strictly more precise than `ilike` substring matching too (`to_tsvector` won't match "azul" inside "Azulejo" — different lexemes — where `ilike '%azul%'` would have false-positived on it). Separately, LLM keyword expansion (asking Malu for a few related terms instead of one phrase) was chosen over two more expensive alternatives considered and rejected for now: (a) a dedicated query-expansion LLM call — strictly worse, since it adds a redundant round trip the existing tool-call turn doesn't need; (b) embeddings/`pgvector` semantic search — the "most correct" long-term answer for true paraphrase understanding (spec's "understand the customer" priority), but real recurring cost/latency (an extra OpenAI call per search) and new infra (re-embedding pipeline on catalog writes) not justified until the cheaper combination here proves insufficient in practice.
**How to apply:** Validated directly against real production data (company `76529c46-85f2-43cb-86d1-7a71e53f034c`, whose real "Camiseta Azul" product was the original bug report) via the Supabase MCP's `execute_sql`, reproducing the exact failing query and confirming both the fix and the `keywords` OR-across-alternatives behavior, plus a precision check ("azul" does not match "Azulejo Decorativo"). `supabase db reset` locally applied the migration with no errors; `npm run test:unit` (19/19) passed; the full local `vitest --project=integration` run could not be completed in this session because Next.js refuses a second `next dev` instance against the same project directory while a real `npm run dev` was active — the new/updated integration tests in `tests/integration/product-search.test.ts` and `tests/integration/agent-engine.test.ts` are believed correct by the same reasoning validated against production data above, but have not yet had an automated pass locally; run the suite before trusting it blindly in CI. 20 adversarial test products (same-name-different-size, cross-category color overlap, a comma/quote-in-name case, an out-of-stock case, and the "Azulejo" substring trap) were seeded directly into that same real company for manual testing — ask before deleting them if this comes up, they weren't cleaned up in this session.

## 2026-08-27 — CI uses `npm install`, not `npm ci` — a real npm bug with multi-platform optional native binaries

## 2026-08-27 — Never resolve a package-lock.json merge conflict with a plain `npm install` on one platform
**Decision:** Resolving a `package-lock.json` merge conflict must be a full regenerate (delete `package-lock.json` and `node_modules`, then `npm install` fresh), never a plain `npm install` run against the conflicted file to "fix itself."
**Why:** Broke CI (`No matching Supabase CLI binary package found for linux-x64` on `ubuntu-latest`) after a `feature/C1` rebase's `package-lock.json` conflict was resolved with a plain `npm install` on Windows. `supabase` (a devDependency) ships one `optionalDependencies` entry per platform (`@supabase/cli-darwin-arm64`, `@supabase/cli-linux-x64`, `@supabase/cli-windows-x64`, ...); npm only actually installs the one matching the machine it runs on. ## 2026-08-27 — Conversations rotate after 24h of inactivity, prototyped in the dev-chat-test tool ahead of D2/D3

**How to apply:** When D2 (inbound webhook) and D3 (conversation engine) are actually built, this exact rule — filter conversation lookup to `status = 'active'`, check `updated_at` age against a 24h constant, close-and-recreate on staleness, touch `updated_at` after every turn — should move there and be deleted from the dev-chat-test route (which is itself temporary, see its own `TODO(C1-TEST-ONLY)`). ## 2026-08-26 — Sensitive column locked down with column-level GRANTs, not a second table
**Decision:** `company_whatsapp_connections.access_token` (Trello D1) lives on the same table as the rest of the connection metadata. It's locked down with column-level grants — revoke the table-wide select/insert/update privilege, then re-grant it back naming every column except `access_token` (migration `20260826104820`) — rather than moving it into a separate zero-RLS-policy table (the initial approach, reverted after user pushback).
**Why:** User asked directly why it needed two tables instead of one. Postgres column-level privileges are the more idiomatic tool for "this row is fine to read except one field" — one migration, one table, no join. It also fails *louder*: a regular client's `select *` (or any query naming the column) gets an outright permission error, rather than a separate-table design's silent empty result for a stray query against the wrong table. The one thing it gives up is discoverability — a table with zero policies visually announces "don't touch this" to someone skimming table names, where a locked column requires checking grants specifically; judged an acceptable tradeoff for one column on one table. **Pitfall hit while building this:** a column-level `revoke select (access_token) ... from authenticated` layered on top of the pre-existing table-wide grant (from `20260825171500`) is a silent no-op — Postgres's table-wide privilege supersedes a column-level one rather than being narrowed by it. Only caught because the RLS integration test actually exercised a live select against local Supabase, not from reading the SQL. The fix is to revoke the table-wide privilege entirely first, then re-grant per-column.
**How to apply:** Any future "one sensitive field on an otherwise normal row" case (an API key, a webhook secret, etc.) should default to this same column-level-grant pattern, not a second table, unless the sensitive data genuinely needs its own independent lifecycle (different retention, different FK shape) that a single column can't express. Always verify a column-level lockdown like this with a real RLS integration test (an authenticated client actually attempting the select) — the revoke-on-top-of-a-table-wide-grant no-op won't show up from SQL review alone.

## 2026-08-25 — faq shape is `{ question, answer }[]`; PATCH endpoints use merge-patch semantics
**Decision:** Trello B2's `PATCH /api/companies/[companyId]` establishes two conventions with no prior precedent in this codebase: (1) `companies.faq` (jsonb) is an array of `{ question: string, answer: string }` objects, capped at 50 entries (300/2000 char limits on question/answer), saved as a whole-array replace, not per-entry patches; (2) the endpoint uses merge-patch semantics — a field key present in the request body with value `null` clears that column, a key omitted entirely leaves the existing value untouched.

## 2026-08-25 — Product list excludes soft-deleted rows by default; price/currency validated as a pair, including on partial update
**Decision:** Trello ticket B3's `GET /api/companies/[companyId]/products` excludes `is_active = false` rows unless the caller passes `?includeInactive=true`. `DELETE` on a product does `UPDATE is_active = false`, never a real `DELETE`. Both `POST` (create) and `PATCH` (update) reject a `price` present without a `currency`; `PATCH` computes this against the row's state *after* the requested fields are merged in, not just the fields present in that one request.
**Why:** The card explicitly asks for soft-delete "to preserve historical event data" (`events.product_id` can reference a product) — a hard delete would either cascade-null those rows or fail the FK. Hiding inactive products from the default list keeps the common "list my catalog" call from needing every caller to filter deleted rows out client-side, while `includeInactive=true` still allows a UI that wants to show/restore them. Validating against the merged state (not just the request body) closes an easy hole: `PATCH { currency: null }` on a product that already has a `price` would otherwise silently produce a priced-but-currency-less row.
**How to apply:** Any future soft-deletable resource should default list endpoints to excluding inactive/deleted rows with an explicit opt-in query param, rather than making callers filter client-side. Any future paired-field validation (values that only make sense together) on a `PATCH` endpoint must validate the effective post-merge state, not just the fields present in that request.

## 2026-08-25 — create_company_with_owner RPC must be SECURITY DEFINER, and public-schema functions need an explicit `anon` revoke
**Decision:** Trello ticket A3's create-company RPC (`public.create_company_with_owner`, migration `20260825154320`) is `SECURITY DEFINER`, not the initially-tried `SECURITY INVOKER`. Also added an explicit `revoke execute ... from anon` alongside the `from public` revoke.
**Why:** Two RLS/grants gotchas hit while implementing and testing this against the live project (verified via a real signup + authenticated RPC call, not just reasoning about the SQL): (1) With `SECURITY INVOKER`, the function's `insert into companies ... returning * into new_company` failed with "new row violates row-level security policy for table companies" — the `RETURNING` clause is itself checked against the table's SELECT policy (`is_company_member`), and the caller isn't a member yet at that point since the `company_users` owner row is the *next* statement. This is a standard chicken-and-egg RLS problem for any "create X and become its owner" flow. `SECURITY DEFINER` bypasses RLS for the whole function body, which is safe here only because the function hardcodes the owner to `auth.uid()` and takes no `company_id`/`user_id` params. (2) After switching to `SECURITY DEFINER`, `revoke execute on function ... from public` alone left `anon` still able to call it — Supabase's public-schema default privileges grant EXECUTE directly to `anon`/`authenticated`/`service_role` on new functions, not via the `PUBLIC` pseudo-role, so revoking from `public` doesn't touch them.
**How to apply:** Any future RPC function in `public` that (a) needs to bypass RLS for a legitimate multi-table write, or (b) has `RETURNING` on a table whose SELECT policy depends on a row inserted later in the same function, should default to `SECURITY DEFINER` with an explicit `auth.uid() is null` guard (never trust an implicit invoker-rights check for this pattern). And whenever a public-schema function shouldn't be `anon`-callable, revoke from `anon` explicitly — `revoke ... from public` is not enough on this project.

Putting them in an API-unexposed schema removes the RPC surface while leaving them fully usable from RLS (which executes in-database, unaffected by PostgREST schema exposure).
