# Architecture

High-level structure of the system: main components, how they talk to each other, and why.

## Components

Sidde MVP: a platform for hiring pre-built AI employees (first: Malu, an AI sales rep) that talk to customers over WhatsApp. See `Sidde_MVP_Specification.md` (repo root) for full product spec and `Sidde_MVP_Database_Tables.md` for the original table sketch.

Supabase project: **ai-employees** (`wtewquippvcteuxzcztd`, org `pxgsqmjvtajofdyaepyr`, region us-east-2). A separate "Faceless Videos" project exists in the same org — unrelated, do not target it.

## Application

Next.js (App Router, TypeScript, Tailwind) at the repo root, alongside `supabase/` — one codebase for both the admin dashboard UI and API routes/server actions (decided over a separate backend+frontend split; see decisions.md). Source lives under `src/app/`; non-route logic (Supabase clients, future domain code) lives under `src/lib/`.

### Auth (Trello A2)

Supabase Auth via `@supabase/ssr`, cookie-based sessions:
- `src/lib/supabase/client.ts` / `server.ts` — browser and server Supabase clients.
- `src/lib/supabase/middleware.ts` + `src/proxy.ts` — refreshes the session cookie on every request (Server Components can't write cookies themselves) and gates access: unauthenticated users hitting `/dashboard*` are redirected to `/login`; authenticated users hitting `/login` or `/sign-up` are redirected to `/dashboard`. Next.js 16 renamed the `middleware.ts` convention to `proxy.ts`/`export function proxy` — this repo already uses the new name.
- `src/lib/auth/actions.ts` — `login`/`signUp`/`logout` server actions, called directly from the `/login` and `/sign-up` page forms. Auth errors are translated to user-facing copy (`friendlyAuthError`) rather than shown raw. Lives under `lib/`, not `app/`, since it isn't a route — an `app/auth/` folder with no `page.tsx` would look like a route that doesn't exist.
- `src/app/api/me/route.ts` — `GET` current-user endpoint for non-Server-Component callers.
- `src/app/dashboard/page.tsx` is the marketplace home, the real front door as of Trello ticket F1 (see "Onboarding & admin shell" below) — no longer a placeholder.
- Company creation/membership is intentionally not part of A2 — that's A3, layered on top of a logged-in user.

Env vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (the modern `sb_publishable_...` key, safe to expose client-side — RLS is what actually protects data). Real values live in `.env.local` (gitignored); `.env.example` has the placeholder shape.

### Companies & membership API (Trello A3)

Route Handlers under `src/app/api/companies/` — this is the API surface other epics build against, so it's plain HTTP endpoints rather than Server Actions (see decisions.md):
- `GET /api/companies` — list companies for the current user. Plain `select * from companies`; RLS (`is_company_member`) already scopes it, no manual join.
- `POST /api/companies` — create a company. Delegates to the `public.create_company_with_owner` RPC (migration `20260825154320`) so the `companies` insert + `company_users` owner insert happen atomically in one Postgres function call, since supabase-js has no client-side multi-table transaction. The function is `SECURITY DEFINER` (RLS-bypassing) and `anon` is explicitly denied EXECUTE — see decisions.md for why both were necessary, not just the obvious-looking `SECURITY INVOKER` + `revoke ... from public`.
- `POST /api/companies/[companyId]/members` — add/invite a member (no email invites in MVP; target user must already have an account). Re-checks the caller is owner/admin at the API layer (querying their own `company_users` row) before inserting, so a non-admin gets a clean 403 instead of a raw Postgres RLS error. Additionally, only an existing `owner` can assign the `owner` role to someone else — an `admin` can add members/admins but not mint another owner. This distinction is API-layer only: RLS's `is_company_admin` treats `owner`/`admin` as equivalent for every other operation (updating the company, managing membership in general), so owner-vs-admin has no meaning anywhere else in the system today.
- `GET /api/companies/[companyId]` (Trello B2) — the single-resource sibling of the list endpoint above; any member can view (`requireMember`, matches RLS's `is_company_member`). Returns the full row — profile fields (`name`/`email`/`phone`/`website_url`/`currency`/`country`/`timezone`/`industry`) plus the knowledge fields (`description`/`shipping_policy`/`return_policy`/`payment_policy`/`faq`/`additional_information`) that C3's `get_business_information`/`get_policy_information` tools will read at runtime. `industry` (nullable `varchar`, migration `20260827124109_add_industry_to_companies`) is a free-text business-sector label surfaced on the Settings "Business Identity" card — set/cleared through PATCH like the other short profile fields, not part of the `create_company_with_owner` RPC.
- `PATCH /api/companies/[companyId]` (Trello B2) — only owner/admin (`requireAdmin`, matches RLS's `is_company_admin`; the only route so far needing an admin-only file-local check that isn't the members route's bespoke owner-vs-admin logic). **Merge-patch semantics**: a key present with value `null` clears that column; an omitted key leaves it untouched — this is now the pattern for any future partial-update endpoint (e.g. B3's product update), not something to reinvent per-route. Validation limits (all file-local constants, no shared validation module exists yet): free-text fields (`description`, `shipping_policy`, `return_policy`, `payment_policy`, `additional_information`) up to 5000 chars; short profile fields up to 255 chars; `currency` exactly 3 chars (matching the DB's `varchar(3)`, checked here so a bad value 400s cleanly instead of surfacing a raw Postgres error); `faq` — see decisions.md for the shape. No RPC needed (unlike A3's create-with-owner): an UPDATE has no chicken-and-egg RETURNING-vs-SELECT-policy problem the way an INSERT-and-become-member does.
- `requireMember`/`requireAdmin` are file-local to this route (not extracted to `src/lib/`), matching B1's precedent above. Worth noting: this is now the third route file (A3's members route, B1's agents route, this one) with its own near-duplicate membership-check logic — a real candidate for extraction if a fourth shows up, but not done here since it's outside any single ticket's scope.

### Hire-an-agent API (Trello B1)

`src/app/api/companies/[companyId]/agents/[agentSlug]/route.ts` — the agent is a URL segment, not hardcoded, even though the MVP only ever hires `malu`: adding a second agent later means adding an `agents` row, not touching this route.
- `GET` — hire status for `agentSlug`: `{ companyAgent: {...} | null }`. Used by F1's onboarding wizard to decide "Hire Malu" vs "Malu is ready."
- `POST` — hire that agent: inserts a `company_agents` row directly with `status: "active"` (no `"hired"` intermediate state — see decisions.md). **Idempotent**: calling it twice returns the existing row with `200`, not an error — unlike A3's members endpoint, where a duplicate genuinely is a conflict. No RPC needed here (unlike company creation): the caller is already a company member before hiring, so there's no chicken-and-egg RLS problem to route around. Optional body `{ name?: string }` overrides the default display name (`company_agents.name` is a per-company, merchant-editable label); default is the slug capitalized (e.g. `malu` -> `Malu`) — `agents` has no `name` column of its own, only `slug`/`role`/`description`.
- Both handlers share two small file-local helpers (`requireMember`, `getAgentBySlug`) rather than duplicating the checks a second time within the same file. Unlike the earlier hardcoded-Malu version of this route, an unknown `agentSlug` is now a **`404`**, not a `500` — the slug comes from the caller (URL), so a bad one is a client error, not a platform config problem.
- Malu's `agents` row is seeded by a migration (`20260825181902_seed_malu_agent`), not `supabase/seed.sql` — `seed.sql` is local-dev-only and never touches the remote project, but Malu needs to exist there for hiring to work at all. Any future agent needs the same treatment: a migration-level insert, not a code change to this route.
- The `defaultAgentName(slug)` fallback (capitalize the slug — `agents` has no `name` column) lives in `src/lib/agents/naming.ts`, shared with the onboarding UI (below) rather than duplicated — a trivial pure-string helper, unlike the membership-check duplication above which is deliberately *not* shared.

### WhatsApp connection (Trello D1)

Backend-only ticket: provider decision + schema + the server-side endpoint(s)
F4 calls — F4 has since shipped for real, see the "Onboarding & admin shell"
section above (`src/app/dashboard/my-agents/[agentSlug]/channels-section.tsx`).
**Provider: Meta Cloud API direct** (Embedded Signup), not a BSP
(Twilio/360dialog) — see decisions.md for the cost/UX tradeoff that drove this.

- `supabase/migrations/20260826104820_create_whatsapp_connection_tables.sql`
  — one table, `company_whatsapp_connections` (one row per company,
  `unique(company_id)`): `phone_number_id`, `waba_id`, `display_phone_number`,
  `status` (`whatsapp_connection_status` enum: `pending`/`connected`/`disconnected`),
  `access_token`, `connected_at`. RLS: member-readable (`is_company_member`),
  admin-write (`is_company_admin`) for every column *except* `access_token`,
  which is locked down with an explicit column-level
  `revoke select/insert/update ... from authenticated, anon` followed by a
  `grant select/insert/update (every column except access_token) ...` —
  Postgres treats a table-wide grant as superseding any column-level grant,
  so the revoke has to remove the table-wide privilege first (the blanket
  grant from `20260825171500` gave one) and re-grant it back naming only
  the safe columns; a column-level revoke layered on top of an
  already-table-wide grant is silently a no-op (caught by the RLS test
  actually exercising it against local Supabase, not by reasoning about the
  SQL alone). This enforces the lockdown per-column regardless of the
  row-level policies, so a `select *` from a regular client errors outright
  rather than silently omitting or leaking the column. This was chosen over a second
  zero-policy table (the initial approach) because it's less schema
  duplication and is the idiomatic Postgres tool for "most of this row is
  fine to read, one column never is." Any future column with this same
  shape (client-scoped row, one field that must stay server-only) should
  follow this pattern rather than splitting into a second table by default.
- `src/lib/supabase/service.ts` (new) — `createServiceClient()`, a
  server-only Supabase client using `SUPABASE_SERVICE_ROLE_KEY` (new env
  var, no `NEXT_PUBLIC_` prefix). Bypasses both RLS and the column-level
  grant above — the only way to read or write `access_token`. **D4
  (outbound adapter) will need to reuse this exact client** to read the
  stored token when sending messages — don't re-derive a second
  service-role client.
- `src/app/api/companies/[companyId]/whatsapp/route.ts` — `GET` (member-readable
  status + display number, selecting an explicit safe-column list that never
  includes `access_token`), `DELETE` (admin-only disconnect: flips `status`
  to `disconnected` and nulls `access_token` via the service client — the
  regular admin client can't touch that column at all; a no-op, not an
  error, if nothing was connected).
- `src/app/api/companies/[companyId]/whatsapp/connect/route.ts` — `POST`
  (admin-only). Body `{ code, phoneNumberId, wabaId }`, exactly what Meta's
  Embedded Signup hands the browser on success (F4 will build that popup
  trigger). Server-to-server sequence against the Graph API
  (`https://graph.facebook.com/v21.0/...`, overridable via
  `META_GRAPH_API_BASE_URL` for tests): exchange `code` for a business
  access token, register the phone number for Cloud API messaging (reusing
  the previously-stored `two_step_pin` for this company if one exists, else
  generating a fresh one — migration `20260826135816`: Meta ties a phone
  number to whatever PIN its first `/register` call used, and rejects any
  later `/register` for that number with a *different* PIN
  ("(#133005) Two step verification PIN Mismatch") — a real bug hit and
  fixed while building this, since the original code generated a new random
  PIN on every call, breaking any reconnect),
  subscribe the app to the WABA's webhooks (**done here, not in D2** — D2's
  card only owns receiving/normalizing inbound messages), fetch
  `display_phone_number`. The whole row (including `access_token` and
  `two_step_pin`, both column-privilege-locked the same way) is
  written in one upsert via the service client — the regular client
  couldn't write `access_token` anyway, so there's no reason to split the
  write. Upserts on `company_id`, so reconnecting is idempotent (same
  convention as B1's hire endpoint). Any Graph API failure returns a
  generic `502` — Meta's raw error text is never surfaced, matching F2's
  don't-show-raw-API-errors convention.
- New env vars: `SUPABASE_SERVICE_ROLE_KEY`, `META_APP_ID`, `META_APP_SECRET`,
  `META_WHATSAPP_CONFIG_ID` (all server-only; see `.env.example`). Real
  values require a Meta App with the WhatsApp product + an Embedded Signup
  configuration — an external prerequisite this ticket can't create.
  `META_WHATSAPP_CONFIG_ID` isn't used by the connect route itself — it's
  for whichever page triggers the Embedded Signup popup (see the dev-test
  page below). **No `NEXT_PUBLIC_` env vars were needed for any of this**:
  the page that runs the Facebook JS SDK client-side is a Server Component
  that reads these server-only vars and passes them down as props to its
  Client Component — reuse that pattern rather than adding a
  `NEXT_PUBLIC_META_*` duplicate of anything above.

**F4 has shipped** (`channels-section.tsx`, see above): `src/app/dashboard/dev-whatsapp-connect-test/`
(the temporary, dev-only page/client-component pair that triggered Embedded
Signup with no i18n/design system) was deleted in full, per its own

- `src/app/api/companies/[companyId]/whatsapp/manual-connect-test/`

  different tests can pick a failure mode without shared server state.

### Internationalization (EN/PT)

`next-intl`, cookie-based with **no `[locale]` URL segment** — deliberately, to avoid restructuring every `redirect()` call in `src/lib/auth/actions.ts`, the `proxy.ts` matcher, and every internal link (see decisions.md for why locale-prefixed routing was rejected). **The project rule — never hardcode a UI string, always add it to both message files — lives in [CLAUDE.md](../../CLAUDE.md#internationalization), not here; this section is how it's implemented, that one is what to do every time.**
- `src/i18n/request.ts` resolves the locale: an explicit `locale` cookie wins; otherwise it checks the `Accept-Language` header for a `pt` substring, defaulting to `en`. No cookie is written until the user actively picks a language via the switcher.
- `messages/en.json` / `messages/pt.json` — namespaced by area (`Auth`, `Landing`, `Dashboard`, `Marketplace`, `AgentDetail`, `MyAgents`, `Products`, `Settings`, `Teach`, `LanguageSwitcher`). `HireTeam` was retired when the inline hire card was replaced by the marketplace/detail flow; `Teach` survives (trimmed to just its section-level keys) since `business-info-section.tsx`/`policy-section.tsx`/`faq-section.tsx` still resolve their copy from it after moving under `dashboard/settings/`. Agent display names (e.g. "Malu") are DB data and are never translated, only the surrounding copy (ICU interpolation, e.g. `"Hire {name}"`). A nested namespace path works directly in both `getTranslations`/`useTranslations` (e.g. `useTranslations("Teach.shipping")`) — used so a reusable component (`PolicySection`) can resolve its own scoped strings from a `sectionKey` prop instead of the parent having to pass every translated string down individually.
- `src/components/language-switcher.tsx` — a plain `<select>`, rendered by each surface's own chrome (landing nav, login/sign-up top-right, dashboard sidebar's desktop rail and mobile bar) rather than one global instance in `src/app/layout.tsx`. It used to be a single copy wrapping every page from the root layout; that read as a stray floating row sitting above each surface's own header once surfaces (the landing page, the dashboard sidebar) started owning real chrome of their own, so it moved into each one instead — every pre-auth and post-auth surface still gets it, just placed by the surface that needs it. Calls the `setLocale` Server Action (`src/lib/i18n/actions.ts`, mirrors `logout`'s shape) which sets the cookie, then `router.refresh()`.
- Server Components use `getTranslations` (`next-intl/server`); Client Components use `useTranslations`. `getTranslations` also works inside Server Actions invoked via `<form action={...}>` (verified for `login`/`signUp`'s error messages) — both are still ordinary requests carrying the same cookies/headers `getRequestConfig` reads from.
- Because locale resolution reads cookies/headers on every request, the app can no longer statically prerender any page (`next build`'s route list now shows everything as `ƒ` dynamic) — an expected, accepted tradeoff of request-time locale detection, not a regression to chase.
- `next.config.ts` is wrapped with `createNextIntlPlugin()`, required by the library regardless of routing mode.

### Product catalog API (Trello B3)

Route Handlers under `src/app/api/companies/[companyId]/products/`, following A3/B1's shape (explicit `requireMember` check for a clean 403, file-local, duplicated per file rather than shared):
- `GET /api/companies/[companyId]/products` — list. Excludes soft-deleted (`is_active = false`) products by default; pass `?includeInactive=true` to include them.
- `POST /api/companies/[companyId]/products` — create. `name` is required; `price`/`currency` must travel together (a price with no currency is rejected, a currency alone is allowed). All other columns (`external_id`, `sku`, `description`, `image_url`, `product_url`, `category`, `variants`, `attributes`, `metadata`) are optional passthrough.
- `PATCH /api/companies/[companyId]/products/[productId]` — partial update (only fields present in the body change). The price/currency rule is validated against the **effective merged state**, not just the fields in the request — e.g. sending only `{ currency: null }` on a product that already has a `price` is rejected, since the resulting row would have a price with no currency. `is_active` can be set directly here too (e.g. to reactivate a soft-deleted product).
- `DELETE /api/companies/[companyId]/products/[productId]` — soft-delete (`is_active = false`), never a hard `DELETE`, per the card's explicit request to preserve rows that `events.product_id` may reference. Idempotent: deleting an already-inactive product just re-applies `is_active = false`, no error.
- Both `[productId]` handlers first look up the product by `id` **and** `company_id` together, returning `404` if it doesn't exist or belongs to a different company — same "caller-supplied identifier, so a miss is a client error" reasoning as B1's `agentSlug` 404.
- No schema changes needed — the `products` table and its RLS policies already existed from the initial MVP schema migration (`20260823204115_create_products_table`).

### Product import (Trello B4)

`POST /api/companies/[companyId]/products/import` — `multipart/form-data` bulk upload (CSV or XLSX), spec §12's upload → parse → validate → report invalid rows → import valid rows flow. Same `requireMember` bar as the rest of the products routes (member, not admin).

- **Parsing libraries: `csv-parse` + `exceljs`, not the single-package `xlsx` (SheetJS)** — SheetJS's npm-published version is stuck on an old release with known prototype-pollution/ReDoS CVEs (their own docs now point people at their CDN instead of npm for the patched build). Since this endpoint's entire job is processing arbitrary uploaded files, that off-registry install source wasn't worth it; `csv-parse`/`exceljs` are actively maintained, npm-registry-published, and each narrower in scope. `exceljs` pulls in `uuid@8.3.2`, which `npm audit` flags (moderate) — accepted as-is rather than force-downgrading `exceljs` to an older release, since the vulnerable `uuid` code path (an explicit `buf` argument to v3/v5/v6) isn't exercised by read-only XLSX parsing.
- **Limits**: 5MB max file size, 2,000 max data rows, both checked before parsing and both a clean `400` if exceeded (re-check once a hosting provider is chosen). A parse failure (corrupt/non-matching file) is a `400` with a clear message, never a `500`.
- **Row mapping/validation reuses B3's rules, not a copy**: `validatePriceCurrency` (in `products/route.ts`) is `export`ed and imported here rather than duplicated a third time. `stock` gets its own `validateStock` (see below) — exported from `products/route.ts` too, but `products/[productId]/route.ts` keeps its own local copy rather than importing, matching that file's existing precedent of duplicating `validatePriceCurrency` rather than sharing it (deliberate per-route-file duplication, not an oversight).
- Column names map onto B3's fields with one rename: spec's `image` column → `image_url`. `variants` is expected to be a JSON string per cell (e.g. `[{"color":"red"}]`); invalid JSON is a per-row validation failure, not a parse-time one.
- Row numbers in the response (`skipped: [{ row, reason }]`) are 1-indexed positions among parsed data rows (blank rows are skipped for both formats) — not a literal spreadsheet line number.
- Valid rows are inserted in one bulk `supabase.from("products").insert([...])` call, not looped one-by-one — atomic, and RLS's `is_company_member` check has no chicken-and-egg problem since membership is confirmed before any row is built. The response is `200` even when some/all rows are invalid (expected outcome, not a request failure) — only structural problems (bad file, over a limit, unparseable) are `400`.

`stock` (migration `20260826135937_add_stock_to_products`): `integer`, nullable, no default, no `CHECK` — `null` means "not tracked," `0` means "out of stock," same app-layer-only validation style as `price` (`validateStock`, mirrors `validatePriceCurrency`'s pattern). Added to `OPTIONAL_PASSTHROUGH_FIELDS` in both B3 product routes so it's readable/writable through the regular single-product API too, not just the import path.


### Product search (Trello B5)

`src/lib/products/repository.ts` — `ProductRepository` (`search(params, supabaseClient?)`, `get(companyId, productId, supabaseClient?)`), the spec §12 abstraction the Agent Engine's (C1) `search_products`/`get_product` tools call directly, in-process.

- **Uses the service-role client (`createServiceClient()`) by default, not the RLS-scoped one** — its real caller is an inbound WhatsApp message with no authenticated merchant Supabase session, so B3's regular-client-plus-RLS approach doesn't apply here. `company_id` and `is_active = true` are filtered explicitly in application code instead. Any future caller must always pass a trusted `companyId`, never one taken from an unauthenticated party.
- **`supabaseClient` is an optional injectable override** (added while building C1): both functions build their own `createServiceClient()` only when the caller doesn't pass one. Found the hard way — C1's tool wrappers were passing `ctx.supabase` around without this param existing, so in Vitest's own process (which never has `SUPABASE_SERVICE_ROLE_KEY` pointed at the local test stack — only the spawned `next dev` process does, see Testing below) `createServiceClient()` blew up with `supabaseUrl is required`. Any future caller that wants full dependency injection (tests, or a different backend) must be able to pass its own client through this same param — don't reintroduce a hardcoded `createServiceClient()` call anywhere in this module.
- `search` (**rewritten 2026-08-27** — see that date's decisions.md entries; the `ilike`/JS-ranking version below is history, not current behavior): filters on `category` (exact), `priceMin`/`priceMax` (`gte`/`lte`), `attributes` (jsonb containment), and `keywords`/`text` (merged into one list) via a Postgres function, `public.search_products` (migration `20260827180000_add_product_search_ranking`), called through `.rpc()`. That function does real full-text search (`search_vector` generated column, `to_tsvector('portuguese', ...)`, `name` weighted above `description` via `setweight`) — a product matches if it matches **any** keyword (OR across keywords; a multi-word keyword still requires all its own words together, via `websearch_to_tsquery`'s space-is-AND syntax), ranked by `ts_rank` plus a small (`*0.1`) `pg_trgm` similarity tie-breaker. Ranking/matching/limiting all happen in Postgres now — no JS-side candidate pool or sort. EXECUTE on the function is revoked from `anon`/`authenticated` (service-role only), since it takes `company_id` as a plain parameter with no membership check of its own, same trust model as everything else in this module.
  - Superseded an original plain-`ilike` implementation (single literal-phrase substring match) that had a real bug: a query only matched if its exact word sequence appeared verbatim in `name` or `description` — found by hand-testing Malu (a real product was invisible to a completely reasonable customer search). An intermediate tokenized-`ilike` fix (every word required, either field) shipped first, then was itself replaced by the full-text rewrite described above.
  - **`category` is part of `search_vector`** (migration `20260829120000_index_product_category_in_search_vector`, weight `C` so a name match still outranks a shared category). Found by hand-testing: a merchant asked for "camisa de futebol" and was told the store had none, while the shirt was sitting there categorised `Futebol` — the word appeared in no name or description, and the `p_category` filter param couldn't help because it demands an exact case-sensitive value the model is explicitly told never to guess. Merchant-curated structured data was simply invisible to keyword search. Changing a generated column means drop + re-add; the GIN index goes with it and is recreated.
  - **Zero-result relaxation** (`withUnmatchableWordsDropped`): when the strict pass returns nothing, each distinct word is probed once (in parallel, `limit 1`, same category/price filters), any word with no match anywhere in the catalog is dropped, and the search is re-run with the survivors **still ANDed**. Fixes the other half of the same bug — "camisa de time" becomes `'camis' & 'tim'`, and one word the catalog has never heard of killed the whole query even though "camisa" alone found the shirt. Deliberately **not** a widening to OR-of-words: that would answer "camiseta azul masculina" with a "Calça Azul" on the strength of one unrelated word, which is exactly the irrelevance the full-text rewrite existed to remove. A word the catalog doesn't know carries no information, so dropping it costs no precision. Runs only on the empty path, so it can never dilute a search that was already working.
  - Full-text (token-based) matching is also strictly more precise than the old `ilike` substring approach: `to_tsvector` won't match "azul" inside "Azulejo" (different lexemes), where `ilike '%azul%'` would have false-positived on it.
- **Hybrid search — semantic leg via pgvector (2026-08-29, migration `20260829150000_add_product_embeddings`)**: found by hand-testing that lexical matching has a hard ceiling — a merchant's category "Vestimentas" and a customer's "roupa" share no lexeme at all, and no amount of keyword expansion or word-dropping closes that gap, since `to_tsvector` compares stems, not meaning. `products.embedding vector(1536)` (from `text-embedding-3-small`, `src/lib/products/embeddings.ts`) stores a real semantic representation per product; `search_products` now fuses the lexical leg (`search_vector`, unchanged) with a semantic leg (`embedding <=> p_query_embedding`, HNSW-indexed cosine distance) via **Reciprocal Rank Fusion (RRF)** — each leg contributes `1/(60+rank)`, so a product ranked well by either leg rises, and one ranked well by both rises further, with no scale-calibration problem between `ts_rank` and cosine distance. Each leg draws its own top-50 candidate pool independently (a product can appear via the vector leg alone, with zero lexical match) — this is what lets a customer's "camisa de time" or "algo pra usar no estádio" find a product whose only textual trace is `category: "Esporte"`.
  - **`embedding` is a plain nullable column, not generated like `search_vector`** — computing it needs a real OpenAI call, which a generated column's pure DB-side expression can't make. `null` means "not embedded yet" and the row simply falls back to lexical-only ranking for that leg; never an error, never blocks anything.
  - **Generated at write time, not by a backfill-only job** (`src/lib/products/embeddings.ts`, wired into all three write paths: `POST`/`PATCH /products/[productId]`/the B4 import route) — chosen specifically to avoid the staleness problem a CSV-snapshot or backfill-only approach would reintroduce (see decisions.md). `PATCH` only regenerates when `name`/`description`/`category` actually changed, using the *effective* (post-update) value the same way price/currency validation does. Import batches the whole file into one `embeddings.create` call (`createProductEmbeddingsBatch`) instead of one per row. **Never blocks a write**: a failure (network, rate limit, or the test-env kill switch below) returns `null` and the product still saves — logged via `console.error` so a real outage stays visible.
  - **`DISABLE_PRODUCT_EMBEDDINGS=true`** (checked inside `embeddings.ts` itself, set only in `tests/integration/global-setup.ts`'s spawned test process) keeps the ~60 product-create call sites across the integration suite from making real OpenAI network calls — every write still succeeds with `embedding: null`, exercising the same degrade-gracefully path a real outage would. Hybrid *ranking* itself is tested by writing a fabricated vector directly (`tests/integration/product-search-hybrid.test.ts`, imports `ProductRepository` in-process — same justified HTTP deviation as `agent-engine.test.ts`, since no route accepts a raw 1536-float query embedding as customer input), never by waiting on a real embedding.
  - **`ProductRepository.search`'s new `openaiClient?` param is deliberately NOT defaulted** to `createOpenAIClient()` the way `supabaseClient?` defaults to `createServiceClient()` — that default is a free local Postgres call, safe to default; silently defaulting the OpenAI one would mean every untouched caller (starting with `product-search.test.ts`'s plain HTTP route, which has no per-test DI seam) starts making real, paid API calls it never asked for. Only the Agent Engine's `search_products` tool passes one, via a new `ctx.openai` field on `ToolExecutionContext` (the same client `run()` already uses for the Responses/Conversations API — no separate credential). One embedding is generated per search call from the *combined* keyword set (not one per keyword) and reused unchanged if the existing lexical zero-result relaxation (word-dropping) has to retry — dropping a dead lexical word doesn't change what the customer meant.
  - **`PRODUCT_PUBLIC_COLUMNS`** (`src/lib/products/columns.ts`) is now the explicit column list every product-returning `select()` in the codebase uses instead of `"*"` — `embedding` (1536 floats/row) and `search_vector` would otherwise leak into every JSON API response and RSC payload for zero benefit (the browser has no use for either), balloon the B4 bulk-import response, and feed spurious digits into `grounding.ts`'s number-collection walk if a raw product row ever reached a tool result. Fixed across `ProductRepository.get`, both product CRUD routes, the import route, and the dashboard product list page (`search_vector` had already been silently leaking this way since the 2026-08-27 full-text migration — not a new bug, just fixed in the same pass).
  - **One-off backfill**: `scripts/backfill-product-embeddings.mjs` (`npm run backfill:product-embeddings`) embeds every active product with `embedding is null`, in batches. Plain `.mjs` (no TS path aliases) since this repo has no ts-node/tsx runner — a one-off script isn't worth adding one for; its embedding-text logic must be kept in sync with `embeddings.ts` by hand if either changes. Safe to re-run (only ever selects null rows). Already run once against the real project's 28 products.
- `get`: also enforces `is_active = true` — a soft-deleted product must never be recommendable by direct id either, e.g. if it was mentioned earlier in a conversation and the merchant later delisted it.
- `src/app/api/companies/[companyId]/products/search/route.ts` — a thin `GET` wrapper, added only so the repository could be validated over real HTTP before C1's in-process test harness (`tests/integration/helpers/service-client.ts`) existed — see `tests/integration/product-search.test.ts`. **Not** what the Agent Engine calls (it uses `ProductRepository` directly in-process). Because `ProductRepository` bypasses RLS, this route enforces company membership itself first (same reasoning as D1's service-client routes) before delegating. `?productId=` short-circuits to `.get()` (wrapped as a 0/1-element list); otherwise it runs `.search()` over `text`/`keywords` (repeatable query param, OR semantics — added alongside the rewrite above)/`category`/`priceMin`/`priceMax`/`attributes` (JSON-encoded)/`limit` query params.

### Agent Engine (Trello C1)

`src/lib/agent-engine/` — the orchestration shell from spec §17 ("what turns an LLM call into Malu"), implementing the 11-step pipeline. **No caller exists yet** (D2, the WhatsApp inbound webhook, isn't built) — this is a plain importable module, `AgentEngine.run({ companyId, conversationId, message }, deps?)`, not shaped around any webhook payload. The pipeline only starts once a `conversations` row already exists; finding/creating that row (which customer, which channel) is future D2 routing logic, not this module's job. Every dependency (`supabase`, `openai`, `model`, `tools`, `maxToolIterations`) is injectable via `deps` and defaults to the real production implementation — this is what lets tests fake the OpenAI client without a mock server.

- **One file per step where it earns one** (`config.ts` step 1, `conversation.ts` step 2, `customer.ts` step 3, `knowledge.ts` step 4, `prompt.ts` step 7, `tool-loop.ts` steps 8+9), collapsed to one `stubs.ts` for steps 6/10 which are one-liners today.
- **Step 2 simplification**: the Responses API's `conversation` param carries prior-turn history server-side, so "load recent conversation history" reduces to "resolve or create `conversations.open_ai_conversation_id`" (`resolveOpenAiConversationId`, create-once-and-persist) — no manual message replay needed. `instructions` (system prompt) is passed fresh per call and is never part of persisted conversation state.
- **Step 4** (`knowledge.ts`) — **rewritten by C3** (was a real stub: a full unfiltered read of the `companies` row injected into every prompt call). Now loads only `businessName`, kept directly in the prompt since it's cheap and always relevant; every other `companies` field (description, contact, industry, shipping/return/payment policy, FAQ) moved to on-demand tool calls (`get_business_information`/`get_policy_information`, below) instead of being force-fed into context regardless of relevance.
- **Step 5 ships as two real tools, not a stub** — `tools/search-products.ts`/`tools/get-product.ts` wrap B5's already-real `ProductRepository`, since its own file comment already names a mid-turn tool as its intended caller. This gives the tool-call contract (the ticket's actual deliverable) a genuine worked example instead of an invented one. Both wrappers pass `ctx.supabase` through as `ProductRepository`'s new optional `supabaseClient` param (see the B5 section above) — required for the injected test client to actually take effect instead of `ProductRepository` silently building its own.
  - `search_products`' `keywords` param (**2026-08-27** — see decisions.md) asks the model for 2-5 related terms per call instead of one literal phrase — costs no extra LLM round trip (same tool-call turn), and the schema description explicitly tells the model to expand a general category word (e.g. "calçado") into concrete product types (e.g. "tênis"/"sapato"/"sandália") rather than searching the category word itself, since catalog entries essentially never contain the abstract category term — found by hand-testing (Malu told a customer nothing matched "calçado" instead of trying more specific terms).
- **Two grounding tools added by Trello C3** — `tools/get-business-information.ts` (no args) and `tools/get-policy-information.ts` (`type: "shipping" | "return" | "payment" | "faq"`), both thin wrappers around a new `src/lib/companies/repository.ts` (`CompanyRepository`), mirroring B5's `ProductRepository` shape/DI pattern exactly (optional injectable `supabaseClient`, defaults to the service-role client). Implements spec §18 ("the LLM must not be trusted to invent factual business information") by replacing knowledge.ts's old always-injected dump with retrieval Malu only pays for when actually needed. `getPolicyInformation` returns an explicit `{ type, available: boolean, content }` — `available` matters more here than on `getBusinessInformation`'s flat optional-field shape, since this resolves one specific yes/no request (per the card's explicit "never silently return null" requirement). FAQ is stored as `jsonb` (an array of `{question, answer}`); `CompanyRepository` formats it into plain Q/A text before it ever reaches the model, so every policy type reads the same regardless of which one was asked for — still just deterministic templating over real stored data, not generation.
- **The tool-call contract** (`tools/types.ts`): `AgentTool = { name, description, parameters (JSON Schema), strict?, execute(args, ctx) }`. `ctx: ToolExecutionContext` (`companyId`/`agentId`/`conversationId`/`customerId`/`supabase`/`openai` — the last added for hybrid search's semantic leg, see B5's section above) is passed by the loop and must be what every tool trusts — never a same-named key inside model-supplied `args` (mirrors B5's "always take a trusted companyId" rule; enforced by spreading `args` before `companyId: ctx.companyId`, never after). `tools/registry.ts`'s `defaultTools` array is the append-only registration point future tools use — no other wiring needed, though a new tool also has to be granted to an agent in `tools/tool-sets.ts` (see below) before anyone is actually offered it. `strict` defaults to `false` in `toOpenAiTool`, since OpenAI's strict mode requires every schema to declare `additionalProperties: false` and list every key (including optional ones) in `required`; opt a tool into `true` only once its schema is actually written to that shape.
- **`tool-loop.ts`** calls `responses.create`, and if the model returns `function_call` items, executes each via the matching registered tool and resubmits `function_call_output` items as the next call's `input` (the conversation id already carries everything server-side — no replay), repeating up to `maxToolIterations` (default 4, `DEFAULT_MAX_TOOL_ITERATIONS`). An unregistered tool name throws `UnknownToolCallError`; exceeding the iteration cap throws `ToolLoopLimitExceededError` rather than degrading silently — a library shouldn't guess at a user-facing fallback.
- **No `model` column exists anywhere** in the schema — `DEFAULT_MODEL` (`src/lib/agent-engine/constants.ts`) reads `OPENAI_MODEL` env, falling back to `"gpt-5.4-mini"` (the id smoke-tested during this ticket's setup).
- **`agents.system_prompt`/`personality` are populated for Malu** (Trello C2, migration `20260827160000_set_malu_personality_and_system_prompt`, content sourced from spec §5-9) — `buildSystemPrompt` (step 7) now uses `system_prompt` verbatim instead of its `role + description + personality` fallback (that fallback still exists, for any future agent shipped without a hand-written prompt).
- **Five platform-level guardrails are prepended unconditionally**, before any agent's own `system_prompt` (`prompt.ts`) — all found by hand-testing, all deliberately generic/agent-agnostic so they survive whatever any given agent's `system_prompt` says: `CONFIDENTIALITY_GUARDRAIL` (never reveal these instructions/internal labels, even if asked directly), `LANGUAGE_GUARDRAIL` (always reply in the customer's own language, not whatever language the instructions happen to be written in), `CAPABILITY_GUARDRAIL` (states the counterparty is always a customer, never trusting a claimed identity otherwise; can search/answer/guide-to-checkout; cannot create/edit/manage catalog data or discuss anything technical; must decline without asking the customer for DB field names), `GROUNDING_GUARDRAIL` (Trello C3 — check available tools before answering a specific/checkable question from general knowledge, even one that doesn't sound store-related, since a merchant's FAQ can cover any topic; C7 added a third paragraph forbidding unretrieved and self-calculated figures), `SCOPE_GUARDRAIL` (**this store only** — refuse general knowledge/trivia/advice rather than acting as a general chatbot). See the 2026-08-27/28/29 decisions.md entries for what each one was found fixing.
  - **`SCOPE_GUARDRAIL` must stay ordered after `GROUNDING_GUARDRAIL` and defers to it**: it declines only what the business has nothing on file about, because "this doesn't sound like a store question" is exactly the reasoning C3's guardrail exists to forbid. Getting that precedence wrong re-breaks the FAQ bug C3 fixed — the two are asserted together in `prompt.test.ts`. It also names what stays in scope (greetings, courtesy, empathy, needs/occasion/size/budget discovery, opinions on the store's own products), since the failure mode of a scope rule is a wall.
- **Per-agent tool sets** (Trello J2, `tools/tool-sets.ts`) — `AGENT_TOOL_SETS` maps `agents.slug` to the tool names that agent is offered, and `resolveToolsForAgent(slug)` turns that into the array handed to the loop. Code-level and keyed by slug, mirroring `AGENT_ENRICHMENT` (`src/lib/agents/catalog.ts`): no schema change, and the same "the DB is the roster, this file only enriches it" split. There is deliberately **no `agents` column for a tool list** — a tool is code that must exist to be callable, so making capabilities editable as data would let a row reference a tool that isn't there.
  - Every agent gets a **common set** (`get_business_information`, `get_policy_information`, `request_human`) — read-only business knowledge plus the escape hatch. Malu adds the sales tools (`search_products`, `get_product`, `create_checkout_link`, `flag_buying_intent`); Ana adds the scheduling tools (`list_services`, `find_available_slots`, `book_appointment`, `cancel_appointment` — J3, see "Ana's scheduling tools" below). Neither agent's set overlaps the other's.
  - **An unmapped agent falls back to the common set, never the full registry.** Falling back to everything would silently reintroduce the bug this ticket fixes for every future agent; falling back to the common set fails visibly instead ("she won't book anything") and is cheap to fix by adding an entry. Note `john` — hand-inserted into the remote DB, seeded by no migration — is unmapped and therefore lost the sales tools he was previously offered by default.
  - **A tool name with no matching registered tool throws `UnknownToolNameError`** rather than being skipped: a typo would otherwise silently strip a capability, which is close to invisible in an LLM product. `tests/unit/agent-engine/tools/tool-sets.test.ts` pins every entry against the real registry so it can't reach production.
  - **`deps.tools` still overrides everything** — the slug filter is only the default. That's what keeps every existing test able to drive the loop with fake single-purpose tools.
- **`company_agents.status` (paused) is loaded but not enforced** — `loadAgentConfig` returns it; deciding whether to invoke the engine at all for a paused agent is left to the future caller (D2). Not an oversight — flagged explicitly in the C1 plan.
- **`determineIntent` (step 6) has no owning future ticket** among C3/C4/C5/C7 as of this writing — ships as a stable placeholder (`"unknown"`), a real gap worth resolving during backlog grooming, not a design decision.
- `src/lib/openai/client.ts` — `createOpenAIClient()`, server-only factory mirroring `createServiceClient()`'s shape (no singleton). New env vars: `OPENAI_API_KEY`, `OPENAI_MODEL` (both server-only, see `.env.example`).

### Buying-intent detection (Trello C6)

- **A model-callable tool, not a keyword/regex classification pass** — deliberate, and the reason it isn't English-only: a purchase signal is phrased completely differently in every language ("quero esse", "me manda o link", "lo quiero", "I'll take it"), and any keyword list would only ever catch the language it was written in. No `tracking_id` (checkout-link only), no `metadata`, no dedup — a customer can legitimately signal intent more than once and E2 counts occurrences. No migration needed: A1's `event_type` enum already has `buying_intent` and the table's columns already match the card's suggested fields.

If it doesn't resolve (stale, wrong, or another tenant's), it's silently dropped and the row is written with `product_id: null` rather than failing the turn — the buying-intent signal is real regardless of a bad product reference.

Guidance lives in the tool description only (no `system_prompt` change) — matching how `create_checkout_link` / `get_policy_information` carry their own call/don't-call rules.

### Response grounding validation (Trello C7)

`src/lib/agent-engine/grounding.ts` — the Agent Engine's step 10, which shipped from C1 as a pass-through stub (`validateResponse`) specifically waiting for this ticket. Enforces spec §6/§18's "must never invent price/stock/policy/characteristics" and the "Ground" criterion from §27.

- **Approach (b) of the two the card offered** — record the facts a turn actually retrieved, then check the final text against them. Approach (a) ("make the model quote/template tool results") was rejected as being just another instruction, the same class of thing the prompt-level `GROUNDING_GUARDRAIL` already is and that hand-testing broke twice during C3. See decisions.md.
- **Only numeric price and stock claims are enforced** — the enforceable subset is exactly the facts with a canonical value in Postgres. A non-numeric policy/characteristic claim ("we accept returns", "it's cotton") is a semantic judgement no pattern check can make, and stays covered by the prompt guardrail alone. Documented rather than papered over.
- **Claim extraction is deliberately narrow**: a figure only counts as a price if it carries a currency symbol/word or a price verb (`custa`, `sai por`, `costs`…), and as stock only next to a real stock word (`unidades`, `em estoque`, `left`…). "Encontrei 3 opções" is a result count, not a claim. URLs are stripped first (C4's checkout links and `product_url`s are full of digits) and percentages skipped (no discount is stored anywhere to check one against). Precision beats recall here: a false block replaces a good reply with "let me check that" in *every* conversation, while a miss just lands back on the prompt guardrail.
- **Number parsing is locale-agnostic** — `1.299,90` (pt-BR) and `1,299.90` (en) both resolve to the same value, compared as integer cents. The last separator is the decimal point unless followed by exactly three digits, which is genuinely ambiguous across those locales (`1.500`) and yields both readings.
- **Three grounding sources**, cheapest first: this turn's tool results (`runToolLoop` now returns `{ responseText, toolResults, messageItemIds }` instead of a bare string), the customer's own message (echoing back a budget they stated invents nothing), and — only if something is still unmatched — the company's **real current data** (active products' `price`/`stock` via a targeted `.in()`, plus the numbers in its policy/FAQ/description text).
- **That third source is the cross-turn backstop and the reason the check is usable at all**: OpenAI holds prior turns server-side, so a price retrieved two turns ago and simply restated now has no tool result in this process. Checking the live DB instead of caching a per-conversation fact ledger also means a **stale** price fails, correctly. Accepted limitation: it grounds a figure against the company's data as a whole, so quoting product A's real price while discussing product B still passes — not detectable without knowing which product a sentence is about.
- **A reply with no figures costs nothing** — zero queries, the overwhelmingly common case.
- **On failure: regenerate once, then fall back.** The retry runs the full tool loop again with a `developer`-role correction naming the exact rejected figure, so the usual outcome is Malu going and actually looking it up — a real answer in her own voice and language, not canned text. Only a second failure yields `UNGROUNDED_FALLBACK_TEXT` (`constants.ts`), overridable via `deps.ungroundedFallbackText`. That constant is the one string in the pipeline that can't honour `LANGUAGE_GUARDRAIL` (no model turn left to write it, nothing detects the customer's language) — PT, the MVP's launch language.
- **The rejected draft is deleted from the OpenAI conversation** (`discardConversationItems`, `conversation.ts`) before regenerating. Responses are created with `store: true`, so without this a blocked invented price stays in server-side history and gets quoted back next turn ("como eu te falei, R$ 199") — the block would leak across turns. Best-effort: the customer is already protected either way, so a failed cleanup must not fail the turn.
- **`GROUNDING_GUARDRAIL` gained a matching third paragraph** (never state an unretrieved figure; never state a total/sum/discount you calculated yourself). Prompt and enforcement have to agree — a self-computed total traces to no retrieved value, so the check blocks it, and without the prompt line the model would keep producing sums that keep getting rejected.
- **`AgentEngineResult.grounding`** (`{ status: "grounded" | "regenerated" | "blocked", violations }`) is returned so G1's QA pass — which exists to try to break this — can see it fire; `dev-chat-test` echoes it and flags interventions inline, since a successful block otherwise just looks like Malu being vague.
- Tests: `tests/unit/agent-engine/grounding.test.ts` (number formats, every claim pattern, the false-positive cases that matter — result counts, sizes, links, percentages — plus the customer-message source and the DB-error path), three cases in `tests/integration/agent-engine.test.ts` against real Postgres (invented price blocked with neither draft sent, regenerated retry accepted, real catalog price restated with no tool call this turn). `stubs.ts` is down to `determineIntent`.

### Checkout-click redirect (Trello E1)

`src/app/c/[trackingId]/route.ts` — the other half of C4's loop. A customer taps the link in WhatsApp; this resolves the tracking id, records the click, and forwards to the merchant's own page.

- **Public and unauthenticated by design** (the customer has no Sidde account and isn't in `auth.users`), so it uses the service-role client — `events` RLS is company-membership scoped and would deny both the lookup and the insert. The tracking id from the URL is the only untrusted input and is used purely as a lookup key: **every id written on the click row is copied from the minted row**, never from the request.
- **302, never 301.** A permanent redirect gets cached by the browser, so every click after the first would skip the server entirely and go straight to the merchant — silently losing the measurement this endpoint exists for. `cache-control: no-store` for the same reason at the proxy layer.
- **Inserts its own `checkout_click` row rather than mutating the minted one** (`events` is append-only). `tracking_id` is left **null** on the click row so the partial unique index never collides across repeat clicks; the id it belongs to travels in `metadata.tracking_id`. Each real tap is its own row.
- **Link-preview crawlers are redirected but not counted** (`isLinkPreviewAgent`, `src/lib/checkout/links.ts`). WhatsApp — the channel these links are *sent over* — fetches every URL in a message to build its preview card before a human touches it, so without this, every link Malu sends would immediately register a click. The matcher is deliberately conservative: an unrecognized agent counts as human, since a real click misread as a bot silently loses a data point.
- **A failed click insert never costs the customer their redirect** — they're mid-purchase; losing one analytics row is strictly better than a dead end. The error is logged and the redirect proceeds.
- **Unknown/expired ids get a friendly, localized, self-contained HTML 404**, not JSON or a stack trace — a real person tapped this. Localized via `resolveLocale()` (same Route-Handler pattern as the product import-template route), copy in the `CheckoutLink` i18n namespace. A DB error and an unknown id return the same page, so nothing leaks about what exists.
- **`src/proxy.ts` excludes `c/`** from its matcher: there's no session to refresh on a public link, so running `updateSession`'s `auth.getUser()` round-trip would add latency to every click for nothing.
- Nothing here records revenue, an order, or any completed-purchase signal — a click is a click, never a sale (spec §14/§15).
- Tests: `tests/unit/checkout/link-preview.test.ts`, and `tests/integration/checkout-redirect.test.ts` (over real HTTP, mint→tap→click→redirect end to end; covers repeat clicks, the preview-bot path, append-only preservation, and the unknown-id page).

### Analytics aggregation API (Trello E2)

`GET /api/companies/[companyId]/analytics` — the read side F6's dashboard consumes directly. Returns exactly the five metrics spec §15 names for the initial dashboard, each as `{ metric, total, series: [{ date, count }] }`:

- `conversations` / `customers` — counts from those tables. `product_recommendations` / `buying_intent` / `checkout_clicks` — `events` rows filtered by `type` (the response keys are spec §15's dashboard labels, not the raw enum values). Order in the `metrics` array is fixed to spec §15's listing order.
- **Query params** (all optional, all lenient-defaulted like the products list route — a bad value falls back, never 400s): `granularity` = `day` (default) | `week`; `from` / `to` = `YYYY-MM-DD` inclusive bounds. Defaults: `to` = today in the company's timezone, `from` = 30 days back (`day`) / 84 days back (`week`). The one hard error is `from` after `to` → `400`. An over-long span is **clamped** to `MAX_RANGE_DAYS` (370), not rejected.
- **Timezone-aware day boundaries.** Buckets follow `companies.timezone` (falls back to `UTC` if unset/invalid) so "today" on the dashboard is the merchant's today. The DB query runs in UTC widened by ±1 day; the pure aggregator re-filters each row to its real local calendar date. `week` buckets are keyed by the ISO-week Monday on/before the date.
- **Series are zero-filled** across the whole range so F6 can draw a continuous line; `total` is the sum of the series (single source of truth, no separate count query to drift from it).
- **Member-readable** (`requireMember`, matches the `is_company_member` SELECT policy on all three tables) — file-local check for a clean 403, same precedent as every sibling route. No admin gate.
- **No migration, no RPC.** Aggregation is plain JS over rows read through the RLS-scoped client; `route.ts` pages past PostgREST's 1000-row cap (`fetchWindow`) so a high-volume company isn't silently undercounted. If catalog/event volume ever makes the row scan a real cost, a `date_trunc` Postgres function is the upgrade path — not needed at MVP scale (same call as B3's `ilike`-over-FTS decision).
- **Pure core split out** to `src/lib/analytics/aggregate.ts` (`aggregateAnalytics`, plus `weekStart` / `bucketKeysInRange` helpers) — unit-tested without a DB, mirroring how B5's `ProductRepository` and C4's `checkout/links.ts` keep their pure logic out of the IO layer. The range-resolving + windowed-read half is `src/lib/analytics/load.ts` (`loadCompanyAnalytics`), **shared** by the route and F6's page (below) — added when F6 landed, so the route no longer inlines `fetchWindow`.
- Nothing here touches revenue or attribution — explicitly out of MVP scope per spec §15.
- Tests: `tests/unit/analytics/aggregate.test.ts` (bucketing, timezone shift, week grouping, event-type mapping, out-of-range drop), `tests/integration/analytics.test.ts` (real Postgres: non-member 403, empty-company zero series, per-type day counts scoped to the company, weekly grouping, `from > to` 400).

### Product management UI (Trello F3)

`src/app/dashboard/products/` — the merchant-facing screen for the catalog, following F1/F2's conventions (`page.tsx` Server Component fetches company/role/first-page directly via the server Supabase client; Client Components own their own save state; shared `src/components/ui/*` primitives; `Products` i18n namespace mirroring `Teach`'s nesting style).

- **`GET .../products` gained `category`/`search`/`page`/`pageSize`** (closing a gap B3's own card asked for but never built). `category` is exact-match; `search` is case-insensitive `ilike` on `name`; pagination is 1-indexed `page`/`pageSize` (default 20, max 100), lenient-defaulted on invalid input rather than `400`ing (same permissiveness as `includeInactive`'s string check). Response is now `{ products, total, page, pageSize }` — additive, nothing else called this endpoint before.
- **`canEdit` here means "any company member," not owner/admin** — deliberately different from Teach's `["owner","admin"].includes(role)` gate, because B3's product routes only ever call `requireMember`. Don't "fix" this to match Teach's stricter gate; it would invent a restriction the API doesn't enforce.
- **Edit opens in a dialog; Add and delete-confirm stay inline.** This app's first modal/dialog component (`src/components/ui/dialog.tsx`) was added after user feedback that editing a product inline inside its own table row was cramped. `ProductsManager` owns `editingId`, derives `editingProduct = products.find(p => p.id === editingId)`, and renders one shared `<Dialog>` wrapping the same `ProductForm` used for create — `ProductList`/`ProductRow` no longer embed a form at all, they just call `onEdit(id)`. "Add product" (a collapsible panel at the top of the page, not row-scoped) and the delete-confirm two-click flow deliberately were **not** moved into the dialog — only Edit was reported as cramped, and both of those already read fine as inline expand/confirm (the same idiom F2's `faq-section.tsx` established). `Dialog` is a real, reusable primitive now (portaled via `createPortal` to `document.body`, closes on Escape/backdrop-click/explicit ×, focuses the panel on open) — the next screen that needs a modal should reuse it, not build a second one.
- **Delete is "Deactivate," never "Delete"** — a two-click inline confirm (`Products.delete.deactivateButton` → `confirmButton` → commits the `DELETE` call), satisfying the ticket's "make clear this deactivates, not erases" requirement at the label level. After a successful deactivate, the row's `is_active` flips to `false` in local state immediately (shown muted, with an inline "Reactivate" `PATCH`) rather than vanishing — it naturally drops out on the next filtered re-fetch.
- **`variants`/`attributes` use a structured key→multiple-values editor** (`key-values-editor.tsx`'s `KeyValuesEditor`, shared by both fields in `product-form.tsx`) instead of a raw JSON textarea — a merchant adds an option name (e.g. "Color") and one or more chip-style values for it (e.g. "Blue", "Red"), producing `{ "Color": ["Blue", "Red"] }`. Replaced an earlier free-JSON-textarea version after user feedback that it wasn't merchant-friendly. `normalizeKeyValues()` (exported from the same file) tolerates any prior stored shape (a flat object, single-string values, or anything unrecognized normalizes to empty) so old/freeform data doesn't crash the editor — it just starts empty and gets overwritten on next save, acceptable since no real merchant data exists yet at this stage. This shape is independent of B4 import's own JSON-string-per-cell convention for CSV/XLSX — the two input paths write to the same freeform jsonb columns but aren't required to agree on internal shape.
- **`import-panel.tsx` is this app's first client-side file upload** — a real `<input type="file">` sits hidden (`className="hidden"`), triggered by a visible `Button` calling `fileInputRef.current?.click()`, with the chosen filename shown as separate text next to it. A native unstyled file input renders its own browser-chrome "Choose File" control that doesn't match this app's `Button` styling at all — this hidden-input-plus-trigger-button is the pattern any future file-upload UI in this app should copy, not a bare `<input type="file">`. The actual upload fetch deliberately sends **no `Content-Type` header** (the browser sets the multipart boundary itself), unlike every other fetch call in this app which sets `application/json`.
- **`Button` gained a `danger` variant** (`src/components/ui/button.tsx`) — bordered/red-toned like `secondary` but signals a destructive confirming click (used for the deactivate flow's actual "click again to confirm" button). `secondary` (not `ghost`) is now used for ordinary row actions like Edit/Deactivate too — `ghost` (text-only, no border/background) reads as plain text rather than a clickable control once it's sitting inline in a table row, so it's reserved for genuinely secondary/de-emphasized actions like the confirm-flow's Cancel.
- **`GET .../products/import-template`** (new, sibling to `import/route.ts`) — a downloadable starter CSV matching exactly the columns the import route expects, `requireMember`-gated. Header names are fixed English (the literal keys `mapAndValidateRow` reads) regardless of locale; only the two illustrative example rows are localized, via `resolveLocale()` (exported from `src/i18n/request.ts` — the same cookie/Accept-Language detection `getRequestConfig` itself uses, reused here since this is a Route Handler generating raw file content, not a page going through the `next-intl` message-bundle system). The example locale strings are plain TS objects in the route file, not `messages/*.json` entries — CLAUDE.md's "never hardcode a UI string" rule targets JSX/page copy; a generated file's illustrative example data was judged close enough to seed/fixture data (see `supabase/seed.sql`'s own precedent) not to need full message-bundle plumbing, while the *explanatory text around it* in `import-panel.tsx` (format description, hints) is real UI copy and does go through `Products.import.*` translation keys as usual.
- **Entry point**: reached via the sidebar's Products tab (see "Onboarding & admin shell" above), not a dashboard checklist card — F3 originally shipped a `LinkStepCard` on the old single-page checklist dashboard, but that whole page was replaced by the marketplace/my-team/products/settings shell before this branch merged; the checklist/step-counting mechanism no longer exists anywhere in the app.
- Product `price`/`stock` come back from Postgres as `string`/`number` — `price` specifically as a numeric string (e.g. `"25.50"`), always run through `Number()` before formatting or arithmetic, never compared/concatenated raw.
- **`Input`/`Select`/`Textarea` now set `w-full min-w-0`** on their actual form-control element (they didn't before) — surfaced as horizontal scrolling inside the new edit dialog: three fields in a `flex-row` group (price/currency/stock, etc.) each rendered at the browser's default intrinsic input width instead of sharing the row, overflowing a narrow container. It was latent on every other page too (just invisible there, since a wide page has room to spare), so the fix is in the shared primitives, not a dialog-specific patch. **Passing `className="flex-1"` (or similar) to `Input` only reaches the inner `<input>`, not the wrapper `<div>` those components render around label+field — that wrapper is the actual flex item.** To let a field share/shrink in a flex row, wrap the whole `Input`/`Select` call in `<div className="min-w-0 flex-1">...</div>` at the call site (see `product-form.tsx`'s price/currency/stock row and `key-values-editor.tsx`'s value-input row) — a flex item's default `min-width: auto` otherwise refuses to shrink below its content's natural size regardless of what width class lands on a descendant.

#### Services catalog (K1)

- **No `PRODUCT_PUBLIC_COLUMNS` equivalent is needed.** `products` has `embedding`/`search_vector` columns that must be kept out of `select`; `services` has neither, so `select("*")` is already safe here. Don't add a column allowlist "for symmetry" — it would be dead weight.

So blank in the UI normalizes to `0` before the request, not `null`. The list only renders the buffer line when it's `> 0`.

If Products is ever touched again, it should be brought in line rather than the drift being copied forward.
- Service `price` comes back from Postgres as a numeric **string** (same as products) — always `Number()` it before formatting.
- **Verifying a dashboard page by fetching its HTML is a trap:** `next-intl` serializes the whole message namespace into the RSC payload, so grepping raw HTML for a label finds strings that are *not* rendered (it briefly looked like the read-only banner was showing for an owner). Strip `<script>` blocks before asserting anything about what the page actually displays.

#### Appointments view (K4)

- **H3's list endpoint was extended here**, the way F3 extended B3's for the same reason — the shipped shape couldn't render a readable screen. `GET .../appointments` now embeds `services(name)` and `customers(name, phone)` (both to-one, so PostgREST returns an object or `null` — `service_id` is nullable and survives a service being soft-deleted, which the UI shows as "Service removed"), and accepts `?order=desc`. Both are covered by integration tests in `appointments.test.ts`; the UI itself has none, per this project's no-frontend-tests rule.
- **`?order=desc` exists because "past bookings" reads latest-first.** Only the literal string `desc` flips it, so a typo can't silently invert a merchant's upcoming list.
- **"Upcoming" vs "past" is one endpoint with the `starts_at` window flipped** (`from=now` / `to=now`), not two code paths.
- **Times render in the *company's* timezone, not the viewer's** — a booking is an event at the business. Uses the same `company.timezone && isValidTimeZone(...) ? ... : "UTC"` fallback as `availability/load.ts` and `analytics/load.ts`. Passing an explicit `timeZone` to `Intl.DateTimeFormat` also keeps server and client output identical, so this can't hydrate-mismatch — **don't** switch it to the browser default.
- **Actions are `completed` / `no_show` / `cancelled`, all plain `PATCH { status }`.** Approve/decline on `requested` rows is deliberately absent — that's K7, which also has to record a `cancellation_reason` on decline. Cancel *is* offered on `requested` because it's the same plain status change every other row gets.
- **A status change re-fetches rather than patching local state**, since the changed row may no longer match the active filter (cancel something while filtered to "confirmed" and an in-place patch would keep displaying it).
- Terminal statuses (`cancelled`/`completed`/`no_show`) render muted with no actions. Google Calendar sync is H3/I3's business and fires inside the route — the UI never touches it.

- **Never export a plain value from a `"use client"` module and import it into a Server Component.** `APPOINTMENT_SELECT` originally lived in `appointments-manager.tsx`; Next turns client-module exports into *client reference proxies*, so the page handed supabase-js a proxy and died at request time with `(intermediate value).split is not a function` inside `.select()`. Types line up and `next build` passes — it only fails when the page is actually requested. Shared constants/types now live in `appointment-types.ts`, which deliberately has no `"use client"` directive.

### Scheduling foundations — services, business hours, appointments (Trello H1–H3)

The first slice of the "Ana" scheduling agent epic (H–L): pure backend/schema, no UI yet (that's K-epic). Deliberately shaped to mirror B3's products routes wherever the domain allows, so H1's ticket text ("mirror the products CRUD conventions") holds literally, not just in spirit.

- **`services`** (migration `20260829193910`) — a company's bookable offerings: `name`, `description`, `duration_minutes` (required, positive integer), `buffer_minutes` (default `0`, cleanup/travel time appended after the slot), `price`/`currency` (same pair-or-neither rule as products), `category`, `is_active`. `src/app/api/companies/[companyId]/services/` — GET (list, `includeInactive`/`category`/`search`/pagination) + POST, and `.../[serviceId]/` — PATCH (partial, effective-merged-state price/currency validation) + DELETE (soft-delete via `is_active=false`). Copies `products/route.ts` field-for-field (same `requireMember`, same validation style, file-local and duplicated per this repo's convention) minus embeddings — a service has no search-relevance use case the way a product catalog does.
- **`business_hours`** (migration `20260829193919`) — a recurring **weekly template**, not calendar-specific dates: `day_of_week` (`smallint`, `CHECK 0-6` — convention is `0 = Sunday`, matching `Date.getUTCDay()`/Postgres's `EXTRACT(dow FROM ...)`, made explicit by I2 which is the first code to actually resolve a calendar date against this column), `start_time`/`end_time` (`time`, `CHECK end_time > start_time`), `is_active`. `UNIQUE(company_id, day_of_week, start_time)` allows split shifts (e.g. 9-12 and 14-18 on the same day) as two rows rather than one row with a gap. `GET`/`PUT /api/companies/[companyId]/business-hours` — `PUT` is **whole-array-replace** (delete-then-insert, same "replace the whole set" semantics as F2's FAQ section), not a diff/merge; sending `[]` clears the company's hours entirely. **No holiday/exception table** — deliberately out of scope for H2: a day blocked off in the merchant's connected Google Calendar (J-epic, not built yet) is already "busy" from that calendar's own free/busy data, so a parallel exceptions table would just be a second, easier-to-desync source of the same fact.
- **`companies.requires_appointment_approval`** (migration `20260829193925`, `boolean not null default false`) — the merchant's manual-approval-vs-auto-confirm setting from the roadmap's resolved open question. A flat column on `companies`, matching `timezone`/`currency`/`industry`'s existing style, updated through the **existing** B2 `PATCH /api/companies/[companyId]` route (added as a new field block there) rather than a new endpoint — same "respect current structure" reasoning as B2's other settings.
- **`appointments`** (migration `20260829193937`) — `service_id` (nullable, `on delete set null` — a deleted service shouldn't retroactively invalidate a past booking), `customer_id` (required, `on delete cascade`), `conversation_id`/`agent_id` (nullable, for bookings Ana makes mid-conversation vs. ones created directly via this API), `status` (new enum `appointment_status`: `requested`/`confirmed`/`cancelled`/`completed`/`no_show`), `starts_at`/`ends_at` (`timestamptz`, `CHECK ends_at > starts_at`), `google_event_id` (nullable, for J-epic's future Calendar sync), `notes`, `cancellation_reason`.
  - **`ends_at` bakes in the service's `buffer_minutes`, not just `duration_minutes`** — computed server-side as `starts_at + (duration_minutes + buffer_minutes) minutes`, both on create and on reschedule, never trusted from the client. This means the calendar/overlap-prevention constraint below reserves the buffer too, and any future display UI (K4) that shows the customer-visible appointment window must subtract `buffer_minutes` back out of `ends_at` rather than showing it raw.
  - **Double-booking is prevented at the database level**, not just in application code: `exclude using gist (company_id with =, tstzrange(starts_at, ends_at, '[)') with &&) where (status not in ('cancelled', 'no_show'))`, requiring `btree_gist` (enabled in the same migration). This is robust against races that an app-layer "check then insert" can't be (two concurrent bookings for the same slot). A violation raises Postgres error code `23P01`, caught in both the POST and PATCH (reschedule) route handlers and translated to a clean `409 { error: "This time overlaps with an existing appointment" }` instead of a raw DB error.
  - **`status` is server-computed on create**, never client-supplied: `"requested"` if the company's `requires_appointment_approval` is `true`, else `"confirmed"` — the client can't self-approve a booking by just sending `status: "confirmed"` in the POST body.
  - `src/app/api/companies/[companyId]/appointments/` — GET (filters: `status`, `from`/`to` on `starts_at`, pagination; default order `starts_at ascending`, soonest-first — unlike products' `created_at desc`, since an appointments list is inherently a schedule) + POST. `.../[appointmentId]/` — PATCH (status transitions, `notes`, `cancellation_reason`, and **reschedule**: changing `starts_at` and/or `service_id` recomputes `ends_at` server-side the same way creation does) + DELETE (quick soft-cancel, `status='cancelled'`, idempotent — never a hard delete, so the exclusion constraint's slot-freeing behavior and any future audit trail both stay intact).
- No customers CRUD API exists yet (out of scope for H1-H3) — tests that need a customer row insert one directly via the signed-up test user's own RLS-scoped client, the same workaround pattern used wherever a table has no HTTP surface yet.

### Google Calendar connect flow (Trello I1)

`company_calendar_connections` (migration `20260829201627`) + `src/app/api/companies/[companyId]/calendar/` — the schema and server-side OAuth token exchange that I2 (availability engine) and J-epic (Ana's booking tools) build on. Structurally a close copy of D1's WhatsApp Embedded Signup flow — same shape, different provider, because that's what lets K2's future "Connect Google Calendar" button be a straight copy of `channels-section.tsx`'s existing pattern (load a vendor JS SDK, trigger a popup, POST the result to a connect route).

- **The consent flow is JS-driven, not a server-side redirect.** K2 (not built yet) will load Google Identity Services and call `google.accounts.oauth2.initCodeClient({ ux_mode: 'popup', ... })` — Google's own equivalent of Meta's Embedded Signup popup — which hands the browser a short-lived authorization `code` directly via a JS callback, no page navigation. That code gets POSTed to `.../calendar/connect`, exactly like D1's `{ code, phoneNumberId, wabaId }` POST. This means there is **no registered callback URL and no server-side redirect route** — `src/lib/google-calendar/oauth.ts`'s `exchangeCodeForToken` passes the literal string `"postmessage"` as `redirect_uri` on the token exchange, which is Google's documented required value for this exact popup-code-client flow (not a real URL).
- **Both `access_token` and `refresh_token` are column-privilege-locked** (unlike D1, which only locked `access_token` — WhatsApp has no refresh token). Same revoke-table-wide-then-regrant-by-name technique as migration `20260826104820`, just naming every column except both. Only `src/lib/supabase/service.ts`'s service-role client can read or write either.
- **`google_calendar_id` is hard-coded to `'primary'`** at connect time — Google's real special calendar-id alias for "the account's default calendar," not a placeholder. No calendar-picker UI exists or is planned; matches the already-resolved "single calendar per company for MVP" product decision.
- **Scope is the single, full `https://www.googleapis.com/auth/calendar`**, not a narrower `readonly`/`freebusy` scope — I2 only needs freebusy today, but J-epic's future `book_appointment` tool will need to create real events on the connected calendar (`appointments.google_event_id`, from H3, already anticipates this), and deciding the scope once now avoids a forced later re-consent.
- **`refresh_token` is retained across reconnects, never overwritten with `null`.** Google only includes `refresh_token` in the token response on the very first consent, or when the client forces `prompt=consent` (K2's trigger always will) — an ordinary reconnect can legitimately omit it. The connect route reads any existing stored `refresh_token` via the service client before the token exchange and falls back to it (`refreshToken ?? existing?.refresh_token ?? null`) — the same "read existing before writing" shape as D1's `two_step_pin` reuse for Meta's PIN-mismatch constraint.
- `GET`/`DELETE /api/companies/[companyId]/calendar` — member-readable status / admin-only disconnect (flips `status`, nulls both token columns, no-op-safe when nothing was connected) — a direct structural copy of D1's `whatsapp/route.ts`. `POST /api/companies/[companyId]/calendar/connect` — admin-only, body `{ code }`, upserts on `company_id` (idempotent reconnect, same convention as B1/D1).
- **What this ticket does NOT do**: no calendar listing/picker, no `freebusy.query` calls, no event creation — just obtaining and durably storing a valid, refreshable token plus which calendar (`'primary'`) it's for. I2 is the first real consumer of the stored `access_token`; nothing yet reads or refreshes it.
- Tests mock Google's token endpoint with a real local HTTP server (`tests/integration/helpers/google-oauth-mock.ts`, wired into `global-setup.ts` via `GOOGLE_OAUTH_TOKEN_URL`), same pattern and same reasoning as D1's `graph-api-mock.ts` (the route runs in a separately-spawned `next dev` process that can't share an in-process fetch mock with the test runner). A magic code (`"good-code-no-refresh"`) simulates Google's real reconnect-without-refresh-token behavior, letting `calendar-connection.test.ts` prove the retention logic against the actual stored row (via `getTestServiceClient()`), not just that the call doesn't error.

### Availability engine (Trello I2)

`src/lib/availability/engine.ts` (pure) + `src/lib/availability/load.ts` (IO) — given a service and a date range, computes bookable slots by intersecting `business_hours` (H2), existing `appointments` (H3), and the connected Google Calendar's `freebusy.query` result (I1). The first real consumer of I1's stored `access_token`. Split mirrors E2's `analytics/aggregate.ts` (pure, unit-tested) + `analytics/load.ts` (IO, shared by a route and a page) exactly — the ticket itself asked for "a pure function, easy to unit-test against fixed inputs," and this is what makes that literally true rather than aspirational.

- **`day_of_week` convention: `0 = Sunday`**, matching `Date.getUTCDay()`/Postgres's `EXTRACT(dow FROM ...)`. H2's own migration never pinned this down when it shipped (its `CHECK (day_of_week between 0 and 6)` doesn't say which end is which); this is the first place it's made concrete, since the engine has to actually resolve a calendar date to a `business_hours` row. Retroactively clarifies "Scheduling foundations" above.
- **Local wall-clock ↔ UTC conversion is hand-rolled via `Intl`**, no date/timezone library added (none exists in this repo) — `zonedTimeToUtc`/`tzOffsetMsAt` in `engine.ts` use the standard two-pass offset-resolution technique (format a UTC guess in the target zone to measure the offset, correct, re-measure once more to catch a DST-transition edge case), the same `formatToParts` house style `analytics/load.ts`'s `localDate` already established for the opposite direction (UTC instant → local calendar date).
- **Slot semantics**: the *reserved* interval checked for overlap (against `appointments` and Google-busy intervals alike) is `[start, start + duration + buffer)` — matches H3's own "buffer baked into `ends_at`" convention. The **returned** slot is `{ start, end: start + duration }` only; buffer is protected but never shown, per H3's own note that a display layer must subtract it back out. Only the visible `duration` portion has to fit inside a `business_hours` window — the trailing buffer may run past closing time (the last cleanup of the day happens after the doors close in real life), simpler than also constraining the buffer to the window and harmless since nothing else is ever scheduled in that trailing dead time.
- **Google freebusy failures degrade gracefully — never block booking.** If no calendar is connected (no row, or `status != 'connected'`), the stored token can't be refreshed, or the `freeBusy` call itself errors (network, Google outage), `loadAvailableSlots` still returns slots computed from `business_hours` + our own `appointments` alone, with `googleCalendarChecked: false` in the response so a caller (K-epic UI, Ana's future tool description) can know the live calendar wasn't actually consulted. Matches this codebase's existing pattern of never letting an external dependency's outage take down a core flow (product embeddings degrading to `null`, checkout links' `available: false` envelope). Accepted risk, stated plainly: a slot the merchant only marked busy in Google (not reflected in `appointments`) could still be offered when this path triggers — narrowed by I3 (real two-way sync, not built yet) and by the token-refresh logic below keeping the common "just expired" case from ever reaching this fallback.
- **Token refresh was added here, not deferred** — I1's own decision log flagged that nothing yet read or refreshed the stored `access_token`, and Google's tokens are short-lived (~1hr), so a real `freeBusy` call needs this to do anything at all. `src/lib/google-calendar/oauth.ts` gained `refreshAccessToken(refreshToken)` (mirrors `exchangeCodeForToken`'s shape, `grant_type: "refresh_token"`; Google's refresh response never includes a new `refresh_token`, so only `accessToken`/`tokenExpiresAt` come back). `load.ts` checks `token_expires_at` before calling Google, refreshes proactively when past/missing, and persists the new token via the service client — a refresh failure (e.g. a revoked grant) falls into the same graceful-degrade path as any other Google failure.
- **`src/lib/google-calendar/freebusy.ts`** (new) — `queryFreeBusy(accessToken, calendarId, timeMin, timeMax)`, a thin `POST /calendar/v3/freeBusy` wrapper. `GOOGLE_CALENDAR_API_BASE_URL` env override for tests, same pattern as `GOOGLE_OAUTH_TOKEN_URL`/`META_GRAPH_API_BASE_URL`.
- **Thin HTTP wrapper for testability**: `GET /api/companies/[companyId]/services/[serviceId]/availability?from=&to=` (member-readable, both params required — no default-range guessing like the analytics route, since a caller always has a specific window in mind). Not the real intended caller (J3's `find_available_slots` tool will call `loadAvailableSlots` in-process, same as the Agent Engine calling `ProductRepository` directly) — exists purely so the engine could be validated over real HTTP before that tool exists, identical justification to B5's `products/search/route.ts`.
- Tests: `tests/unit/availability/engine.test.ts` is the real correctness coverage (chunking, buffer-only-trailing-past-close, appointment/Google-busy blocking, past-slot exclusion, non-UTC timezone resolution) — no DB, runs regardless of Docker. `tests/integration/helpers/google-calendar-mock.ts` (new, mirrors `google-oauth-mock.ts`) stands in for `freeBusy.query`, keyed on the requested `google_calendar_id` (magic values `"busy-calendar"`/`"trigger-freebusy-failure"`) — since the I1 connect route always hard-codes `google_calendar_id: "primary"`, tests that need a specific mock scenario overwrite that column directly via the service client after a real connect, the same direct-row-write escape hatch other integration tests use for state no HTTP route can set. `tests/integration/availability.test.ts` covers the route end to end, including the token-refresh path (forcing `token_expires_at` into the past and confirming both a successful `freeBusy` call and a persisted new expiry).
- **`business_hours` is also enforced on the appointments *write* path** (found gap, fixed 2026-08-29 — not part of I2's original ticket scope, see decisions.md), not just advised by this read-only engine. `engine.ts` exports a second pure function, `isWithinBusinessHours({ timezone, businessHours, startsAt, durationMinutes })`, reusing the same local-day/timezone resolution as `computeAvailableSlots` but without requiring alignment to the slot-step grid (a manually entered time just needs to fit inside an open window). `appointments/route.ts` (POST) and `appointments/[appointmentId]/route.ts` (PATCH's reschedule branch) both call it and 400 with `"This time is outside business hours"` on a miss — **skipped entirely when the company has zero active `business_hours` rows**, so an unconfigured company (the default) can still accept bookings rather than being silently locked out.

### Calendar sync on booking (Trello I3)

Keeps a confirmed appointment's Google Calendar event in sync with `appointments` (H3) — **one-way only** (our writes → Google). An external edit or delete made by hand directly in Google Calendar is never reconciled back; that's deliberately deferred — see [this future Trello card](https://trello.com/c/y9YcEjLx/58-future-reverse-google-calendar-sync-external-edits-deletes-reconciled-back-into-appointments) for the reverse-sync work and why it isn't in the MVP.

- **Sync is keyed on `confirmed`, not on booking itself.** A `requested` appointment (pending manual approval, `companies.requires_appointment_approval = true`) never touches Google Calendar — the merchant's calendar should reflect real commitments, not requests still awaiting their own approval. A Google event is created the moment an appointment becomes `confirmed`, whether that happens immediately at `POST` (the auto-confirm case) or later via a `PATCH { status: "confirmed" }` on a previously-`requested` row.
- **Scope: create on confirm, delete on cancel, update on reschedule** — `completed`/`no_show` are after-the-fact labels that don't change anything about the event going forward, so they're left alone. Reschedule (`starts_at`/`service_id` changing) isn't explicitly named in the ticket but is included as a minimal necessary extension: leaving a stale, wrong-time event on the merchant's calendar after a reschedule would be worse than not syncing at all. A reschedule only patches the event's `start`/`end` — the summary is left as-is (the service essentially never changes on a reschedule, and updating it would need a customer-name refetch this path otherwise avoids).
- **Every sync operation is best-effort and never throws** — no connected calendar, an unrefreshable token, or the Google API call itself failing all degrade silently (`console.error`-logged), never blocking the appointment write that triggered them. `google_event_id` staying `null` (or being cleared to `null` on cancel) IS the signal that sync didn't happen or is no longer applicable — no separate boolean flag needed here, unlike I2's `googleCalendarChecked`, since a real nullable column already encodes the state.
- **`src/lib/google-calendar/connection.ts`'s `getValidAccessToken(companyId)`** — the "fetch the connection row, confirm it's connected, refresh an expired token and persist it, degrade to `null` on any failure" sequence, extracted from I2's `availability/load.ts` (which now calls this instead of its own inline copy) once I3 needed the exact same sequence a second time. An "extract on second use" moment, same judgment call as B4 exporting `validatePriceCurrency` once a second file needed it — not extracted preemptively in I2 because I3 didn't exist yet.
- **`src/lib/google-calendar/events.ts`** — `createCalendarEvent`/`updateCalendarEvent`/`deleteCalendarEvent`, thin wrappers over the Calendar API's `events` resource. Reuses `freebusy.ts`'s `GOOGLE_CALENDAR_API_BASE_URL` (exported from there since both files hit the same Google host — one real shared constant, not per-file duplication of unrelated config). Event `start`/`end` are sent as RFC3339 datetimes carrying `starts_at`/`ends_at`'s own `Z` UTC suffix directly — no separate Google `timeZone` field needed alongside an offset-bearing `dateTime`. **A `404`/`410` on delete is treated as success**, not an error: since I3 doesn't reconcile the reverse direction, an event that's already gone (deleted by hand, or a retry) self-evidently isn't there to delete — failing that call would be actively wrong.
- **`src/lib/google-calendar/appointment-sync.ts`** — `syncAppointmentConfirmed`/`syncAppointmentRescheduled`/`syncAppointmentCancelled`, the three operations the appointments routes call. Each is independently never-throwing on top of `getValidAccessToken` already being never-throwing.
- **Hooked into `appointments/route.ts` (POST)** and **`appointments/[appointmentId]/route.ts` (PATCH/DELETE)** — keyed off the appointment's **pre-update** `google_event_id` to decide which of the three mutually-exclusive branches applies (cancel-and-had-one / confirm-and-didn't-have-one / reschedule-and-had-one). A shared file-local `cancelGoogleEventAndClear` helper in `[appointmentId]/route.ts` avoids duplicating the cancel branch between `PATCH` and `DELETE`, which both live in that one file already.
- Tests: `tests/integration/helpers/google-calendar-mock.ts` was extended (not replaced) with `events` create/update/delete handlers, keyed on `google_calendar_id` the same way its `freeBusy` handler already was (`"trigger-events-failure"` fails every events call; deleting the fixed id `"already-gone-event"` returns `410`). `tests/integration/appointment-calendar-sync.test.ts` covers: auto-confirm creates an event; manual-approval defers creation until the confirming `PATCH`; no connection / an events-API failure both degrade to `google_event_id: null` without erroring the booking; both `DELETE` and `PATCH { status: "cancelled" }` delete the event and clear the column; a reschedule updates the event while keeping the same `google_event_id`; cancelling an appointment whose event was already externally deleted doesn't error. No new unit-test file — unlike I2's chunking algorithm, there's no meaningfully complex pure logic here to isolate; the wrappers are thin IO, covered by the integration suite via the mock.

### Ana's scheduling tools (Trello J3)

`src/lib/appointments/repository.ts` (`AppointmentRepository`) + four `AgentTool`s in `src/lib/agent-engine/tools/` — this is the ticket that gives Ana her hands. Structurally a copy of B5's `ProductRepository` + Malu's catalogue tools: a thin deterministic repository behind tools the model calls mid-turn, `companyId`/`customerId`/`conversationId`/`agentId` always taken from `ToolExecutionContext` (never model args), the service-role client by default with an injectable `supabaseClient?` override for tests, and each tool wired into `defaultTools` (`tools/registry.ts`) **and** listed in `AGENT_TOOL_SETS.ana` (`tools/tool-sets.ts`) — a tool in the registry is not offered to anyone until it's in a slug's set (J2).

- **`list_services`** — the deterministic read that grounds Ana in what the business offers (name / description / duration / price / category), the scheduling analog of `search_products`. **Added as a fourth tool beyond the card's named three** because `find_available_slots`/`book_appointment` both need a real `service_id` and nothing else exposed the catalogue to the model — resolving a service by name inside those tools would reintroduce the string-guessing the grounding work keeps removing (see the 2026-08-30 decisions.md entry).
- **`find_available_slots`** — calls I2's `loadAvailableSlots` in-process (same as the Agent Engine calling `ProductRepository` directly). Returns UTC slot instants + the business `timezone` (so the model can speak local time) + I2's `googleCalendarChecked` flag + a `truncated` marker; caps at 20 slots. An unknown/other-company service returns `{ available: false, reason: "service_not_found" }` rather than throwing.
- **`book_appointment`** — writes the `appointments` row, replicating `POST /api/companies/[companyId]/appointments` (H3) field-for-field: server-computed `ends_at` (`duration + buffer`), server-decided `status` from `companies.requires_appointment_approval` (`requested` vs `confirmed`, and the result says which so Ana can tell the customer), `isWithinBusinessHours` enforcement with the same permissive-when-unconfigured default, the `23P01` overlap-constraint catch → `{ booked: false, reason: "slot_unavailable" }`, and the I3 `syncAppointmentConfirmed` hook (only when `confirmed`; best-effort, `google_event_id` stays `null` on failure). All failures are returned result objects, never thrown — a throw aborts the whole turn (`tool-loop.ts`).
- **`cancel_appointment`** — soft-cancel (`status = 'cancelled'`, never a hard delete), **scoped in the repository to `customer_id` as well as `company_id`** so Ana can only ever cancel the booking of the customer she's talking to. Idempotent (`alreadyCancelled: true` on a re-cancel). Clears `google_event_id` and calls `syncAppointmentCancelled` if one was set. Takes an `appointmentId` from a `book_appointment` result earlier in the conversation — there is **deliberately no "list my appointments" tool** for MVP, so a booking from a much older conversation (outside the model's visible history) can't be cancelled here and falls to `request_human`. **Reschedule is not its own tool** — cancel then re-book, per the card.
- **Personality/system prompt**: migrations `20260830140000_set_ana_personality_and_system_prompt` (content-only, mirrors C2's Malu migration) + `20260830150000_reinforce_ana_date_handling` (full-rewrite reinforcement, same shape as Malu's `reinforce_*` migrations). Her booking-flow instructions (`list_services` → `find_available_slots` → `book_appointment`), "always speak the business timezone", "don't promise a slot is free when `googleCalendarChecked` is false", the approval-status explanation, reschedule = cancel + re-book, "you only handle scheduling — no products/prices/checkout", and (the reinforcement) "the customer gives timing loosely — turn it into a date range yourself, confirm softly when unsure, never demand an exact date/year". The platform guardrails in `prompt.ts` are still prepended verbatim.
- **Current-date anchor** (`prompt.ts` + `index.ts`, all agents): `buildSystemPrompt` now takes an optional `currentDate` string; `index.ts` loads the company timezone (`loadCompanyTimezone`, new, alongside `loadBusinessName`) and passes `formatCurrentDate(timezone)` → `"Thursday, June 12, 2026 (America/Sao_Paulo)"` (falls back to UTC when unset/invalid). Emitted as a real-context section (like `Business name:`), with a generic instruction to resolve relative dates ("next Thursday", "tomorrow", "the 15th") from it and confirm briefly when unsure rather than asking the customer to spell out a full date. **Root cause of a J3 hand-testing bug**: without a temporal anchor Ana literally could not resolve "próxima quinta" and fell back to demanding an exact date with a year. Opt-in param so the pure `prompt.test.ts` calls stay unaffected; `index.ts` always supplies it.
- **Known wording gap** (not fixed here, flagged in decisions.md): `CAPABILITY_GUARDRAIL`/`SCOPE_GUARDRAIL` are labelled platform-level but were written for Malu and still say "you can search the product catalog"/"helping this customer as a shopper" — harmless-ish for Ana since her tool set has no catalogue tools and her own prompt corrects the framing, but they should be genericised in a follow-up.
- Tests: `tests/integration/scheduling-tools.test.ts` (mirrors `checkout-link.test.ts` — imports the tool modules directly, real local Postgres, no Google connection so I3 sync degrades to `google_event_id: null`) covers `list_services` active-only scoping, real slot computation, the confirmed/requested status branch, overlap and outside-hours refusals, cross-company isolation, cancel + idempotency + the customer scoping, and one full `AgentEngine.run` (find → book → row lands). `tests/unit/agent-engine/tools/tool-sets.test.ts` and `tests/integration/agent-tool-sets.test.ts` gained assertions that Ana is offered the four scheduling tools and Malu is not. **Not run locally this session** (Docker/local Supabase was down) — unit + `tsc` + `eslint` are clean; the integration file follows the established pattern.

### Anonymous visitor identity + public chat API (Trello M3)

Third ticket of epic M — the first real app code in this epic. `POST/GET /api/chat/[companySlug]/[agentSlug]` is public and unauthenticated, so it lives outside the merchant-namespaced `/api/companies/[companyId]/...` tree entirely, at a new top-level `/api/chat/` route — same precedent as `/c/[trackingId]` (Trello E1): service-role client throughout, untrusted input used only as a lookup key, excluded from `src/proxy.ts`'s session-refresh middleware (added alongside the existing `c/` exclusion, same "no session to refresh on a public call" reasoning).

- **`AgentEngine.run({ companyId, conversationId, message })` needed zero changes** — confirmed by reading `src/lib/agent-engine/index.ts` directly before writing any of this. It was already channel-blind; this ticket is entirely about how a `conversationId` comes to exist for a channel that isn't WhatsApp.
- **Session id is client-generated (`crypto.randomUUID()`), stored in the visitor's own `localStorage`, sent as an opaque key — never a cookie.** The chat page (M4) is always served from Sidde's own origin even when embedded in a third-party iframe, so its `localStorage` is scoped to Sidde regardless of what site embeds it; no third-party-cookie problem to work around. The server never mints one, only validates the shape (UUID regex, `400` on a mismatch) before using it as a lookup key. New nullable-unique `customers.web_chat_session_id` column (migration `20260830195901`) — not part of M1/M2, this ticket's own schema need, same way H3 needed its exclusion constraint without a separate ticket.
- **`src/lib/web-chat/session.ts`'s `resolveWebChatSession`** — find-or-create the customer by `web_chat_session_id` (`channel: 'web_chat'`), find-or-rotate the active conversation (same 24h-inactivity TTL and rotation logic as `dev-chat-test`). **Deliberately not extracted into a module both routes share** — `dev-chat-test` is test-only scaffolding tied to its own deletion condition (D2 shipping, a different epic's ticket), not this one's call to touch; this is a fresh, independent implementation of the same shape, not a refactor of the old one.
- **Domain-allowlist check requires the client to self-report its embedding context — architecturally necessary, not a shortcut.** The chat page's own `fetch()` calls to this API are same-origin to Sidde regardless of iframe nesting, so the raw `Origin`/`Referer` headers on the API request are always Sidde's own URL, never the embedding site's — there is no way to observe "what site embedded this" from the API call alone. That information only exists client-side, at iframe-load time (`window.self !== window.top` + `document.referrer`); M4/M5 (not built yet) capture it and pass it as an optional `embeddedOn` field. `src/lib/web-chat/embed-authorization.ts`'s `isEmbedOriginAllowed` (pure, unit-tested) parses the hostname, `www.`-normalizes both sides, and fails closed on anything malformed. `embeddedOn` absent (direct visit to the standalone page) always passes regardless of the allowlist — the check only ever applies to embedded use.
- **`company_agents.status !== 'active'` (missing or paused) → a `403` indistinguishable from "never hired"** — never leaks *why* a chat is unavailable (not paying vs. paused vs. never hired), same "don't give an attacker a signal" reasoning as elsewhere in this codebase.
- **Three independent rate-limit checks, all before any OpenAI call, all POST-only** (`src/lib/web-chat/rate-limit.ts`) — WhatsApp's own implicit cost brake (a phone number) has no equivalent here, so this is the deliberate replacement (see the roadmap artifact's "Who's allowed to use it" section):
  1. Per-IP rolling window (new `chat_ip_rate_limits` table, migration `20260830195909`, RLS enabled with zero policies — service-role-only, same "deny everyone but the one caller who needs it" shape used elsewhere; 20 requests/60s, IP from `x-forwarded-for`'s first entry). A hit is recorded immediately once the check passes, **before** `AgentEngine.run()` is ever called, so a failed or retried attempt still counts — closes the "induce a failure to dodge the limit" loophole.
  2. Per-conversation rolling window — reuses `messages` directly, no new table (10 customer messages/60s).
  3. Per-conversation hard cap — same table, no time bound, a circuit breaker (200 total), not meant to be hit in ordinary use.
- **The customer's own message is persisted before calling the Agent Engine; the reply only after it succeeds.** A downstream `AgentEngine.run()` failure returns a generic `502` (never leaking internal error detail — unlike `dev-chat-test`, a merchant debug tool, this is real public traffic) but the customer's message is never lost. Verified live: a throwaway company with `OPENAI_API_KEY` briefly unset locally produced exactly this — a `502` with the customer's message still landing in `messages`, nothing else.
- **`GET` history spans every conversation for a customer+agent pair, not just the current active one** — conversation rotation (the 24h TTL) is an invisible implementation detail; a visitor refreshing right after a rotation boundary shouldn't see their history reset. Joins `messages` to `conversations` via PostgREST's `!inner` embed syntax, filtered on `customer_id`/`agent_id`. A session with no customer row yet returns `{ messages: [] }`, not an error — the common case today, since M4 doesn't exist yet.
- **No OpenAI mocking infrastructure added.** Every validation/auth/rate-limit path (404/403/400/429) short-circuits before `AgentEngine.run()` is ever reached, so the integration suite covers all of it with zero OpenAI involvement. The one path that needs a real model call was verified with a manual live smoke test instead (throwaway company + real hire via direct SQL, real HTTP calls against the live dev server): confirmed a real grounded reply, confirmed a second message with the same `sessionId` continues the same conversation (not a new one), confirmed `GET` returns the full, correctly-ordered history — then cleaned up via cascade delete.
- Tests: `tests/unit/web-chat/embed-authorization.test.ts` (exact match, `www.` normalization either direction, empty-allowlist-blocks-everything, malformed-value-fails-closed, direct-visit-always-passes). `tests/integration/web-chat.test.ts` covers every reject path (unknown slug → 404, not-hired/paused → 403, bad origin → 403, malformed `sessionId`/empty `message` → 400, fresh-session history → empty not error) plus all three rate limits — seeded directly via the service client rather than real POSTs, so the automated suite makes zero real OpenAI calls anywhere.

### Standalone hosted chat page (Trello M4)

Fourth ticket of epic M — the actual page a merchant links to instead of a WhatsApp number (bio, email signature, a QR code on a receipt). `src/app/talk/[companySlug]/[agentSlug]/` — public, unauthenticated, `talk/` added to `src/proxy.ts`'s exclusion matcher alongside `c/`/`api/chat/` (same "no session to refresh" reasoning). Pure consumer of M3's API; M3 itself is unchanged.

- **`page.tsx` is a Server Component** that mirrors (not imports) `resolveCompanyAndAgent` from the M3 route — same three-step lookup (company by slug → agent by slug+active → `company_agents` status), but returns page-shaped results instead of `NextResponse`. Company/agent not found, or never hired at all → `notFound()` (a broken/wrong link). Hired-but-**paused** → a soft inline "chat unavailable right now" state instead of a hard 404, since a pause is plausibly temporary. `generateMetadata` sets the tab title to `"{agentName} · {companyName}"`.
- **Built with a Stitch design ("Malu Chat — Customer Perspective"), with two deliberate departures from it.** (1) The mockup's "Verified Human-Centric AI" badge and "AI Assistant" page title are cut entirely — `Sidde_MVP_Specification.md` §7/§28 and CLAUDE.md's product-language rule are explicit that the customer should feel "someone from this store is helping me," never that they're talking to a bot; the real page shows only the agent's photo, name, and a presence dot. (2) The mockup's attach-file button is cut, not stubbed — there is no file-upload capability anywhere in this codebase, and a non-functional button is dead UI. One addition beyond the mockup: messages are grouped by calendar day (`Today`/`Yesterday`/date), computed client-side from `created_at` — the mockup only shows a static "Today," but M2/M3's whole point was persisting history across days, so a returning visitor's history needs to read sensibly across more than one.
- **`chat-widget.tsx` (`"use client"`)** owns the session id, message list, and send flow. The session id is read from `localStorage` (key `sidde-chat-session:{companySlug}:{agentSlug}`, `crypto.randomUUID()` if absent) but deliberately **not** React state — it's held in a `useRef` and only ever needed inside an effect/event-handler, not JSX, so there's nothing to synchronize into a render; "is the chat ready" is derived from `messages` (`null` until the history fetch resolves) instead. This sidesteps `react-hooks/set-state-in-effect` cleanly rather than fighting it with a deferred/microtask workaround.
- **Send is optimistic and never rolled back on failure.** The customer's message is appended to local state immediately, then `POST`ed; on failure (`429` or otherwise) an inline error appears but the optimistic message stays — matching the API's own documented guarantee that the customer's message is persisted server-side before the engine call, so a failed reply still means the message was received.
- Reuses existing per-agent branding helpers rather than inventing new ones: `defaultAgentName`/`agentPhoto` (`src/lib/agents/naming.ts` / `media.ts`), `company_agents.name` as the display-name override.
- Live-verified against the real project (`mateus-company`/`malu`): full send → real grounded reply → page refresh reloads the same history from the same `localStorage` session id → mobile viewport renders correctly → paused-agent state and unknown-slug `notFound()` both confirmed by toggling `company_agents.status` directly.

### Embeddable widget script (Trello M5)

Fifth ticket of epic M — the last piece of the "who's allowed to embed this" story M1/M3 designed but never got to exercise for real: `embeddedOn` has existed as an API parameter since M3, but M4's direct-visit page never embeds itself, so nothing had ever sent a real one until this ticket.

- **`public/widget.js`** — the bootstrap `<script>` a merchant pastes into their own site. Plain, dependency-free JS (no build step, no React) — it has to run correctly on an arbitrary third-party page regardless of that page's own framework/bundler/CSP, the same "zero assumptions about the caller" posture `/api/chat/` and `/c/[trackingId]` already take. Reads `data-company`/`data-agent` off its own `<script>` tag via `document.currentScript` (captured immediately, before any async work — required for that API to work at all) and derives the Sidde origin from its own `src` (`new URL(script.src).origin`) rather than hardcoding it, so the same file works unmodified in local dev and production. Renders a fixed circular launcher (bottom-right, brand indigo, no illustrated character — the Stitch "Embedded Agent - Animated Preview" reference has one, but that art doesn't exist as a real asset here and the user explicitly treated the reference as directional, not final). Lazily creates an iframe (`{origin}/talk/{company}/{agent}?embedded=1`) only on first open, not on page load. **Responsive sizing is pure CSS** (`@media (max-width: 480px)` switches the open panel to fullscreen) — no JS-driven resize protocol.
- **`embedded=1` on the iframe URL drives the UI only (the close button); `document.referrer` drives the actual security check — two different signals for two different jobs, on purpose.** Reading `window.self !== window.top` client-side to gate the close button's visibility would need an effect (browser-only value, unavailable during SSR), which either causes a hydration mismatch or fights `react-hooks/set-state-in-effect` the same way M4's session id did (solved there via a ref, but that trick only works for values that never affect JSX — a close button's visibility genuinely does). Putting `embedded=1` on the URL sidesteps the whole problem: it's a normal search param, read via `useSearchParams()`, identical during SSR and hydration. Trusting the URL for this is fine specifically *because* it's UI-only — a hand-crafted `?embedded=1` on a direct visit just shows a close button that posts to a parent that isn't listening, harmless. `document.referrer` is never cached (in state or even a ref) — it doesn't change during the page's life, so it's read fresh at each `fetch()` call site instead.
- **`chat-widget.tsx` treats any `403` from the history `GET` as "blocked in this embedded context," no error-message parsing.** `page.tsx` already confirmed the agent is actively hired before `ChatWidget` ever renders, so once mounted, a `403` can only mean the domain allowlist rejected `embeddedOn` — renders a compact `unavailableHere` state, input never shown. The header's `X` close button (only rendered when `isEmbedded`, reuses the existing `XIcon`) does `window.parent.postMessage({ type: "sidde-chat:close" }, "*")` — `"*"` is correct here, not a shortcut: the widget can't know the embedding site's origin in advance, and the payload carries nothing sensitive. `widget.js`'s own listener validates `event.origin` before acting on an incoming close message.
- **Found and fixed a real fail-open gap in `isEmbedOriginAllowed`** (`src/lib/web-chat/embed-authorization.ts`), pre-existing since M3 but never exercised until this ticket sent a real `document.referrer`: `if (!embeddedOn) return true` treated an **empty string** the same as `null`/`undefined` (always allowed). A genuinely-embedded visitor whose `document.referrer` is stripped by the host page's own `Referrer-Policy` would have silently bypassed the allowlist. Now `null`/`undefined` (not embedded) still passes; `""` (embedded, unreadable origin) fails closed like any other malformed value. One new unit test (`isEmbedOriginAllowed("", [...])` → `false`); every prior test still passes unchanged.
- **No dashboard "get your embed code" UI** — that's M6; verification used a hand-constructed `<script data-company="..." data-agent="...">` tag. **No `next.config.ts` change** — confirmed no `X-Frame-Options`/CSP headers exist anywhere in this app that would block `/talk/` from being iframed.

**Two real bugs found and fixed during live verification, both in code from this same work, neither previously exercised:**
1. `CopyField`'s clipboard-copy handler (`web-chat-channel-card.tsx`) called `navigator.clipboard.writeText` unguarded — a denied/unavailable clipboard permission (real in some browser/OS configurations, and always true in this session's sandboxed verification browser) threw an unhandled promise rejection. Reworded to avoid literal angle brackets ("...before your site's closing body tag") rather than escaping — simpler and reads fine.
- Live-verified end-to-end against a fresh throwaway account created through the real sign-up flow (not the dev-only DB shortcuts used elsewhere this session, since dashboard pages need a real authenticated session): M6's card renders the correct link/snippet for the throwaway company+agent; M7's list editor adds, normalizes (`https://www.mymerchantsite.com/` → `www.mymerchantsite.com`), saves, removes, and re-saves to `{}` correctly (confirmed via direct `select` after each save); an invalid entry (`"not a valid domain"`) is rejected with a clear inline error and never reaches the database. Throwaway account/company deleted afterward via Supabase MCP.

## Data model

Implemented in `supabase/migrations/` (2026-08-23), all tables in `public` schema with RLS enabled:

- **users** — public profile mirroring `auth.users` (`id` FK's to `auth.users.id`). Auto-populated by a trigger (`private.handle_new_user`) on `auth.users` insert.
- **companies** — one row per merchant business (Malu's employer). Holds business info, shipping/return/payment policy text, `faq` (jsonb), currency/country/timezone, plus (Trello M1) a unique `slug` (auto-generated, powers the web chat URL) and `allowed_embed_domains` (`text[]`, deny-by-default widget allowlist). See "Web chat channel — schema" above.
- **company_users** — join table, user ↔ company membership with `role` (enum `company_role`: `owner`/`admin`/`member`). Unique per (company_id, user_id).
- **agents** — platform-defined AI employee catalog (e.g. Malu, slug `malu`). Managed by Sidde, not merchants; merchants only read active agents.
- **company_agents** — an agent hired by a specific company (`status`: enum `company_agent_status`, `active`/`paused` only — no separate "hired" state). Unique per (company_id, agent_id).
- **customers** — a company's end customers (`channel`: enum `conversation_channel` — `whatsapp` or, as of Trello M1, `web_chat`).
- **conversations** — a thread between a customer and a company's agent; `agent_id` FKs to the global `agents` table (per `Sidde_MVP_Database_Tables.md`), not `company_agents`; `channel` uses the same `conversation_channel` enum as `customers`; `open_ai_conversation_id` links to the OpenAI-side conversation. `status` (`active`/`closed`/`paused`) is still plain `varchar` + `CHECK`, not an enum — left as-is deliberately.
- **products** — a company's catalog (name/price/currency/stock/images/category/variants/attributes as jsonb), imported from CSV/XLSX today (Trello B4), designed for future ecommerce integrations (Shopify/WooCommerce/etc.) without changing Malu's `ProductRepository` abstraction.
- **company_whatsapp_connections** — one row per company (Trello D1): WhatsApp Cloud API connection state (`phone_number_id`/`waba_id`/`display_phone_number`/`status`/`token_expires_at`) plus `access_token`, which is column-privilege-locked (see Access model below) rather than split into a second table. `token_expires_at` (migration `20260826112152`) just records when the 60-day Meta token goes stale — no auto-renewal exists yet (see decisions.md).
- **events** — append-only log of the three trackable behaviors from spec §14–15: `buying_intent`, `product_recommendation`, `checkout_click` (single shared table with a `type` enum column, not one table per type). Scoped to `company_id`, `conversation_id`, `customer_id` (all required); `agent_id`/`product_id` optional. `tracking_id` is the `sidde.link/c/{tracking-id}` lookup key, set on `checkout_click` rows when the link is created and read back on click; unique when present (partial unique index). `metadata` jsonb holds type-specific extras (e.g. `destination_url`) that don't warrant their own column. No `updated_at`/no update trigger/no update or delete RLS policies — rows are never mutated after insert.
- **messages** (Trello M2) — append-only, per-conversation chat history for the web chat channel (`role`/`content`), same shape/RLS pattern as `events`. See "Message history table" above for why this exists despite the app's original "no messages table" design.
- **services** (Trello H1) — a company's bookable offerings (name/description/duration/buffer/price/currency/category), the scheduling-agent analog of `products`. See "Scheduling foundations" above.
- **business_hours** (Trello H2) — a company's recurring weekly availability template (`day_of_week`/`start_time`/`end_time`), whole-array-replaced via PUT. See "Scheduling foundations" above.
- **appointments** (Trello H3) — a booked (or requested) slot against a `service`, with DB-level overlap prevention (`EXCLUDE USING gist`) and server-computed `ends_at`/`status`. See "Scheduling foundations" above.
- **company_calendar_connections** (Trello I1) — one row per company: Google Calendar OAuth connection state (`provider`/`google_calendar_id`/`status`/`scopes`/`connected_at`) plus `access_token`/`refresh_token`, both column-privilege-locked (see Access model below). See "Google Calendar connect flow" above.

### Enum types

Fixed-value columns use real Postgres enums (not varchar+CHECK) where the value set is small and stable:
- `company_role` (`owner`/`admin`/`member`) — `company_users.role`
- `company_agent_status` (`active`/`paused`) — `company_agents.status`
- `conversation_channel` (`whatsapp` only for now) — `customers.channel` and `conversations.channel`. Adding a channel later (website, Instagram, ...) requires an `ALTER TYPE ... ADD VALUE` migration.
- `event_type` (`buying_intent`/`product_recommendation`/`checkout_click`) — `events.type`.
- `appointment_status` (`requested`/`confirmed`/`cancelled`/`completed`/`no_show`) — `appointments.status` (Trello H3).
- `calendar_connection_status` (`pending`/`connected`/`disconnected`) — `company_calendar_connections.status` (Trello I1).
- `message_role` (`customer`/`agent`) — `messages.role` (Trello M2).

`conversations.status` was deliberately left as `varchar` + `CHECK` (`active`/`closed`/`paused`), not converted — only `company_agents.status` was simplified to an enum, per an explicit product decision (see decisions.md).

Checkout-link **creation** is implemented (Trello C4, see the Agent Engine section); the **redirect** service that resolves a link and records the real click (E1) is not built yet, so minted links currently 404.

**Superseded as of Trello M2** — see "Message history table" above. Originally: no `messages` table by design, since message history wasn't persisted in our own DB; `conversations.open_ai_conversation_id` alone was used to fetch history from OpenAI's Conversations API on demand. That's still true for how the Agent Engine itself works — the new `messages` table is a display-only side effect written by the web chat channel, not a replacement for the engine's own memory.

### Access model

- All company-scoped tables (`companies`, `company_agents`, `customers`, `conversations`, `products`) are readable/writable only by members of that `company_id`, via three `security definer` helper functions: `private.is_company_member(company_id)`, `private.is_company_admin(company_id)` (admin = `owner`/`admin` role), and `private.is_company_owner(company_id)` (owner only). `is_company_owner` exists solely to gate `company_users` rows whose role is or would become `owner` — everywhere else, `owner`/`admin` are equivalent.
- These helpers live in a **`private` schema**, deliberately not listed in `supabase/config.toml`'s `[api].schemas` (only `public`, `graphql_public` are exposed) — this keeps them callable from RLS policies and triggers while blocking direct PostgREST RPC access (`/rest/v1/rpc/...`). Any new internal-only helper function should go in `private`, not `public`.
- `agents` is readable by any authenticated user (`is_active = true` rows only); only `service_role` can write to it (no insert/update/delete policies for regular users) — it's Sidde's platform catalog, not merchant-editable.
- Every table has a `before update` trigger (`public.set_updated_at`) that stamps `updated_at = now()`.
- `company_whatsapp_connections.access_token` (Trello D1) is locked down below the table's own RLS policies: migration `20260826104820` revokes the table-wide select/insert/update privilege and re-grants it back per-column, naming every column except `access_token` — a column-level revoke layered on top of an existing table-wide grant is a no-op in Postgres, so the table-wide privilege has to go first. This blocks that single column for every regular client regardless of row-level access, while every other column on the same row still follows the normal member-read/admin-write RLS. Only `src/lib/supabase/service.ts`'s service-role client can touch it.
- `company_calendar_connections.access_token`/`.refresh_token` (Trello I1) follow the identical pattern (migration `20260829201627`), just locking two columns instead of one — see "Google Calendar connect flow" above.

## Conventions

### Supabase database changes

The Supabase CLI only picks up flat, timestamped `.sql` files directly in `supabase/migrations/` (no subfolders) — that's the single source of truth for schema and security, applied in order.

- **`supabase/migrations/`** — all schema and security changes go here as migrations, one logical change per file, named `<timestamp>_<description>.sql` (e.g. `supabase migration new create_employees_table`). This includes:
  - Table creation / alteration (`CREATE TABLE`, `ALTER TABLE`)
  - Row Level Security: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` plus `CREATE POLICY ...` — enable RLS in the same migration that creates the table, don't leave a table without policies even temporarily
  - Indexes, functions, triggers, views
- **`supabase/seed.sql`** — local dev fixture/sample data only (not schema). Runs after migrations on `supabase db reset`. Use `INSERT ... ON CONFLICT DO UPDATE` (upsert) so it's safe to re-run.
- **`supabase/functions/`** — edge functions, one subfolder per function (Deno).

Never hand-edit the remote database directly — always go through a migration so `supabase/migrations/` stays the reproducible history of the schema.

When applying migrations via the Supabase MCP tool (`apply_migration`), it only writes to the remote database — it does **not** create a local file. Always also write the matching `.sql` file to `supabase/migrations/` using the exact `version`/`name` reported by `list_migrations`, so local files and remote history stay identical.

### Supabase MCP server

Configured in `.mcp.json` (checked into the repo, no secrets — it authenticates via browser OAuth):

```json
{ "mcpServers": { "supabase": { "type": "http", "url": "https://mcp.supabase.com/mcp" } } }
```

- **No `project_ref` query param** — despite being the documented/intended way to pin every MCP call to the **ai-employees** project (so the unrelated "Faceless Videos" project in the same org can't be touched by accident), authenticating against a `project_ref`-scoped URL currently fails outright (`"resource: Resource must be a valid MCP endpoint"`) — a known, open upstream bug in Supabase's hosted MCP OAuth (`supabase/agent-skills#147`), not a config mistake. See the 2026-08-27 decisions.md entry. **Until that's fixed, there is no URL-level guardrail** — always pass and double-check `project_id: "wtewquippvcteuxzcztd"` explicitly on every `apply_migration`/`execute_sql` call. Revert to the scoped URL once Supabase closes that issue.
- `read_only` is deliberately **not** set — `apply_migration` needs write access (see the migration convention above).
- Auth is dynamic client registration (browser OAuth). Run `/mcp` in an interactive terminal session, pick `supabase`, and choose Authenticate. There is no token to store. In CI, pass a personal access token instead via a `headers` entry: `"Authorization": "Bearer ${SUPABASE_ACCESS_TOKEN}"`.
- Optional `features=<groups>` param narrows which tool groups load (e.g. `database,docs`); left at the default.

### Testing

- `npm run test:unit` — pure logic, no external services. Currently empty (see `tests/unit/README.md`).
- `npm run test:integration` — starts local Supabase (Docker), resets it from `supabase/migrations/`, boots a real `next dev` on port 3100, and runs `tests/integration/**` against it over real HTTP with real signed-up users. One command, needs Docker Desktop running. See the 2026-08-25 decisions.md entry for why this hits real infra instead of mocks.
- Local Supabase ports are shifted to `553xx` (not the `543xx` defaults) in `supabase/config.toml`, to coexist with the unrelated "Faceless Videos" project's own local stack on this machine.

**Where new tests go:**
- One file per feature/domain area: `tests/integration/<area>.test.ts` (e.g. `companies.test.ts`) for tests that go through the actual Next.js API routes over HTTP.
- `tests/integration/<table>-rls.test.ts` (e.g. `company-users-rls.test.ts`) for tests that call PostgREST/RPC directly via supabase-js, bypassing the Next.js app entirely — use this when testing an RLS policy or Postgres function itself (whether an admin/owner/member can do X), not app-layer behavior.
- Reuse `tests/integration/helpers/`: `auth.ts`'s `signUpTestUser()` for a fresh authenticated test user (returns `userId`, a ready `cookieHeader` for HTTP tests, and a `client` for direct supabase-js calls), `request.ts`'s `api()` for HTTP calls against the test server, `env.ts`'s `getTestEnv()` for the local Supabase URL/key. Don't re-implement the cookie-jar/session dance those already handle.
- `tests/unit/<name>.test.ts` only once there's pure logic worth isolating from the HTTP/DB layer (see its README).
- Once `supabase/functions/` has real edge functions: `tests/integration/<function-name>.test.ts`, calling it over HTTP against `getTestEnv().supabaseUrl + "/functions/v1/<function-name>"` — `supabase start` already runs the local edge runtime, no extra setup needed. No frontend/UI tests in this repo (see CLAUDE.md) — the priority is backend logic, edge functions, RLS, and other Supabase-level behavior.

**CI:** `.github/workflows/test.yml` runs both `unit` and `integration` as separate jobs on every PR/push targeting `main`. The `integration` job needs no extra setup beyond installing dependencies — Docker is preinstalled on `ubuntu-latest` runners and the `supabase` CLI is a devDependency, so `npx supabase` (used internally by `npm run test:integration`) just works. **Both jobs use `npm install`, not `npm ci`** — deliberately, since `npm ci` repeatedly hit a real npm bug (`npm/cli#4828`) that silently fails to install the correct platform-specific optional dependency for native-binary packages with many platform variants (hit with both `supabase`'s own CLI binaries and, separately, `rolldown`/Vitest 4's — see the 2026-08-27 decisions.md entries). To actually block merging on these, enable "Require status checks to pass" for `main` in GitHub's branch protection settings and select both jobs — that part isn't in this repo, it's a GitHub UI/API setting.
